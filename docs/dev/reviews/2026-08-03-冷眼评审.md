# 冷眼评审报告（2026-08-03）

评审者：全新上下文的 AI 评审会话（未参与本仓库任何开发）。
实测基线：`pytest -q` 45 passed in 4.28s（注意：含 1 条真实 API 冒烟，.env 有 key 时会静默花钱）；`-m "not llm"` 44 passed, 1 deselected。
文档数字复算：REAL_TRAJECTORY 估算 243、四工具 schema 389、拍平后 956 字符、原始 JSON 1505 字符——全部与代码实测一致。

## 严重

1. loop 会被「合法 JSON 但非对象」的 arguments 直接崩掉，且不回填 tool 消息。
   src/pai/loop.py:102-107。json.loads 只挡 JSONDecodeError；模型返回 `[1,2]`、`null`、`"hello"` 时，`t.run(**args)` 在进入 Tool.run 的 try 之前抛 `TypeError: argument after ** must be a mapping`，loop 整个崩掉（评审已实测三种输入全崩）。同时打穿两条自家决策：第 2 条「任何分支都必须回填 tool 消息」、第 1 条「Tool.run 边界保证任何调用路径不漏」。
   建议：json.loads 后加 `isinstance(args, dict)`，非 dict 走坏 JSON 同款错误回填；补测试。

2. STATUS.md 的「45 passed，全部离线」与事实不符。
   docs/STATUS.md:45。45 = 44 离线 + 1 条 llm 真实冒烟；纯离线是 44 passed, 1 skipped。违反 AGENTS.md「数字要真实」铁律；实际后果：任何有 key 的人跑全量测试就静默花钱。
   建议：改为「44 离线 + 1 llm 冒烟（有 key 时运行）」。

3. thinking mode 盲点：devlog 断言与 loop 实现二者必有一错。
   docs/devlog.md:129 称 deepseek-v4-flash「思考模式默认开启」；loop.py:77-87 组装 assistant_entry 时丢弃 reasoning_content。refs/deepseek-api/guides/thinking_mode.md:99,186 写明：带 tools 的请求若未正确回传 reasoning_content，API 返回 400。目前没炸是因为实测 session 里 reasoning_tokens 全为 0（即思考模式实际没开）——这又与 devlog 矛盾。无论哪边错，两个互相矛盾的断言不该并存。
   建议：先核实 v4-flash 到底默认开不开；开则 loop 必须回传 reasoning_content（且 anchor 的 completion_tokens 口径要重审），不开则纠 devlog。

## 值得改

4. decisions 第 19 条「切点几乎不动」论证有漏洞。
   「均匀偏差不影响切点」只在切点按比例定义时成立；pi 的 find_cut_point 按绝对预算切（keepRecentTokens=20000）。1.5 倍低估意味着想保 2 万实际保约 3 万，挤占 reserve 余量。实现 find_cut_point 前必须重审。

5. decisions 第 8 条与第 6 条自相矛盾。
   第 6 条：低估是唯一会炸窗口的方向；第 8 条：未知 role 静默记 0——0 是最极端的低估，且是「悄悄进入阈值判断的数」，恰是第 8 条自己要避免的。建议未知 role 仍按 content 估算（宁可高估）或留告警路径。

6. decisions 第 9 条理由不成立。
   「严格大于防阈值横跳」防不了——边界上 > 与 >= 只差 1 token。真防横跳的是压缩后落点远离警戒线。结论无害但理由错，且会被当面试话术背出去。建议改为「边界取舍无实质影响，定一个并用测试钉住」。

7. 锚重置后的读数盲区——已知缺陷 1 的严重性被低估。
   compact() 重置 anchor=None 后，紧接着的 context_tokens 退化为纯估算（-33%），而这恰是最需要准确回答「压缩救回来了没有」的时刻（熔断器依赖它）。建议：熔断器判断改用压缩后首次真实 usage 回传，此点现在就补进 STATUS 缺陷 1。

8. loop 层锚簿记无测试钉住。
   loop.py:92-94 的 `anchor_index = len(messages)` 是 off-by-one 高危点；评审实测改成 len(messages)-1 后 45 测试照样全绿（test_loop.py:105 只断言 estimated > 0，断言过弱）。建议：FakeClient 两步带 usage 脚本，精确断言第二条 usage 的 estimated == anchor + 尾部估算。

9. 锚定精度测试与活代码危险耦合。
   test_compaction.py:473-497 的 REAL_USAGE_STEPS 真实值录制于当时的工具 schema，测试却用 get_tools() 取活 schema——将来改一句工具描述就可能假失败且报错不指向真因。建议把录制时的 schema 冻进夹具。

10. 无 docstring 的工具在装饰时崩 IndexError。
    tools/__init__.py:64 `splitlines()[0]` 对空 docstring 崩（已实测）。改为条件取值或显式报「工具必须有 docstring」。

11. 单轮多 tool_calls 无测试覆盖。
    所有测试脚本每轮只有一个 tool_call；「N 条 tool 消息按序配对」「合法+未知工具混同轮」两个配对不变量无测试。DeepSeek 会发并行工具调用，非假想场景。

12. decisions 第 16 条「32 倍」的两个输入项偏虚。
    0.64 系数来自单条小轨迹的字符比（非 token 比，且强依赖轨迹形态）；原样发吃缓存的前提是 tools 逐字节一致带上——届时「不听话」的模型能真的发出工具调用，还牵连 reasoning_content 回传义务。方向不变，但实现 summarize 时要把这两个变量补进实验设计。

## 可选

13. AGENTS.md:41 表述不准：`dict[str, X]` 在 3.9 运行期合法（PEP 585）；真正需要 future import 的只有 `int | None`（PEP 604）。fake_llm.py:31 无 future import 用 `list[dict]` 实跑通过即证据。
14. loop 的 client / response 无类型注解，违反自家规矩；可给最小 Protocol（chat.completions.create），顺带静态约束 FakeClient 同构性。
15. session.py:18 文件名精确到秒，同秒两个 SessionLog 写同一文件。加毫秒或计数器。
16. serialize_conversation 不跳过 system 消息——summarize 时 system 会同时出现在拍平文本与新上下文里，浪费摘要预算。实现 summarize 时显式决定。
17. read_file 截断后无分页/offset，模型可能基于残缺视图去 edit。可在截断提示语里建议模型用 bash 分段读，零成本。
18. session=None 时也每步计算 estimated，纯浪费（量极小）。
19. estimate_tokens 假设 content 是 str/None；OpenAI 协议 content 可为分段列表，接多模态前要处理。
20. decisions 第 7 条理由已过时：「400 字符=100 token 心智模型」已被第 15 条废弃，引用链未回收（结论仍成立）。

## 对已知 6 条缺陷的重评

缺陷 1 的「重置为 None」方向对但不完整（见第 7 条）；其余 5 条自评准确。
