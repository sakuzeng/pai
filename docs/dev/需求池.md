用户提出的想法在这里落地，然后才决定去哪。 与 [TODO.md](TODO.md) 的分工是硬的：
TODO 是「已确认要做的事」，这里是「想要但还没评估的事」——混在一起会稀释 TODO
那句「唯一待办入口」的权威性。

## 规矩（三条）

1. 一行一条，记原话，不转述。
   转述会丢掉决定性的细节：2026-08-10 「点一下展开」这五个字直接决定了需求归属 TUI 阶段；
   同一天我把「`.env` 按包位置解析」转述成「pai 起不来」，差点修错方向。
2. 三种出路，必须标注：
   - 升格 → 立 [features/](features/README.md) 档案，走 brainstorm → spec → plan；
   - 降格 → 小改动，直接进 TODO 一行；
   - 不做 → 划掉 + 一句理由（保留记录，不删）。
3. 不许长期堆积：每个路线图阶段动工前清一次。

### 2026-08-19 `!小修` 自助门要不要收紧（用户提出，待裁决）

用户原话：「做这些分支的时候没有跟我讨论和进行计划的相关落盘了吗，这是为什么呢」

背景见 devlog 同日「流程偏离自查」。问题的实质不是这一轮做错了什么，而是
`guards/design_gate.py` 的 `!<理由>` 放行是自助的：写理由的人和认理由的人
是同一个，于是它约束的只是自律。十次改动里六次走这条口子，就是这个结构的结果。

我能想到的两条路（未替用户选，等裁决后升格 decisions）：
- 限定用途：`!` 只许用于不改变行为的改动（typo、注释、纯文档、格式），
  凡动 src 行为的一律立档案。判据清晰，代价是小 bug 修复也要走全流程。
- 保持自助但留证据：`.active` 里必须写明改动规模预估（文件数/行数），
  超过阈值不许走 `!`。代价是阈值本身要拍一个数，且预估仍由我自己写。

### 2026-09-10 `--resume` 看起来没恢复对话（已升格 feature 48，已交付）

  代码把 `messages` 里的旧对话画上屏。默认开备用屏，于是 `--resume` 起来后的界面

  `messages` 为空时造 system 条目，`_inject_instructions` 见到旧的指令消息就跳过，
