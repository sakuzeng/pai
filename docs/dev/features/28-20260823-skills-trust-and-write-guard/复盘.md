# 28 · 复盘（四问）

## 学到什么

- 「同族问题合并交付」的判断被验证了：写面、信任、软链附属三条来自三个不同
  出处（25 复核中 4、25 遗留 1、25 复核中 3 残余），但根都是「skills 是持久化
  指挥权位点」——合成一个档案后，三问拍板互相咬合（写面挡住塞进来的、门禁
  挡住已塞进的、软链只放用户自己的），单独修任何一条都留缺口。
- 装配期的 reader 版 asker 是个现成的门禁挂点：信任对话不需要新交互机制，
  `asker_ref` 在 TUI 起来前就可用（feature 12 为权限问答建的通道），
  「新需求先找既有缝」再次省掉一个子系统。
- pty e2e 能钉「录制之外」的行为：信任问题发生在 TUI 起来之前，录制文件里
  没有，靠 Session.raw 裸字节断言——feature 13 为退出提示留的这条通道
  这次接住了启动路径。

## 哪里走了弯路

- 没大弯路。一处返工：27 的子目录回归测试与 25 的 skill e2e 被新门禁连带
  打红，需要预置信任标记——这不是测试写错，是新特性改变了它们场景的前置
  条件。教训是引入「默认拒绝」类特性时，先 grep 一遍现有测试里同场景的
  用例，主动改而不是等红。

## 我现在质疑什么

- 质疑信任粒度的「项目级一次性」：信任后新增的 skill 静默生效（CC 同款
  弱点）。更强的形态是按 skill 内容 hash 记信任、新增/变更再确认——
  成本是标记文件从布尔变清单。等真实事故或 CC 先踩了再说，已在 devlog
  「已知边界」记录。
- 质疑危险写名单的路径段匹配：`.pai/skills` 子串匹配有理论误伤
  （`x.pai/skills-y` 这类名字），与 `.git/hooks` 既有模式同类同险。
  真实撞上再收紧为分隔符边界匹配，不预支。
- 质疑 once 的「未信任不加载」对 CI 场景的摩擦：脚本化跑 pai 的人要先开
  一次交互模式才能信任项目 skills，没有非交互的信任通道（比如
  `pai --trust-project-skills` 或 settings 项）。当下 pai 没有 CI 用户，
  但这个摩擦是结构性的——如果将来有人报，出路已经想好，不用重新设计。

## 下次怎么做更好

- 「默认拒绝」类特性动工前，把受影响的既有测试清单先列出来（grep 场景
  关键词），改场景前置与写新测试同批做，省一轮红。
- 三家对照在拍板选项里给「AI 推荐」时，把推荐理由里的成本差写得更直白
  （这次 A 与 B 的差是「一行 warn」对「新增信任存储 + 首扫交互」，用户
  仍选了 B——说明推荐权重里「彻底」比「便宜」重，下次校准）。
