# 09-20260810-working-dir-boundary · 复盘

## 学到了什么

**注入验证本身会写错，而且注错的表现与「测试无效」一模一样——都是全绿。**

Task 7 验「显式 ask 与兜底 ask 的区分」时，我把 `bypassPermissions` 从第 4 步挪到
第 7 步之前，14 条全绿。第一反应是「这个区分没被测住」。复查才发现：显式 ask 的检查
仍在 bypass 之前，照样先命中返回，**注入根本没打中目标**。

可迁移的形式：**变异测试的每一次注入，都要先回答「我改的这行，在目标场景里真的会被
执行到吗」**。控制流靠前的分支会屏蔽掉靠后的注入点，而屏蔽的结果与「没有测试覆盖」
在现象上不可区分。feature 07 那三条注入没撞上，纯属运气好——它们改的都是必经之路
（求值顺序常量、`require_all` 计算、拆分函数）。这条够格进 knowledge/concepts/。

**第二条：「默认值是常量还是函数」是一个独立的设计维度，而且默认被忽略。**
feature 07 我把 CC 的三态引擎抄得很细（求值顺序、匹配下放、bash 四坑），
唯独把兜底抄成了 `default_decision = "allow"` 一个常量——因为**常量是「默认值」这个
词的默认形状**，压根没想过它可以是个函数。CC 那边根本没有这个常量，
兜底是 `in_working_dir ? allow : ask`。抄一个系统时，最容易漏掉的不是复杂的部分，
是**你以为自己已经理解的那个简单部分**。

## 哪里走了弯路，为什么

**弯路一：feature 07 的前置精读有缺口，而我在那时没发现。**

`claude-docs/permissions-hooks.md` 里「工作目录 / cwd / 目录边界」grep 零命中，
pi 侧整个阶段只有一句「参照 `beforeToolCall`」。当时为什么没察觉：
我按**官方文档的章节结构**做精读，而目录边界在官方文档里不是独立一章——
它藏在权限模式与工具行为的描述里。笔记覆盖了文档的每一节，却漏掉了一整层机制。

换个人会不会踩：**会**。防呆办法不是「读得更仔细」，而是**精读之后做一次「反向对照」**：
拿实现好的东西去跑几个真实场景，看行为对不对，而不是只对照文档条目打勾。
用户那句「上级目录照理来说不能看」就是一次反向对照，一句话就把缺口炸出来了。

**弯路二：把「不做 bash 目录边界」顺手推成了「bash 兜底 allow」。**

这两件事在 spec 里被我写成了一条。真实关系是：不解析 bash 命令里的路径（做不到，
没有分类器）**不蕴含**「bash 默认放行」——完全可以不解析路径但兜底 ask。
当时的思路是「既然管不了它，就别管它」，而正确的思路是「既然管不了它，
就用最保守的一档兜着」。用户问「CC 里不擅自 push 是怎么实现的」时才暴露出来。

## 我现在质疑什么

**质疑一（最实质的一条）：「bash 不参与边界」这个洞，比拍板时看起来严重得多。**

拍板时它被描述成「bash 不做目录边界，如实记洞」。做完之后我更准确地理解了它的形状：
洞**不在默认路径上**（bash 默认 ask，已经是最保守的），而在**用户为了可用性必然要走的
那条路上**——once 模式下 bash 全被 deny，用户要让它干活，只有两条路：配 allow 白名单，
或开 `--dangerously-skip-permissions`。而一旦配了 `allow: ["Bash(cat *)"]`，
`cat ../../../etc/passwd` 就畅通无阻。

也就是说：**边界保护在用户「正常使用」的那一刻就被自己配的白名单穿透了。**
`test_bash_ignores_the_boundary_and_this_is_the_known_hole` 钉的正是这个，
但当时我把它当「已知代价」，现在我认为它更接近「这个功能的主要失效模式」。

不主张推翻拍板（做 bash 路径解析确实会给出虚假安全感，那是 pi 明确警告的），
但主张：**`/permissions` 或首启时应当明确提示「配了 Bash allow 规则 = 该命令可越界」**。
已登记 TODO。

**质疑二：`dontAsk` 与 `asker is None` 合流，让用户的模式配置被静默忽略。**

Task 6 把两者合成一行 `if asker is None or mode == DONT_ASK`，当时觉得很漂亮
（D#48 的特例终于有了名字）。但它有个副作用我到写复盘才想清楚：
**once 模式下用户显式配 `defaultMode: "default"` 是无效的**——没有真人，
ask 照样降级成 deny，与配了 `dontAsk` 毫无区别。用户的配置被吃掉了，且没有任何提示。

行为本身是对的（没人可问就是没人可问），但**静默**是不对的。
应该在 once 模式下检测到「配置的模式需要真人、而当前没有真人」时告警一次。
已登记 TODO。

**质疑三：危险路径清单硬编码且完全不可见。**
用户看不到清单内容（`/permissions` 不列）、不能增删。CC 的清单也基本硬编码，
但至少它的拒绝理由里会指明是安全检查。pai 现在的理由字符串说了「持久化位点」，
但用户无从知道**还有哪些**路径在清单里，直到撞上为止。

**质疑四（对自己方法论的）：我这次仍然是「先写 plan 的测试清单，再逐条实现」，
而七个 task 里有四个的实际测试数与 plan 不符**（+5/+4、+10/+7、+9/+8、+14/+12）。
每次都是实现时发现 plan 漏了东西。这说明 plan 阶段的测试清单**不该被当成契约**，
它更像一份「已知要测的下限」。但我在 plan 里把它写成了精确的验收数字
（「+7 → 340 passed」），于是每次多写都要回头改 STATUS、都被机器对账逮一次。

## 下次怎么做更好

**plan 里的测试数字写成区间或下限，不写精确值。**

具体做法：验收行从「`+7 → 340 passed`」改成「**至少 +7**（实际以 devlog 为准）」，
STATUS 的数字**只在每个 task 结束时按实际值更新一次**，不预写。

这次七个 task 里，光是「按 plan 的预估数改 STATUS → 被 `test_status_reports_
the_current_test_count` 打红 → 再改成实际数」这个循环就走了四次。
每次都不是 bug，纯粹是把「计划的估算」当成了「应该达到的事实」。
精确数字看着严谨，实际制造了一个必然失败的对账。
