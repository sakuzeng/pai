## 候选方案与确认

四处形状由用户 2026-08-26 用 AskUserQuestion 一次拍板，四问全选推荐项。

### 问 1：「改一个函数要贴很长的上下文保唯一」取什么形状？

- 候选 A·`edit_file` 加 `near_line` 消歧锚（用户选中）。`old`/`new` 语义一字不变；
  只在 `old` 出现多次时用行号挑最近的那一处（平局取靠前的，并在回复里说清挑中了
  第几行）。漂移风险最小：行号只用来「挑哪一个」，不用来「定位内容」——
  行号漂了会挑错或挑不到，但 `old` 仍必须逐字匹配，所以改的一定是一段真长这样的文本。
  与 41 的 `offset` 同一套行坐标。代价：仍要写 `old`，只是可以写得很短。
- 候选 B·新立 `replace_lines(path, start_line, end_line, expect, new)`。真正的行号替换。
  代价：`expect` 其实把 `old` 又要回来了，只是换了个名字——耗的 token 一样多，
  而你多了一个工具要维护。不带 `expect` 的话，模型连着做两次编辑时第二次的行号
  已经漂了，而替换会「成功」，只是替错了地方（静默替错是最坏的一类错）。
- 候选 C·`edit_file` 加 `replace_all`。解决的是另一个真需求（批量重命名），
  但不解决「贴长上下文」——改一个函数体时你要的恰恰是只改那一处。
- 候选 D·不动 `edit_file`，只做 diff 呈现，让改错至少看得见。
  代价：成本还在（每次编辑多耗几百 token 贴上下文），只是出错时不再是静默的。

用户选 A。

### 问 2：diff 给谁看？

- 候选 A·一份 unified diff，模型与终端共用（用户选中）。工具返回值就是 diff。
  模型拿原文、终端拿 sanitize 过的那份——`_display_result` 已经这么分好了，
  且 TUI 里多行结果本来就会变成可展开条目，零额外 UI 工作。
  代价：REPL / once 那条路的 diff 是残的（压成一行 200 字符），如实登记。
- 候选 B·只给模型。零 UI 风险。代价：人还是看不见改了什么，而需求的一半正是这个。
  而且这条与 A 的差别其实只在于「要不要承认 TUI 里它也看得见」——
  只要返回值带了 diff，`_display_result` 就会把它上屏，做不到「只给模型」。
- 候选 C·只给终端（`ToolEnd` 加 diff 字段）。好处是不占模型 token。
  代价：模型自查不了，而「行号漂了能当场看出来」这个好处主要是给模型的；
  且事件是跨模块契约，动它比动返回值重。
- 候选 D·两份分开做，并顺带给 `render_text` 加多行分支，三条路都完整。
  代价：动「返回一行」的契约，`echo.py` 今天依赖着它；本轮会从三件事变成四件。

用户选 A。

### 问 3：diff 多大算大？

- 候选 A·超过行数上限就只报统计（用户选中）。超过 80 行不贴 diff，只报
  `+X / -Y 行` 并说清为什么不贴、去哪看（`git_read("diff")`）。
  新建文件不产 diff（对空文件做 diff 就是把正文再贴一遍），只报行数。
  理由：一段 200 行的 diff 对模型与对人都已经不可读，而它确实花掉 token。
- 候选 B·超了保头保尾（复用 feature 42 的 `head_and_tail`）。
  代价：diff 不是日志，中间挖掉的 diff 既不能应用也不好阅读，
  两头那几行不比一行统计多告诉你什么。
- 候选 C·不设上限。最简单。代价：一次 `write_file` 覆盖 1000 行就能吃掉几千 token，
  而那种时候 diff 恰恰最没用（全是新增，且内容是模型自己刚写的）。

用户选 A。

### 问 4：顺带把三份「默认根解析 + matcher 包装」抽掉吗？

- 候选 A·抽（用户选中）。三份已经在那里，且本轮不会再添第四份。
  现在抽是纯结构改动、行为不变、由既有测试守，验收按「解析后的值逐字相等」。
  代价：本轮多一个 Task。
- 候选 B·不抽。保持范围干净。代价：那条 TODO 继续挂着，而我在 42 复盘里
  已经承认「等触发条件到了再抽」在这里更像一句免责声明。

用户选 A。

## 结果与总结

三件都做了，全量 `1628 passed`（此前 1575）。过程见 [devlog.md](devlog.md)。
本轮没有够格升格进 decisions 的取舍——三处形状都是在既有决策
（D#52 / D#73 / D#78 那一串）之内的选择，没有与参照源的新分歧。

- `core/tools/roots.py`：`root_getter` / `root_matcher` / `path_semantics`。
  三个工具各减一半接线；顺带把「没有路径参数的工具要无视 args」从
  「碰巧不读」变成显式的 `param=None`。
- `edit_file(..., near_line=0)`：只在 `old` 出现多次时用行号挑哪一处，
  平局取靠前并说出来。`old` 唯一时的那条路一个字没变。
  出现多次时的错误文案现在报出每一处在第几行，并点名 `near_line`。
- `edit_file` / `write_file` 的返回值带一段 unified diff；超过 80 行只报
  `+X / -Y` 并把出路指向 `git_read("diff")`；新建只报行数；没变说「无变化」。

验收标准五条的对账：

1. 逐字相等 —— `tests/test_tool_roots.py` 把抽取前的三份实现抄进测试当对照组，
   10 组输入 × 三个工具逐个比对。
2. `near_line` 不改老路 —— `test_without_near_line_the_old_behaviour_is_unchanged`，
   且注入「改回全局 replace」当场变红。
3. diff 太大不贴、说清为什么、指去哪看 —— 三条断言各钉一条。
4. 注入反证 —— 三个 Task 共 16 条，最终全部变红；其中 3 条头一轮没红，
   两条是我的测试挑错了可观察点/方向，一条是我的注释写了个假机制（见 devlog）。
5. 全量绿 + STATUS 同步 —— 都做了。另在 `pai_playground/` 真跑冒烟，
   抓到一处离线全绿也发现不了的空文件头噪音。
