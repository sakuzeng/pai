# 43-edit-and-diff · 复盘

## 学到了什么

这一轮三条注入反证没红，三条的真因各不相同，而它们合起来说明了一件事：
**「反证不红」是个信号灯，不是诊断结果**。规矩只说了「先怀疑实现」，
但实际查下来，三次里实现都是对的，坏的分别是：

- 我的测试挑错了可观察点（`param=None` 那条其实无法被任何输入区分）；
- 我的测试挑错了方向（`---` 会被误删的是被删掉的那一行，不是新增的那一行）；
- 我的注释写了个假机制（`n=0` 声称防止把改动量算成 diff 长度，而上下文行
  以空格打头，本来就落不进计数）。

第三种是这轮的新收获，也是最该记住的一种：**注释可以撒谎，而离线测试证不了伪**。
一段代码里「为什么这么写」的那句话，没有任何机制去校验它。`n=0` 那行代码是对的、
测试是绿的、注释是假的——三者可以长期共存，直到某天有人照着那句假话去改别处。
注入反证在这里意外地起了作用：它逼我问「删掉这个会怎样」，而答案「什么都不会」
恰好戳穿了注释的说法。

第二条，关于 diff 的落点。原本我以为「给模型看」和「给终端看」是两件事，
要分别做。查下来发现 `_display_result` 早就把这一层分好了（模型拿原文、
终端拿 sanitize 过的），`_tool_entry` 也早就会把多行结果折叠成可展开条目。
也就是说这个功能的一大半在两轮之前就已经存在，只是没人往那个口子里放东西。
先去看「现有结构已经准备好接什么」，比先设计「我要加什么」省一半工作。

## 哪里走了弯路，为什么

真跑冒烟抓到的那个空文件头，暴露的是一条更一般的毛病：**我写断言时只断言我
关心的部分，于是我不关心的部分可以任意烂而不被发现**。14 条 diff 测试里，
没有一条在看输出的开头两行——它们都在找 `-b` / `+B` / `@@` 在不在。
于是两行 `--- ` / `+++ ` 纯噪音在每一次编辑结果里都出现，全绿。
更糟的是我的代码注释还写着「不给文件名时不产文件头」，也就是说我不但没测，
还写下了一句错误的断言来解释我为什么不测。

这次是靠真跑看见的。但真跑不是每轮都做，也不该指望它兜住这类事。
可执行的改法是：给「格式化输出」类的函数，至少有一条测试断言**整个输出**
（而不是片段），哪怕是拿一个短小的期望值逐字比。片段断言查的是「有没有」，
逐字断言查的才是「是不是只有」。

## 我现在质疑什么

一、`near_line` 只解决了「挑哪一处」，没解决用户最初那句话里更重的那一半——
「改一个函数得贴够长的上下文」。一个 20 行的函数体照样要原样贴 20 行进 `old`。
我在拍板时把候选 B（`replace_lines` + `expect`）的代价写成「expect 其实把 old
又要回来了」，那句话是对的，但我当时没说的是：候选 A 也没把 old 变短，
它只是让**短的 old 变得可用**。这两件事的收益完全不同，而我把它们混在一句
「解决了贴长上下文」里递给了用户。真正能让 old 变短的做法（比如按行号取一段
再让模型只给新内容）本轮一条都没做。

二、diff 现在无条件跟在每次编辑后面。80 行以内全贴，而模型多数时候刚刚才写下
那段内容——它在读自己五秒钟前写的东西。这笔 token 花得值不值我没有任何数据，
只有一个直觉（「看得见比省得下重要」）。`MAX_DIFF_LINES = 80` 同样是拍脑袋，
且我又一次把它如实写成「未实测」然后登记 TODO——这已经是连续第三轮做同一个
动作了（`MAX_FILES_SCANNED`、`MAX_TIMEOUT_SECONDS`、`MAX_DIFF_LINES`）。
诚实地记录一个拍脑袋的数，三次之后就不再是诚实，是一种习惯性的免责。

三、`roots.py` 抽完之后我加了一句「`param=None` 让 getter 无视 args」，
而真相是 `args.get(None)` 本来就取不到东西。我把注释改成实话了，
但我没有回答一个更根本的问题：既然它不是机制，那这个参数存在的意义是什么？
现在的答案是「让代码说出意图」，可这与我上一条批评的「假机制」只隔一层——
一个说不出口的守卫和一句说错了的注释，对下一个人的伤害其实差不多。

## 下次怎么做更好

给任何「组织一段文本给别人看」的函数，写一条**逐字比对整个输出**的测试。
这一轮的空文件头、上一轮 42 的嵌套括号，都是同一类：输出里有噪音，
而所有断言都在看别处。逐字比对一个短输入的完整输出，成本是一行 `==`，
买到的是「我没在看的地方也不许变」。片段断言留给长输出，
但至少要有一条是整体的。
