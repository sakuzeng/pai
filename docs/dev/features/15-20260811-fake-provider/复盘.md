# 15-fake-provider 复盘

写于 `./test.sh` 全绿之后（769 passed, 3 deselected），交付宣告之前。

## 我学到了什么

1. 「不可测」往往不是能力问题，是三条可解的约束。
「需要模型开口的功能测不了」——真正的障碍是花钱、慢、不可复现这三条，
而不是技术上做不到。假 provider 把三条一次解掉，而前提（`PAI_BASE_URL`）
早就在代码里躺着。被当成天堑的东西，值得先拆成具体约束看看。

2. 假基建的形状必须照实测来，不能照文档来。
SSE 的 usage 位置照 D#58 的实测（末块、`choices` 非空），
而不是照 OpenAI 文档的「独立的 choices 为空的块」。
照文档写的话，pai 的解析器会被喂一个它在真实环境里遇不到的形状，
然后在测试里绿得好好的。假的东西要假得像真的那个，不是像文档里的那个。

3. 「等到出现为止」既快又稳，死等两头不讨好。
第一版每步死等 4 秒，44.7s；改成轮询屏幕直到目标文本出现，17.3s。
死等短了偶发失败、长了拖垮整套——它同时是最慢和最脆的写法。

## 哪里走了弯路

1. 三条注入反证，第一轮只红了一条。
另两条是假绿，而我差点就当成「三条都守住了」交付。逐条查清之后发现
三种完全不同的病因（见下），处理方式也完全不同。

2. 我又一次先写了断言、后想症状。
排版那条我先写了「行宽不越界」——听起来很对，但虚拟屏与真终端一样会自动折行，
永远不越界。第二版写「dock 三行的结构」，也不红。
直到回去查真因（raw mode 下 `ONLCR` 关着、裸 `\n` 只下移不回列首），
才写出「每一行必须顶格」这个症状的直接反面。
顺序应该是：先说清症状长什么样，再写断言。

## 我现在质疑什么

质疑一：这套 e2e 只覆盖了「我知道会坏」的三条。
它们是照着用户已经打回的 bug 补的——对已知问题的回归测试，不是发现新问题的能力。
真正会救我的是「用户头五分钟会做的十件事」跑一遍，而不是「已经坏过的三件事」。
下一步该按用户动作而不是按已知 bug 来写场景。

质疑二：「原 bug 的入口已经不存在了」这件事，我处理得太轻。
排版那条最后是钉在 `/help` 上的，因为原来的入口（工具结果多行）已经被
「折叠成一行」堵死了。这意味着那条 bug 现在有两道防线，而我的测试只守住了第二道。
如果将来有人取消折叠，第一道防线没了、测试仍然绿。
更诚实的做法是在 `commit` 这一层做契约测试（任何多行输入都必须逐行发 `\r\n`），
而不是绕到某条恰好还在的调用路径上去。

质疑三：34s 的主套件，我会开始不敢跑它。
从 12s 涨到 34s 是三倍。规矩说 `./test.sh` 是默认路径，但人（和 AI）在改代码时
会本能地少跑慢的东西。没有分层就是在赌纪律，而赌纪律的规矩迟早会输。

## 下次怎么做更好

1. 注入反证不红时，先分清三种情形——它们的处理完全不同：
   - 注入不对（只还原了一半的 bug）→ 修注入；
   - 断言不对（断在了一个不会变的东西上）→ 回去查症状，钉症状的直接反面；
   - 路径已不存在（另一道防线堵住了）→ 说明测试钉错了层，
     应该往上钉到契约那一层。
2. 先说清症状长什么样，再写断言。 反过来会写出听起来很对、其实什么都没测的断言。
3. 测试场景按「用户会做什么」写，不按「已经坏过什么」写。
