# skills 交付前反向对照（2026-08-22 深夜，真实 API 回合）

roadmap 固定项「交付前：跑一个完整的真实回合，哪怕花钱」。场景：
`pai_playground/skills-smoke/`（gitignored）放一个项目级 skill
`release-note`（description：生成发布说明的固定流程；正文要求标题固定
「Release Note」、第一行含暗号 `RN-SKILL-8842`、要点最多三条各一句话），
然后用真 DeepSeek 跑 `pai "帮我给这次改动写一个发布说明（release note）…"`，
不点名 skill，看模型是否自主匹配加载。

## 结果（第三跑，成功）

会话落盘核验（`sessions/20260822-235950-a6b44afc.jsonl`）三项全真：

- 目录在 system prompt：`<available_skills>` 含 release-note 与 description；
- 模型自主调了工具：`skill({"name": "release-note"})`——没有任何点名提示；
- 正文回填含暗号，且最终回答遵守了全部三条规范（标题「Release Note」、
  首行 `RN-SKILL-8842`、单条要点一句话），模型还自述「按 release-note skill
  的规范生成」。

拍板问 1 的核心疑虑（DeepSeek 对「按需加载」的服从性）在这一回合里没有出现：
工具形态 + 目录指导语足以让它先加载再动手。样本量 = 1，不外推；
但「验收标准 2/3 在真实链路上成立」这一点是实测事实。

## 两次失败的探针（发现本身，如实记）

第一跑：skill 放在 `pai_playground/skills-smoke/.pai/skills/` 但该目录不是
git 仓库——`project_skills_dir` 向上找 git 根，解析到 pai 仓库根，
skill 从未被扫到，模型自然没调。教训有二：

- 探针侧：在仓库内嵌目录做冒烟必须先 `git init`，否则测的是另一个项目；
- 产品侧：「skill 放在子目录不生效」是真实用户会撞的静默失效——扫描时
  两级根都空且 cwd ≠ git 根时，值得提示一句「项目根解析到了 X」。
  已并进 TODO 25 遗留 2（变更不生效/可见性）的范畴一起考虑。

第二跑：`cd xxx && git init -q; pai …` 里 cd 失败（shell 已在目标目录）导致
git init 被 `&&` 短路跳过，pai 照跑——复现第一跑同样的静默失效。
与第一跑同因，怪脚本不怪产品。

## 顺带观察

- 权限层表现正确：once（dontAsk）下 write_file 落盘被拒且理由完整，
  skill 工具与 read_file 读项目内文件全程无阻（边界语义符合 spec 第 3 节）。
- 成本：三跑合计约十几次模型往返，DeepSeek 计价下可忽略。
