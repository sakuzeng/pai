# feature 25 · skills — 复盘（四问）

## 学到什么

- 「最小形态」不是一个形态。R4#A4 把 pi 的做法写成了定向（「零新增工具」），
  动工前反向对照才发现三家在「加载动作」上三分（read / 展开 / 工具），
  评审语言里的「照 X」要先验证 X 是不是共识再照。这次验证只花了半天，
  换来的是拍板问 1 变成一个真问题而不是走过场。
- 重挂搭既有机制的车比新造机制便宜一个量级。「压缩后已加载 skill 仍有效」
  听起来要动 loop 的压缩块，实际上 D#42 的指令重注入路径（压缩后重调
  instructions loader）正好是个现成的挂点——组合 loader 十行，loop 零改动。
  「新需求先找既有缝」值得当成习惯，扩展点地图（E1）就是为这一步准备的。
- 权限层是功能的一部分，不是功能之后的关卡。skill 工具若不声明路径语义、
  用户级根若不进边界，once 模式下整个功能结构性死掉——这在写 spec 时就
  推演出来了（而不是交付后被打回），feature 09 的边界模型总算在第一次
  被「新功能」消费时顶住了。

## 哪里走了弯路

- 模块「一次成形」偷走了两段红。skills.py 初版把 T2 的 render_catalog 与
  T5 的 render_loaded_skills 一并写了，导致 7+3 条测试绿于到达——它们仍有
  钉死价值，但没有经历「先红」的鉴别（devlog 已逐条如实标注）。下次写模块
  骨架时只放 T1 需要的函数，别顺手。
- 交付前反向对照连废两跑：一次是 skill 目录不是 git 仓库（扫描解析到
  pai 仓库根），一次是 `cd && git init` 被短路。两次都是探针脚本的错，
  但第一次暴露的「子目录 skill 静默不生效」是真实用户路径，收进了 evidence。
- 全量回归时把系统 python3 的假红（子进程无 pytest）当过一瞬间的嫌疑对象，
  venv 复跑才定性——`./test.sh` 的「pytest 头一行打印实际版本」那条规矩
  就是为这种时刻写的，先看版本行能省一轮排查。

## 我现在质疑什么

- 质疑「未知与被隐藏说同一句话」的绝对性（T3，抄 dsh）：不泄露被隐藏 skill
  的存在是对的，但用户显式配了 `disable-model-invocation` 的 skill 被模型
  猜名撞到时，回错误里连「有这么个东西但你不能用」都不说，调试「为什么
  模型不用我的 skill」时会多绕一圈。dsh 的前提是它有独立的用户目录视图，
  pai 的 /skill 列表虽能看到，但两边说法不一致这点值得再想。
- 质疑重挂的「整条丢弃」策略（抄 CC）：总预算装不下时静默丢掉较早的 skill，
  与 pai 一贯的「静默失败是 bug」相冲——CC 丢弃时也不提示。至少该在重挂段
  末尾加一行「另有 N 个已加载 skill 因预算未重挂」。已并进 TODO 遗留 3
  （预算校准）一起处理。
- 质疑「装配期扫一次」在 REPL 长会话里的代价：CC/dsh 都做了实时变更检测，
  pai 一个会话可能开几小时，中途写好的 skill 要重启才生效且无任何提示
  （遗留 2）。当时按 pi 最小形态拍的，但 pi 是短会话工具，前提未必迁移。
- 质疑拍板问 1 的样本量：交付前反向对照只有一个真实回合，「DeepSeek 会
  自主加载」是 n=1 的观察。read 形态（候选 A）从未被真跑对比过——如果
  将来发现工具形态的 schema 成本（每请求都带）不划算，复议时缺对照数据。

## 下次怎么做更好

- 评审给的「照 X 做」先花半天验证 X 的普适性再立方案——本次验出「零新增
  工具只是 pi 一家」直接改写了拍板问题的形状，性价比极高。
- 反向对照的探针脚本先自证（`ls .git` 一行），再跑贵的那步——两次废跑
  都是探针自身状态没核实。
- 写新模块时按 task 边界克制地放函数，把「红」留给对应的 task。
