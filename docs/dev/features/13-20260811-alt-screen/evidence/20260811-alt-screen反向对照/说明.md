# alt-screen 反向对照（动工前）—— 2026-08-11

roadmap「前置精读清单的固定末项」要求的**动工前**那一次。对象是 alt-screen 的三块地基：
DECSET 1049（进出备用屏）、SGR 1006 鼠标上报、以及 alt 屏里的 resize。

**怎么跑的**：`探针/probe_alt.py` 与 `探针/probe_resize.py` 在**新开的**终端窗口里跑
（绝不碰正在跑 Claude Code 的那个会话），`探针/drive_probe.py` 用 AppleScript 开窗、
并在探针自己写出的检查点上抓可见屏内容。抓屏时机不靠 sleep 猜——探针每到一个检查点
就往日志里写一行，驱动脚本轮询日志、见到就抓。

**跑到的**：iTerm2 3.6.11（AppleScript 抓屏 + 终端自答的 DECRQM/CPR）、
Terminal.app 470.2（只能靠终端自答，见下面第 2 条）。
**跑不到的**：一切需要真实鼠标事件的（点击/滚轮/拖选）——见[手工清单](手工清单.md)。

## 1. 已在 alt 时再发 `?1049h`：**两个终端都当成「清屏 + 回原点」，不是 no-op**

这条是本次最想验的，因为 CC 的源码**自己跟自己打架**：

- `src/ink/ink.tsx:324`（handleResize 里）：
  「Do NOT write ENTER_ALT_SCREEN: iTerm2 treats ?1049h as a buffer clear even when
  already in alt — that's the blank flicker.」
- `src/ink/ink.tsx:962`（reenterAltScreen 的 docstring）：
  「ENTER_ALT_SCREEN is a terminal-side no-op if already in alt.」

实测（`原始数据/iterm2-probe.log`、`原始数据/terminalapp-probe.log`）：

| | 进 alt 打 4 行后光标 | 重发 `?1049h` 后光标 | 屏上内容 |
|---|---|---|---|
| iTerm2 3.6.11 | 行5 列1 | **行1 列1** | `ALT-CONTENT-1..3` **全没了**（`iterm2-snap2-C.txt`） |
| Terminal.app 470.2 | 行5 列1 | **行1 列1** | 抓不到屏，但光标回原点与 iTerm2 一致 |

**裁决：`ink.tsx:962` 那句是错的，而且不是 iTerm2 独有的怪癖**——xterm 对 1049 的定义
本来就是「存光标 + 切到备用屏 + **清掉它**」，两个 macOS 终端都照做。

> **pai 的直接约束**：**任何「自愈式重进 alt」的写法都会清屏。**
> resize、SIGCONT、睡眠唤醒之后想确认自己还在 alt，不能靠补发一次 `?1049h`——
> 那正是 CC 注释里点名的闪烁源。要么不发，要么发完立刻全量重绘。

## 2. `DECRQM`（问终端「这个模式现在开着吗」）**在 Terminal.app 上完全不可用**

`CSI ? Ps $p` → iTerm2 每条都规规矩矩回 `CSI ? Ps ; 值 $y`；
**Terminal.app 12 条查询全部超时无回复**，而同一个窗口里 CPR（`CSI 6n`）**正常回**。

后果有两层：

- **能力探测不可移植**：pai 不能靠「问一下终端」来决定要不要进 alt、鼠标开没开。
  CC 也不问——它的判据全是环境变量与 `TERM_PROGRAM` 启发式（见
  [K cc-alt-screen 第五节](../../../../../knowledge/tui/cc-alt-screen.md)），
  现在知道这不是偷懒，是**没得问**。
- **不被识别的查询会在屏上留下垃圾**：本次探针第一版把 `DECRQM` 排在 CPR 前面，
  测出「退出 alt 后光标在 列2」，一度以为是 Terminal.app 没把光标原样还回来；
  换成先 CPR 再 DECRQM，结果是 **列1**（`terminalapp-probe.log`）。
  **那一列是我自己的探针打上去的**——不认识的转义序列被终端当成可打印字符吐了出来。
  记下来当教训：**探测手段本身会污染被测对象**，尤其在不支持该查询的终端上。

顺带得到的能力表（iTerm2 3.6.11）：`?7` `?1000` `?1002` `?1003` `?1004` `?1005`
`?1006` `?1015` `?1049` `?2004` **`?2026`（同步输出，pai 的 DockRenderer 已在用）**
全部「认识」；只有 `?1016`（SGR 像素级鼠标）回 `4=永久未设置`，即明确不支持。

## 3. 1000/1002/1003 是**互斥单选**，不是三个可叠加的开关

pi 与 CC 都按 `\x1b[?1000h\x1b[?1002h\x1b[?1003h\x1b[?1006h` 的顺序一口气发四条
（pi `tui-alt-screen.ts:39`、CC `termio/dec.ts` 的 `ENABLE_MOUSE_TRACKING`）。
发完再查（iTerm2）：

```
?1000  2=未设置    ?1002  2=未设置    ?1003  1=已设置    ?1006  1=已设置
```

**只有最后一条生效**：1000/1002/1003 是同一个「上报多少东西」的旋钮的三个档位
（只报按键 / 按住拖动时也报 / 任何移动都报），后设的覆盖先设的；
1006 是正交的**编码格式**开关，所以能与 1003 并存。

> **pai 的直接约束**：照抄那串四条序列会得到 **1003（任何鼠标移动都上报）**——
> 最费的一档：鼠标划过窗口就有字节流进 stdin，而 pai 的输入线程要逐条解析丢弃。
> 要点击与滚轮，**1002 就够**；抄之前得知道自己抄的是哪一档。

## 4. 退出 alt 之后，shell 屏幕**原样还回来**（两个终端都是）

`iterm2-snap5-E-后.txt`：`MAIN-BEFORE-1..5` + `MAIN-BEFORE-末行` 一行不差地在，
alt 里写的东西一个字都没漏到主屏，`MAIN-AFTER` 接在原来的下一行继续打。
光标也回到进 alt 前的**同一行同一列**（iTerm2 行11 列1 → 行11 列1；
Terminal.app 行12 列1 → 行12 列1）。

> 这条是「像新开了一个窗口」这个需求的**技术前提成立**的证据：
> 进出的观感确实是「换一个屏、再原样还回去」，不需要 pai 自己保存/重放主屏内容。
> 代价在别处（见下一条与手工清单），不在这里。

## 5. alt 屏里 resize：**终端不替你重排，不重画就是坏的**

`探针/probe_resize.py`：进 alt 画 4 行（其中一行 96 列宽），然后用 AppleScript 把窗口
从 127x27 改成 72x15，应用**故意一个字节都不重画**。

- `SIGWINCH` **来了**，本次只来 **1 次**（`iterm2-resize.log`）。
  注意这与 CC 注释说的「一次用户操作常发 2+ 次」不矛盾——我这是一次性设 bounds，
  不是人手拖边框；**人手拖的次数没测到**，进[手工清单](手工清单.md)。
- 屏幕**坏了**：`iterm2-resize-snapB-after-narrow.txt` 里，最上面两行变成了
  **主屏的 `Last login` 与命令行**，与幸存的 `ALT-RESIZE-2/3` 混在一起。
  超宽那行既没被截断也没被重新折行，原样留着。
  （成因没查明——可能是 iTerm2 缩窄时对两个缓冲区的重排策略，也可能是 AppleScript
  `contents` 读到的复合视图。**只记现象，不编解释**。）
- 应用随后写的 `AFTER-RESIZE` 一行落在了那堆残骸下面（`snapC`），
  退出 alt 后主屏完好（`snapD`）。

> **pai 的直接约束**：main-screen 下 pai 现在的 resize 处理是「只重画 dock、不动
> scrollback」（feature 12 T8）。alt 下这个策略**不成立**——resize 之后整屏都可能是
> 脏的，必须**全量重绘**。这与 CC 的做法一致（`handleResize` 重置前后帧、下一帧每个
> 格子都写、并且**刻意不清屏**：清了之后 render 那 ~80ms 里屏幕是全黑的）。

## 6. 一条方法论：这次的「反向对照」本身是被工具限制塑造的

- iTerm2 能用 AppleScript 抓屏（`contents` 属性），**Terminal.app 的 AppleScript
  自动化权限没授**（AppleEvent 超时），于是改用 `open -a Terminal xxx.command` 启动 +
  让**探针自己问终端**（CPR）来反推屏幕状态。绕过去了，但拿到的是**间接证据**——
  「光标回到行1」推出「清屏了」，这一步是推理不是观测，如实标注。
- 合成鼠标事件两条路都堵死：System Events `click at` 缺辅助功能授权、
  本机无 `cliclick`、无 pyobjc。**鼠标这一整块没有任何观测**，全进手工清单。
  按 roadmap 那句规矩：**跑不到的部分要留手工清单，不许拿「按源码推」冒充观测。**

## 7. 「resize 之后顶部残留两行主屏内容」——**是读取工具的假象，不是 pai 画的**

先看到的是：resize 之后用 AppleScript `contents` 读回来的屏幕，顶部有
`Last login:` 与启动 pai 的那条命令行，pai 的帧从第 3 行才开始。
这与动工前第 5 条（`iterm2-resize-snapB` 里混进主屏文本）是同一个现象，
当时如实记了「成因没查明，也可能是 AppleScript `contents` 读到的复合视图」。

这次**用 `screencapture` 截了真窗口**（`原始数据/交付前-iterm2-resize后截图.png`）：
**屏幕上是干净的**——logo 就在第一行，没有任何主屏残留。

> **裁决：`contents` 读出来的是一个复合/滞后视图，人眼看到的不是那样。**
> 动工前第 5 条里那句存疑到此关闭，方向是「读取工具的问题」。
> 更一般的教训与第 2 条同源：**测量手段本身会骗人**——
> 这次是 AppleScript 读屏，上次是不被识别的 DECRQM 吐出可见字符。
> 终端相关的观测，凡是「工具告诉我的」都要能被「人眼看到的」复核一次。

⚠️ **但由此写的两处代码保留**，因为它们各自独立成立（不依赖那个假象）：
① 渲染器的**重入保护**——`SIGWINCH` 处理器确实会在一帧写到一半时调进来，
两帧字节交错就是花屏，且后一帧会把「上一帧屏幕上有什么」覆盖成已画好，错位从此修不回来；
② resize 之后**强制全量重画**（`invalidate()`）——CC 的 `handleResize` 也是
重置前后帧缓冲再逐格重写。两条都有离线测试钉住。
