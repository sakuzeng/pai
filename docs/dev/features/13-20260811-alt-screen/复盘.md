# 13-alt-screen · 复盘

## 学到了什么

**① 「记录写给 X 的全部字节」这句话，只要 X 有第二个写入者，就是假的。**
录制器（feature 14）包的是渲染器的 `write`，而终端生命周期（raw mode、进出备用屏）
走的是另一条路直接写 `sys.stdout`。于是录制文件里**没有 `?1049h`**——
回放时不知道这是一段备用屏录制，按「数换行估高度」建了一块比真实终端矮的屏，
帧末尾几行被钳在最后一行叠成一团。**症状看起来像渲染器画错了，其实是录制漏了。**
判据可迁移：给「全量记录器」验收时，要问的不是「它记的对不对」，
而是**「被记录的那个出口，是不是唯一的出口」**。

**② 观测工具会骗人，而且骗法与被测对象同源。** 这次两次：
动工前——不被识别的 `DECRQM` 查询在 Terminal.app 上**漏成可见字符**，
把光标推走一列，差点让我得出「Terminal.app 退出 alt 后光标没还原」的错误结论；
交付前——AppleScript 的 `contents` 读回来的屏幕顶部有两行主屏残留，
而 `screencapture` 截真窗口证明**屏幕上是干净的**。
教训：**终端相关的观测，凡是「工具告诉我的」，都要能被「人眼看到的」复核一次。**
（已写进 [K concepts/alt-screen-and-mouse.md](../../../../knowledge/concepts/alt-screen-and-mouse.md) 第五节。）

**③ DECSET 1049 不是幂等的**，且这条被真实源码写反过（CC 同一文件里两处注释互相矛盾）。
「切到备用屏」的定义里就含「清空它」，所以任何**自愈式重进**都会闪白屏。
这条已经沉淀成通用笔记，不再是 pai 的私有知识。

## 哪里走了弯路，为什么

**把「原则 2」当成一条完整的论断，差点在错误的前提下讨论方案。**
roadmap 里那句「只做 main-screen 模式，不给 main-screen 假装 sticky 语义」，
读起来像一句话，其实是两件事焊在一起的：后半句是 pi 的论断（终端拥有滚动，
所以应用无法可靠提供 sticky/嵌套滚动/命中测试），前半句是 **pai 自己加的范围选择**。
当时写 roadmap 的人（我）把「我们这轮不做」和「不该做」写成了同一句话，
于是半年后（其实是一天后）复议时，第一反应是「要推翻一条经过论证的原则」——
门槛被自己抬高了。

换个人会不会踩：会。**把「本轮范围」与「设计论断」写在同一条里，是通用的坑。**
两者的复议成本差一个量级：范围到期就换，论断要有新证据才推翻。

**第二处**：组帧的两遍渲染，第一版拿第一遍的 dock 长度去截第二遍的结果
（`[-len(dock):]`），在「dock 两遍高度不一样」时把权限框的问题行切掉了。
当时的想法是「第二遍只是为了拿新的滚动态，长度不会变」——
而滚动指示恰恰**会让状态行多出一行**。**自己给自己的假设开了绿灯，没有测试挡着。**

## 我现在质疑什么

**质疑一：「不回吐完整文档」这条拍板，在 `--resume` 落地之前是有真实代价的，
而这个代价我当时没量化。**
拍板依据是「CC 就是这么做的」——但 CC 有 `--resume`，pai 没有。
现在的实际状态是：退出那一刻，整段对话只剩一个 JSONL 文件，而 JSONL 不是给人读的。
今天为止 pai 的用户（就是你）**每次退出都会失去一次「回头翻刚才那段」的能力**。
建议：`--resume` 不要排在「搜索」「点击」后面，它是本轮**引入**的缺口，
优先级应当高于本轮**未做**的那两项。已在 TODO 里写明这个次序理由。

**质疑二：默认开 alt-screen，而崩溃留下的残局比 main-screen 严重得多。**
`try/finally` 兜住了异常与正常退出，但 `kill -9`、以及 `bash` 工具跑起一个
写 rmcup 的程序（vim/less）之后的状态，都没有兜。
main-screen 下最坏是留个乱掉的 dock，用户 `clear` 一下就好；
alt 屏下用户会看到**一个空屏 + 打字没回显**，第一反应是「终端坏了」。
拍板问 4 我给的推荐理由是「pai 是自用项目，没有外部用户风险」——
这句话只覆盖了「影响多少人」，**没覆盖「一次失败有多难恢复」**。
不建议改默认值，但建议补一条「启动时若检测到上次异常退出，打一行怎么恢复」。

**质疑三：滚动只有键盘，而「已上滚」的指示藏在状态行里。**
真跑的时候我自己都要盯着才看见那三个字。用户往回滚之后，
屏幕上最显眼的位置（transcript 区域）没有任何东西说明「你不在最新位置」。
CC 用的是一个悬浮的「跳到底部 / N 条新消息」药丸（`FullscreenLayout` 的 pill）。
本轮不做是对的（范围），但**指示的位置选错了可能比没做还糟**——
它给了「已经提示过用户」的错觉。

**质疑四：`_fit()` 选了静默截断，而 pi 在同一个位置选的是 fail-loud（超宽即 dump + throw）。**
我给的理由是「等有一次真撞上再考虑要不要吵」。但超宽行在 alt 屏里的症状是
**悄悄吃掉右边的内容**——用户不会报告一个他看不见的 bug，
所以「真撞上」这个触发条件**结构上永远不会到来**。这条自相矛盾，值得复议。

## 下次怎么做更好

**给每一条「注入反证」预先写明它要走到的那条路径，并在跑之前问一句
「这条路径在本测试里被走到了吗」。**
本轮 T7 的第三条反证第一轮没红，查下来是「场景不对」——e2e 里 PgUp 之后
再没有新内容到达，注入点根本没被执行。feature 15 已经吃过一次同款亏
（三条反证只红了一条），当时的结论是「不红时先分清注入不对/断言不对/入口不存在」——
那是**事后**的分诊流程。这次的改进是把它提前：写反证时先回答
「哪一行代码会因为这个注入而执行到不同的结果」，答不上来就说明测试还没覆盖那个场景。
