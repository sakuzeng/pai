# 16 复盘

档案 2026-08-11 立项、九个 task 当天实现完，但**停在「实现中」整整八天**——
卡在一条用户真跑撞到的坏路径上（拖选卡顿）。2026-08-19 收尾后才交付。

## 学到什么

「先量数字」不是形式。TODO 里挂了八天的诊断是「每条拖动事件都触发一次整屏重绘」，
而实际上 `app.feed()` 末尾本来就只 refresh 一次、鼠标事件还按批合并过。
真正的分布是：事件一批到达 12.5ms/1 次写，一条一批到达 206~263ms/121 次写——
**批合并只在同一批内有效，管不了「每次 read 只捞到一条」**。
如果按 TODO 的诊断直接动手，会去改一个本来就没问题的地方。

单帧 1.1~1.7ms 且不随 transcript 增大（2000 条也只 1.71ms），这条同样是量出来才知道的。
它顺带否掉了 TODO 里另一条待办的紧迫性（`_highlight` 逐字符扫描——选区代价
实测只有 0.74ms 且不随规模变）。

## 哪里走了弯路

真正的弯路在交付节奏上：九个 task 当天全绿，然后因为一条坏路径停了八天。
期间这个功能对用户是「能用但难用」——鼠标能拖、拖起来卡。
如果当时就按 `perf` 判据量一次（十几分钟的事），它八天前就能交付。
把「未交付」当成一个稳定状态放着，比未修的 bug 本身更值得警惕。

## 我现在质疑什么

一、`DRAG_FRAME_INTERVAL = 0.016` 是从 pi 抄来的常数，我给它写了「约 60fps」的
理由，但**没有在真终端上验过 16ms 对拖选手感是否合适**。基准脚本用的是假时钟，
所有事件落在同一窗口，所以「修复后 2 次写」这个数字是理论上界不是真机表现。
真机上事件到达间隔由终端与系统决定，实际帧数会更多。已登记 TODO。

二、节流判据用的是「这批之前就在拖」，于是**按下与松手那两帧一定会画**。
这是对的，但我没有测「拖到一半松手时，最后位置是否精确」——收尾帧那条测试
验的是「有帧画出来」，不是「画的内容对」。

三、这条修复没有 e2e。R4 那轮反复出现的教训是「组件测试全绿而接缝坏掉」，
而节流恰好在 `feed` 与 `needs_tick` 的接缝上。真终端里 `needs_tick` 由 driver 的
空闲 poll 推动，若某次 poll 因为有输入而不走超时分支，收尾帧就晚一拍——
离线测不出来。

四、更大的一条：**这个功能从「实现完」到「交付」隔了八天，而档案状态一直是
「实现中」，没有任何机制提醒它悬着**。TODO 里有那条卡顿的记录，但 TODO 有 171 条。
「未交付的功能」应该比「待办事项」更显眼。

## 下次怎么做更好

`perf` 类的待办，登记时就把「该量什么」写进去（本轮的 TODO 只写了「先量出数字再改」，
没说量什么，于是八天后重新想一遍）。写成「量 X 在 Y 条件下的耗时与写次数」，
下次接手的人十分钟就能开始。

功能停在「实现中」超过一次会话，就该在 STATUS 的「下一步」里单列一行——
它和普通待办不是一回事。
