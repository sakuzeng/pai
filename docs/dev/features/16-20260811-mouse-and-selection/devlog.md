## 2026-08-11 spec 定稿

目标：把四条拍板 + 两轮实测变成可实现的 spec。

实测直接决定了三处设计（不是「参考了一下」）：

1. 一次滚动手势上百条 → spec 的 G3 是一整节「事件合并」，且验收标准里
   拿实测数字 142 当测试输入：喂 142 条 wheel 只许产生 1 帧。
   查代码时发现 feature 12 的结构（`os.read(4096)` → `app.feed` 整批处理 → 末尾只 refresh 一次）
   已经吃掉了大部分洪水——所以本轮要做的不是发明合并，是把它钉死并补上 delta 累加。
2. OSC 52 静默失败 → G6 改成「本地系统剪贴板优先、OSC 52 只兜底」，
   且反馈措辞分两种：走 pbcopy 成功才说「已复制」，只发了 OSC 52 只能说「已尝试复制」。
3. 1002 与 1003 观测不到差别 → 照拍板发 1003，但注释必须写明它在本机买不到 hover，
   且 hover 高亮进非目标。

spec 里一处 pai 能比 CC 简单的地方（值得单独记）：
选区锚在 transcript 的逻辑行号上，不是屏幕行号。CC 的屏幕缓冲只有当前视口，
所以它必须把「滚出视口的行」另存（`scrolledOffAbove/Below` + 平行的软折行位图）；
而 pai 持有整份文档，滚动时选区天然跟着内容走。CC 那一整块不需要。
验收标准第 5 条把它钉死：选中一段后滚动，选区仍框住同样的内容。

风险里最值得先说的一条：实测那次拖动只有 1 条按下、0 条松开（8 秒到了还按着）——
说明真实操作里按下与松开可能相隔很久，状态机必须容忍「按下之后长时间没有松开」。
这条如果不是实测撞到，我大概率会写成「按下后很快就会松开」的隐含假设。

而真终端是「很多批各一条」。测试喂数据的方式本身就是一个未被检验的假设。

## 2026-08-11 「从后往前拖选不复制」——第三次报告给了决定性线索

用户第三张截图里高亮还在。而复制成功会清掉选区——所以释放事件根本没走到复制那一步，
不是方向逻辑的问题。离线怎么喂都复现不了，因为它压根没送到
（向上/向左拖很容易把指针带出窗口，而终端只在窗口内上报）。

修法不是猜它为什么丢，是别依赖它一定会来：

- 下一次按下时先给上一次手势收尾（该复制的复制）；
- 停手 0.4s 也收尾（`app.tick()`，由驱动空闲那一拍推；`needs_tick()` 在拖动期间为真）；
- 正常释放到了仍然当场收尾，兜底走不到——有测试钉住这条，免得兜底把正常路径拖慢。

顺带给 `driver.py` 补了它此前一条都没有的测试（feature 12 复盘质疑五挂了很久）：
读干净再处理、部分序列不被切断、空闲那一拍会调 `tick()`。

卡顿没修完，如实登记：已做的「读干净再处理」只在事件已经排队时有用。
真正的原因是每条拖动事件都触发一次整屏重绘（离线量到每帧约 1ms + 一次终端写）。
正解是渲染节流（pi 的 `MIN_RENDER_INTERVAL_MS = 16`：置标志位、合并到下一帧），
归下一轮「优化」，且按 `perf` 的判据先量数字再改。

这一轮最值得记的一条：`merge()` 的价值被真终端重新定义了两次。
T2 时我以为它挡住了洪水 → 注入反证证明洪水是 `app.feed` 的结构挡住的 → 我给它补了
「状态机只调一次」的断言；现在发现真终端里事件根本凑不成一批，
合并连生效的机会都没有。
离线测试永远是「一批很多条」，真终端是「很多批各一条」——
测试喂数据的方式本身就是一个未被检验的假设。


## 2026-08-11 兜底第一版被用户当场推翻：「我还在按就结束了」

上一版的兜底是「停手 0.4s 就当这次拖动结束了」。用户试完立刻打回：
慢慢拖的时候，人还按着，选区就被结束并清掉了。

根因是我把两件分不出来的事当成了一件：应用这边收不到任何事件时，
「用户松开了但释放丢了」与「用户还按着、只是没动」在输入流上完全一样。
拿超时去猜，必然误伤其中一种。

改法：让停手只做「不破坏性」的那一半——

| | 做什么 | 不做什么 |
|---|---|---|
| 停手 0.4s（`tick`） | 把当前选中的放进剪贴板 + 给提示 | 不结束拖动、不清高亮 |
| 收到释放 | 复制 + 清高亮 | —— |
| 下一次按下 | 先把上一次收干净，再开始新的 | —— |

于是慢拖不再被打断（接着拖，选区继续长），而释放真丢了也不至于没提示——
剪贴板里已经是当前选中的内容。内容没变就不再复制，免得停着不动时
每一拍起一个 `pbcopy` 子进程。

顺带拆开一处混在一起的职责：`_copy_text` 里原本带着「复制完清高亮」
（那是修「松开后高亮赖着不走」时加的）。清高亮属于「这次手势结束了」，
不属于「复制」——混在一起的直接后果就是自动复制把人家正拖着的高亮清了。

一条测试断言也被这次改动纠正：原来断言「下一次按下之后 `dragging` 为假」，
可按下本来就会开始新的一次。改成断言「没有残留的选区（只剩一个新锚点）」——
先想清楚要断言的性质是什么，再写断言。

## 2026-08-19 收尾 · 拖动期渲染节流（perf）

交付前欠的最后一条：真终端里拖选卡顿。按 AGENTS 的 `perf` 判据先量数字
（`pai_playground/bench/drag_render.py`，视口 100x40、一次手势 120 条移动事件）。

量出来的结论与 TODO 里的猜测不同。TODO 写的是「每条拖动事件都触发一次整屏重绘」，
而 `app.feed()` 末尾本来就只 refresh 一次、鼠标事件还按批合并过。真实分布是：

| 事件到达方式 | 总耗时 | 终端写次数 |
|---|---|---|
| 一批到达 | 12.5ms | 1 |
| 一条一批 | 206~263ms | 121 |

单帧本身只要 1.1~1.7ms，且不随 transcript 增大（2000 条也只 1.71ms）。
所以瓶颈不是「渲染太慢」也不是「批合并没生效」，是事件一条一批到达时帧数太多——
批合并只在同一批内有效，管不了「每次 read 只捞到一条」的情形。

修法照 pi 的 `TuiBase.MIN_RENDER_INTERVAL_MS = 16`：`DRAG_FRAME_INTERVAL = 0.016`，
拖动期距上一帧不足一个窗口就压住这一帧，交给 `needs_tick()` 推出来的收尾帧
（拖动期间它本来就为真，正是 TODO 里预判的那个挂点）。

判据用「这批之前就在拖」而不是「现在在拖」：按下那一帧要立刻画出来（用户得看见
选区起点），松手那一帧同样——两者都不满足 `dragging_before`。

修复后实测：

| transcript | 修复前（一条一批） | 修复后 |
|---|---|---|
| 500 | 206.3ms / 121 次写 | 14.4ms / 2 次写 |
| 2000 | 263.1ms / 121 次写 | 16.4ms / 2 次写 |

红：`1 failed, 13 passed`（只红核心那条，另三条是防过头的守卫本来就该绿）。
绿：`14 passed`。全量 `1179 passed, 1 skipped`。

两条注入反证各红各的：拆掉节流 → 红「一批事件不该画一帧一条」；
把「只对拖动生效」那道判据去掉 → 红「按键永不节流」。

## 2026-08-19 追记（交付当天，feature 20 补 e2e 时推翻上一节的结论）

补 e2e 时做了真机对照实验，上一节发布的性能数字在真终端上不成立。

真 pty、40 条拖动事件，数终端写次数（一帧 = 一条写记录，已实测）：

| 事件间隔 | 有节流 | 无节流 |
|---|---|---|
| 0ms  |  6 |  7 |
| 10ms | 71 | 67 |
| 30ms | 75 | 70 |

两列没有差别。逐层注入反证确认原因：拆掉节流 → e2e 不红；拆掉 driver 的
「读干净再处理」→ 不红（60 条事件约 720 字节，一次 `os.read(4096)` 就全拿到）；
只让每个鼠标事件都 refresh → 不红；**只有把 `_merge_mouse_runs` 一起拆掉才红**。

也就是说：真终端里帧数低是 `_merge_mouse_runs` 与「每批只 refresh 一次」
（feature 12 就有的结构）挡下来的，`DRAG_FRAME_INTERVAL` 没起作用。

上一节 206→14ms 那组数字是基准脚本的产物：它直接在紧循环里调 `app.feed()`
并注入假时钟，人为造出了「逐条到达且间隔 <16ms」这个形态；而真路径上事件
要么被一次 `os.read` 全读进来，要么实际间隔已超过 16ms 窗口。

处置：节流代码保留（无行为回退、有 4 条离线测试钉着它自身的语义），
但不再声称它解决了用户报告的拖选卡顿——那条卡顿的真实成因至今未确诊。
已登记 TODO 重开。这是「基准测出来的收益在真实路径上不存在」的一个实例，
与仓库里「测试为了让被测路径跑起来而注入的参数，正是真实路径上会卡住的地方」
是同一种病的镜像。
