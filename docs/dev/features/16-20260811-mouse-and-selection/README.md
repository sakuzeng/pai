## 需求

**让 pai 接管鼠标**：滚轮滚自己的 transcript、拖选高亮并复制。

用户 2026-08-11 真跑 [feature 13](../13-20260811-alt-screen/README.md) 后当场撞到：
往上滚**看到的是自己之前几次运行留下的旧内容**（截图为证），而不是本次会话的历史。
原话：「有问题，并不和 cc 是一致的」。随后又跑了一次 CC 对照：
「运行 claude 之后根本就往上移动不了」。

### 两张截图合起来说明的是同一件事：**谁拿到了滚轮事件**

- **pai 现在**：一个鼠标上报序列都不发 → 滚轮**穿透**给终端 → iTerm2 在备用屏里把它
  解释成「回看主屏 scrollback」→ 翻出来的是进 pai 之前的 shell 历史与更早几次运行的残留。
- **CC**：`<AlternateScreen mouseTracking={isMouseTrackingEnabled()}>` 默认开启鼠标捕获
  → 滚轮进 CC 自己的虚拟滚动 → 新会话没有可滚内容时**什么都不发生**。
  用户看到的「移动不了」正是事件**被吃掉**的证据。

差别不在「谁滚得动」，在**事件归谁**。

### 为什么另开档案而不是接在 13 后面

features/README 规矩 7 的判据：**「这次改动是在*完成*那次交付，还是在*改变*那次交付的结果？」**

13 的拍板问 3 白纸黑字是「**本轮完全不接管鼠标**」，并把「保住终端原生的拖选复制」
写成了交付物的一部分（[D#64](../../decisions.md)）。接管鼠标是**改变**那个结果 →
**新建档案，13 冻结**。

### 13 拍板时被我说窄了的那个代价（本档案的直接起因）

13 拍板问 3 的选项描述里，「不接管鼠标」的代价我只写了「不能点」，
**没写「滚轮也不归 pai」**——而滚轮比点击高频得多。用户是在真跑时才发现的。
这条已写进 13 的交付后记录，本档案存档留证。

## 候选方案与确认

<!-- ≥2 个候选 + 取舍；只有一个方案等于没讨论。动工前补齐并拍板。 -->

### 方案 A · 只接管滚轮，不做选区

发 `?1002h`+`?1006h`，只处理 wheel 事件，click/drag 一律丢弃。

- **对**：几十行；滚轮手感与 CC 一致。
- **代价**：终端原生的拖选复制失效，退化成「按住 Option 拖」
  （iTerm2 的既定约定；**Terminal.app 的等价键未实测**）。

### 方案 B · 一次做到位：滚轮 + 自写选区

照 CC 的完整做法：自己画高亮、自己算选中文本、松手即复制。

- **对**：用户感知与 CC 一致——拖选看起来「还能用」。
- **代价**：**CC 为此付了 917 行**（`src/ink/selection.ts`）：跨行选择、双击选词/三击选行、
  拖到边缘自动滚、**滚出视口的行要另存**（屏幕缓冲只有当前视口）、软折行拼回逻辑行、
  翻页钳位后要能还原锚点；外加剪贴板三条路径（`termio/osc.ts`：
  `native`(pbcopy/wl-copy/xclip) / `tmux-buffer` / `osc52`，按 `SSH_CONNECTION` 分流）。
  **这个 feature 会比 13 本身还大。**

### 方案 C · 不接管，只把「PgUp/PgDn 能滚」写进界面

- **对**：零风险，保住终端原生选中复制。
- **代价**：滚轮永远不归 pai——用户已经亲身撞到不顺手。

### 确认

**问 1**（2026-08-11）：知道「CC 不是保住了选区、而是重写了选区」之后，鼠标这块怎么定？
- 候选 A·只接管滚轮，选区单独立项：几十行；拖选退化成按 Option。
- 候选 B·一次做到位（滚轮 + 自写选区）：与 CC 一致；CC 用了 917 行 + 剪贴板三路径。
- 候选 C·什么都不接管，只补提示：保住原生选区，滚轮永远不归 pai。

**选择**：**候选 B —— 一次做到位：滚轮 + 自写选区。**
理由：用户明确要与 CC 一致的手感，且已亲身验证过「滚轮穿透」的困扰与
「CC 里滚轮被吃掉」的对照。

**问 2**（2026-08-11）：发哪一档鼠标上报？（实测已证明 1000/1002/1003 互斥单选）
- 候选 A·`1002`：按键+拖动才报，鼠标只是划过窗口时**安静**；选区只需要拖动事件，够用。
- 候选 B·`1003`：任何移动都报，与 CC 完全一致，为将来的 hover 高亮留路；
  代价是鼠标划过窗口就有字节不断流进 stdin。

**选择**：**候选 B·1003（照抄 CC）**。

**问 3**（2026-08-11）：剪贴板怎么写？
- 候选 A·只做 OSC 52：不 spawn 进程、天然支持 ssh，pi 就只用这一条。
- 候选 B·OSC 52 + `pbcopy` 兵分两路：本地走 pbcopy、远程走 OSC 52（照 CC 的分流思路）。

**选择**：**候选 B·兵分两路**。
⚠️ **拍板后实测证明这个选择是对的、而我的推荐是错的**：
OSC 52 在本机 iTerm2 上**根本写不进剪贴板**（BEL 与 ST 两种结尾都试，剪贴板纹丝不动，
且完全静默）。按我推荐的「先只做 OSC 52」交付，复制会在用户自己的机器上静默失效。
证据见 [evidence 第 1 条](evidence/20260811-鼠标与剪贴板/说明.md)。
**因此顺序还要反过来：本地 `pbcopy` 为主，OSC 52 只当 ssh/tmux 兜底。**

**问 4**（2026-08-11）：点击展开工具结果进不进本轮？
- 候选 A·进：命中测试 CC 只用了 130 行（便宜），地基 feature 13 已建好，三条需求一次关掉。
- 候选 B·不进：选区本身已是大块（CC 917 行）；且单击**既可能是展开、也可能是选区起点**。

**选择**：**候选 A·进**。理由：反正鼠标都接管了。
（冲突的解法照 CC：**没拖动才算点击**——`selection.ts` 里 `updateSelection` 的第一条
就是「与锚点同格的第一次移动不算数」，正是为了让裸点击不变成 1 格选区。）

## 结果与总结

**2026-08-11：9 个 task 全部实现，`./test.sh` → 986 passed, 3 deselected。
但不标「已交付」**——用户真跑撞到一条还没修好的路径（见下）。

**能用的**：

- 滚轮滚自己的 transcript（**不再穿透给终端翻出旧会话残留**，这是本 feature 的起点）；
- transcript 里拖选、松手复制（本地 `pbcopy` 优先、ssh 走 OSC 52，措辞分「已复制/已尝试复制」）；
- **点击工具结果展开/折叠**，展开后命令留在第一行、输出缩进挂在下面（照 CC 的形状）；
- 输入框里点击定位光标、拖选、选中后打字/退格直接替换；
- 复制提示右对齐、贴在 dock 分隔线**上方**、2.5 秒自己消失；
- `.pai/settings.json` 的 `tui.mouse` 可整个关掉，关掉即回到 feature 13 的行为。

**还坏着的**（已登记 [TODO](../../TODO.md)）：
**真终端里从后往前（向上）拖选，松手后不复制，且拖动过程卡顿。**
离线复现不了——同样的事件序列两个方向都正常。差别在**事件到达的方式**：
真终端里事件一条一条到，`mouse.merge` 的合并没机会生效（它只在同一批里合并），
而向上拖很容易把指针拖出窗口顶部、释放事件可能根本没送到。
修法方向在 TODO 里写明了，归下一轮「测试与优化」。

**交付前真跑一共打回 10 条**，全部修掉的有 9 条。它们的共同点值得单独记：
**没有一条是离线测试能发现的**——全在「真实入口」（生产路径上提交的是不可展开的条目）、
「真实终端」（事件到达方式、终端模式的副作用）与「真实操作」
（松手在别处、拖出窗口、连续两次手势）上。
