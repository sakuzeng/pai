# 12-tui 复盘

写于 `./test.sh` 全绿之后（**680 passed, 3 deselected**），交付宣告之前。

## 我学到了什么

**1. 「以 CC 为主」这句话必须先拆成「哪一层」。** CC 的渲染层是 React reconciler +
Yoga + 虚拟滚动 + 行宽缓存，pai 复刻不了；值钱的是**行为层**——输入归属仲裁、
抑制语义、模式轮转、resize 策略、非交互闸门。把这层定死、只在架构轴上给候选，
brainstorm 才是在讨论真问题。**照抄一个东西之前，先说清楚抄的是它的哪一层。**

**2. 一个仲裁函数胜过两个消费者互相谦让。** 08 那条事故（`!echo 我是命令` 被当成答案）
在纯 REPL 里只能打补丁，因为病根是「两个消费者抢同一个 `read()`」。
把归属**算出来**——`InputArbiter` 一处判定、每个消费者一个 `is_active`——补丁全都不需要了。
这个形状可迁移：任何「多个东西想读同一个流」的地方都适用。

**3. 测试基建值得先建。** 前置反向对照卡在「看得见字节、看不见屏幕」；
T1 一开始就写了 `tests/tui_screen.py`（最小终端模拟器），于是
「dock 变矮不留残影」「commit 不与 dock 叠影」这类断言才**测的是效果而不是字节**。
断言字节等于把实现钉死，改一种等价写法就假红。
模拟器**遇到不认识的序列直接 raise** 也是关键——静默忽略会让测试对着
「模拟器没看懂所以当没发生」的假象变绿。

**4. 离线测试有一整类问题结构上看不见：走超时那条路的行为。**
真跑冒烟当场撞出「空闲时每 100ms 白刷一帧」——离线测试**永远**发现不了，
因为它们从不等待。凡是「没有输入也要醒一次」的代码，都得真跑一遍。

## 哪里走了弯路

**1. T1 漏了原则 3 的一半，T7 才顶出来。** 渲染器当时没实现 CURSOR_MARKER 的
提取与硬件光标定位，标记被原样写进终端。原因是 T1 的测试全用 `Text` 组件——
**没有一个测试用例会吐标记**，于是这条要求在 T1 里根本没被表达。
教训：**验收条件里写了的东西，红阶段就得有一条测试指着它**，
否则它会一路活到某个下游 task 把它撞出来。

**2. 第一版的模式切换要害测试是假绿。** 它两次都断言 `deny`（default→ask→无真人→deny，
bypass→显式 ask 免疫→deny），换回捕获常量照样过。
写「改完立刻生效」这类测试时，**两次的结果必须不同**，否则它什么都没测。
这与 engineering/mutation-testing-pitfalls.md 那条「注错了和没测住现象一样」同源，
但这次是**断言本身选错了**，不是注入错了。

**3. 用 `python3 - <<EOF` 批量改测试文件，两次把函数内部的 import 改坏。**
字符串替换不认作用域。改代码该用能定位的工具，或者至少替换前先确认唯一性。

## 我现在质疑什么

**质疑一：`_queue_size` 读了别人的私有属性，理由站不住。**
当时写的是「不给 05 交付的 `PendingMessageQueue` 加公开面，为一个显示需求改它不划算」。
但 `len(queue._messages)` 比加一个 `__len__` **更**耦合——它把「内部用 list 存」
这件事泄漏进了 modes 层。这条我当场就不该那么写。

**质疑二：干活期间的按键只在事件到来时被读取，这可能是个真问题而不是遗留。**
`on_event` 里顺手 `poll(timeout=0)` 是个取巧。一个跑 30 秒且不发事件的 bash 命令，
期间用户打的字在 dock 上**完全看不见**（字符没丢，在内核缓冲区，但屏幕不动）。
用户会以为键盘死了。这比档案里记的「输入行不会更新」严重——
它在**最需要反馈的时候**没有反馈。真正的解法要么是独立输入线程（本轮明确不做），
要么让工具执行期也定时 poll。**建议下一轮就处理，别等它变成事故。**

**质疑三：`Ctrl+R` 的回退我在拍板时说得太轻。**
brainstorm 里我把它列成「方案 A 的已知代价」一句带过，用户是在这个描述下选的 A。
但 readline 白送的不止 `Ctrl+R`——词跳的边界细节、libedit 与 GNU readline 的差异、
各终端方向键序列的长尾，我在这轮只支持了「一组主流序列」。
**用户拍板时看到的成本，比真实成本小。** 这不是选错了，是我描述得不够。

**质疑四：非 tty 走另一条代码路径，正是我否掉方案 C 的那个理由。**
我用「两套输入路径 = 病根还在」否掉了 C，然后交付了一个 tty 走 TUI、非 tty 走老 REPL
的实现。两者确实不同（tty/非 tty 在进程启动时就定了，不会中途切换；C 的双态在
一次会话内反复切），但这个区别值得说破——**它是同一种东西的两个剂量，不是两类东西**。
代价是 `run_interactive` 现在有两条主循环，任何交互语义的改动都得改两处，
而「只改了一处」不会让任何测试变红。

**质疑五：171 条测试里，`tui/driver.py` 一条都没覆盖。**
它是唯一碰真 tty/select 的文件，我把它做薄并靠冒烟脚本顶着——
但冒烟脚本不在 `./test.sh` 里，**改坏它不会有任何东西变红**。
「做薄」缓解了风险却没消除它。至少该给 `poll()` 的分支逻辑注入一个假 fd 测一测。

## 下次怎么做更好

1. **验收条件与红阶段测试逐条对表。** T1 漏掉 CURSOR_MARKER 的直接原因是
   「spec 里写了、plan 里写了、但红阶段没有一条测试指着它」。
   拆 task 时应当把验收条件当 checklist 用，一条不落地映射到某条测试。

2. **「改完立刻生效」类测试，先问「两次的结果会不会一样」。**
   一样就说明这条测试不具鉴别力，换个能分辨的场景。

3. **把「只有真跑才发现」的类别写进 plan。**
   本轮真跑撞出的那条（空闲重绘）不在任何 task 的红条里。
   下次 plan 里该有一节「哪些行为离线测不出、准备怎么真跑」，
   与 roadmap 那条「反向对照」固定项对齐——**反向对照不该只在动工前做一次，
   交付前也该做一次**。

4. **拍板描述里，把「已知回退」的完整清单摆出来，不要只举最显眼的一条。**
   用户按我给的成本描述做决定，描述得轻就是替他低估了。

# 追记 · 交付后修复波（2026-08-11 当日）

上面那份写于 `680 passed` 之后、宣告交付之前。**用户真跑当场打回三条**，
另提四轮视觉要求，最终到 747 passed。原文一字不改，这里追记——
因为「交付时我以为做完了」与「用户一跑就崩」之间的落差，本身就是最该留下的东西。

## 我学到了什么（追加）

**5. 「测试全绿」与「能用」之间隔着一整类 bug：接缝。**
171 条离线测试全绿，用户第一次真跑就打回三条，**三条全在组件之间的接缝上**：
回答不上屏（两边都以为对方会打）、权限框卡死（装配期捕获的 asker）、
排版阶梯（一方产出多行、另一方假设单行）。
每个组件单独看都对，各自的测试也都对。坏的是「A 认为 B 会做」与
「B 认为 A 会做」之间那条**没人负责的缝**。
判据：**如果两个组件对同一件事的假设写在各自的注释里，那就是一条缝**——
假设没有被任何一段代码强制过。

**6. 同一个坑会连撞两次，而第二次通常更狠。**
T5 修「权限模式是装配期常量」，当天晚些时候问答通道以完全相同的形状坏了一遍，
后果严重得多（程序死住，Ctrl+C/D 都退不出去）。
修第一个时我想的是「模式这个东西要能切」，不是「**装配期捕获**这个模式还有几处」。

**7. 视觉不是功能的装饰，它是功能的一部分。**
我交付了一个架构正确的 TUI，用户第一眼说「没有 TUI 呀」。
spec 里我只写了功能（活动区/队列区/输入行/状态行），**一个字没写视觉层**；
转录用户给的 CC 截图时，我盯着机制（commit/聚合/耗时），没看 chrome（分隔线/footer/色带）。
「架构对了」不等于「交付对了」。

## 哪里走了弯路（追加）

**4. 用户输入的视觉处理，我连错两次方向。**
第一版只换 glyph（白底白字看不出）；第二版做成灰色——**方向性错误**：
工具行、提示行也是灰的，于是用户自己的问题成了整屏最不显眼的东西，
而它恰恰是长对话里最重要的导航锚点。第三版才照 CC 做整行背景色带。
教训：**定视觉层级前先问「用户扫这一屏时最先要找什么」**，而不是先问「怎么和别的区分开」。

**5. 每一轮都是用户看了截图才发现，我自己一次都没先发现。**
我有终端模拟器、有 pty 探针、有 747 条测试——但**没有一次是我先看到问题的**。
因为我验的都是「我以为要验的东西」。

## 我现在质疑什么（追加）

**质疑六：交付前的冒烟脚本，测的全是不会坏的路径。**
`p5_tui_smoke.py` 跑了启动、打字、退格、shift+tab、`/mode`、`!echo hi`、Ctrl+D——
**没有一条走真实的模型回合**（因为那要花钱），于是「答案不上屏」和「权限框卡死」
两条都躲过了它。**为了省钱而绕开的路径，正是唯一没被验过的路径。**
这与 TODO 里那条方法论（「测试为了让被测路径跑起来而注入的参数，正是真实路径上会卡住的地方」）
是同一种病的两个变体。**建议：交付前必须花那几毛钱跑一个完整回合。**

**质疑七：我把「反向对照」只当成动工前的事。**
roadmap 那条固定项是我这轮加的，写的是「动工前」。而本轮所有真问题都出在**交付后**。
复盘正文第 3 条已经提过「交付前也该做一次」，但我自己写完就没执行——
**规矩写下来不等于会被执行，尤其是写规矩的人自己。**

**质疑八：`^O` 展开是个半成品，而我把它当成了一条交付。**
它是「再打一遍完整的」，不是原地展开。用户要的是「能点」。
我给了三条路让用户选，用户选了「先做便宜的那条」——这个流程是对的，
但我该更早说清楚**方案 A 在拍板时就已经把「能点」排除掉了**，
而不是等用户提出需求再倒推解释。**拍板时讲清代价，比事后解释代价诚实。**

## 下次怎么做更好（追加）

5. **交付前跑一个完整的真实回合**，哪怕花钱。三条打回的 bug 里有两条会被它抓到。
6. **spec 要有「视觉层」一节**，哪怕只写三行：什么在哪、什么颜色、层级是什么。
7. **修完一个装配期捕获的 bug，立刻把同一个装配函数的其余参数逐个过一遍**
   （已沉淀为 [K engineering/injection-seams.md](../../../../knowledge/engineering/injection-seams.md)）。
8. **把「反向对照」从「动工前」改成「动工前 + 交付前」**，并且这次要真的执行。
