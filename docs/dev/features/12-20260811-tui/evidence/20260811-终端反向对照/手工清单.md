## 1. 中文 IME 候选框位置（对应 roadmap 原则 3）

```bash
cd ~/improve/coding/agent/projects/pai && pai
```

在 `› ` 提示符处切到中文输入法，打几个拼音**不要上屏**，看候选框浮在哪里。

- **预期**：紧贴光标（即紧贴你正在打字的位置）。现在 pai 用 `input()`，
  硬件光标天然就在那儿，应该是对的。
- **要记的**：这是 TUI 化之前的**基准线**。TUI 化后如果自己接管绘制而不做
  `CURSOR_MARKER`，候选框会跑到「最后一次写字节的位置」——那才是原则 3 要解决的病。

## 2. `\r` 刷新的视觉残留（对应 roadmap 原则 2 与状态行）

需要一个会真的调工具的任务。**这一步会花钱**（一次很小的真实请求），
不想花就跳过——探针已经证明了宽度计算是对的，这里看的是**折行后的残留**。

```bash
cd ~/improve/coding/agent/projects/pai && pai
› 读一下 README.md 的前几行
```

在状态行 `◐ read_file: ...` 出现的**那一瞬间**把窗口宽度**拖窄一半**。

- **预期（按源码推）**：那一行被终端折成两行；后续的 `\r\x1b[K` 只清得掉
  最后一个视觉行，第一行会**残留在屏幕上**，直到下一次全屏滚动把它顶走。
- **要记的**：残留是否真的出现；出现后是否会被后续输出自然覆盖。
  这决定了 TUI 方案里「底部活动区」到底能不能只靠 `\r` 维持。

## 3. 真实拖动窗口的 resize（对应两篇笔记里「一次操作发多次事件」）

```bash
cd ~/improve/coding/agent/projects/pai && pai
```

在提示符处**打半行中文不要回车**，然后用鼠标拖动窗口边缘缓慢改变宽度。

- **预期（探针已证）**：pai 不发任何字节、不重绘。
- **要看的**：拖动过程中，已经打出的那半行中文**显示是否错位**
  （光标位置与实际字符对不上、字符被截断或重复）。
  探针只能证明「pai 没反应」，错位是终端重排的结果，得用眼睛看。
- **附带**：CC 的注释说「终端一次用户操作常发 2 次以上 resize 事件」。
  如果想验证，可另开一个终端跑：

```bash
python3 -c "
import signal, os, time
n = 0
def h(*a):
    global n; n += 1; print('SIGWINCH #%d -> %s' % (n, os.get_terminal_size()), flush=True)
signal.signal(signal.SIGWINCH, h)
print('拖动窗口，20 秒后退出'); time.sleep(20)"
```

拖一次窗口，看它打出几行。
