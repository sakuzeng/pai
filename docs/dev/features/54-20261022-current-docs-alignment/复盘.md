# 54-current-docs-alignment · 复盘

## 学到了什么

文档一致性测试有明确的覆盖边界：STATUS 首个通过数对上，并不能发现后文的旧数字；
链接存在也不能保证正文说的是当前行为。入口文档需要对照源码与最近交付，历史数字保留在档案。
TODO 的「已完成」标题后继续追加功能小节，会把开放项归错章节；本轮 64 条的错位属于结构问题，
不能用勾选它们来让清单看起来干净。

## 哪里走了弯路

本地 Codex hook 原样沿用了 Claude 的路径变量，变量缺失时连门禁脚本都启动不了。
用户同意补当前目录兜底后，本会话仍使用旧命令缓存；磁盘配置正确与本会话热重载是两回事。
本轮逐次显式运行原 guard，保留判定，不把它当成设计门禁拒绝后自行放行。
批量替换需求池时，一次断言因原文没有预想的空行失败；前面三个文件已写入，随后检查实际状态再继续，
没有把整次调用当成未执行而重复追加。

## 我现在质疑什么

STATUS 精简后，仍必须保留供 viz 解析的模块表；文档同时承担人读快照与程序输入，
所以纯粹按篇幅删表格会损害产品。现有测试已覆盖这条依赖，本轮没有另造状态来源。
TODO 依旧很长：结构归位与近期阅读入口不等于逐条核销，227 条开放项也不等于 227 个 bug。
后续应有证据再关闭条目，不能为了收敛数字把未验收、范围限制或待复现项混作已完成。
校验机制尚未覆盖其他当前数字的漂移，已同步 TODO；这次只改文档，未顺手改测试。

## 下次怎么做更好

更新当前快照只写一处当前测试基线，带日期、运行环境、命令口径及未运行项；历史过程留档案。
迁移 TODO 前后逐条比较原开放项，给结构迁移与实际销账分别报告数字。
修改 STATUS 要同步跑 viz 解析测试；涉及 hook 时分别验证脚本执行和当前会话是否加载了新配置。

## 2026-10-22 · 后续流程复核

这轮复盘最初没有正视「中等整理的方案未事先确认」。用户追问后已确认这属于执行偏差。
