# 26 · 复盘（四问）

## 学到什么

- 假绿的修法要从「为什么绿」反推，不是从「怎么让它红」正推。25 复核只知道
  「掐断重挂仍绿」；本次先读 `find_cut_point` 才明白根因是两锚场景下
  `anchors[:-1]` 只剩 skill 轮自己的锚、刀必然落在它上面——场景改三锚是
  从切点机制推出来的，不是调 usage 数字试出来的。机制看懂了，改法只有一种。
- 双向断言是防「假绿回潮」的便宜保险：正向断言（token 在指令消息）钉行为，
  反向断言（token 不在 tool 消息）钉场景本身成立。将来压缩参数变了导致
  尾段又保住 tool_result，先红的是反向断言，报的是「场景漂了」而不是
  沉默地退化回假绿。一条 assert 的成本。
- 「补测试也要注入反证」从 15 的教训升成了肌肉记忆：本次两条测试各做了
  一次 src 侧临时注入（掐重挂、拦用户通道），红的输出进 devlog 后立即复原。
  测试改完是绿的没有信息量，红过才算数。

## 哪里走了弯路

- devlog 里预写了一个还没跑出来的全量数字（复跑还在后台就写了
  `152.53s`），发现后改成「待填」等真实输出——「数字要真实」这条规矩
  差点在留痕环节破掉。教训：留痕永远写在事实之后，哪怕只差两分钟。
- 首次全量红在 `test_status_reports_the_current_test_count`（STATUS 数字
  过期）。这不算弯路——机器对账干了它该干的活——但说明「新增测试 → 改
  STATUS」这步在我脑子里仍不是默认动作，靠护栏兜住的。

## 我现在质疑什么

- 质疑指令消息的识别方式：断言用 `"# 项目指令与记忆" in content` 找指令
  消息，这个头部字符串是 memory 模块的实现细节，改文案就断言失效（报错
  会是「压缩重建后必须有指令消息」，尚可定位）。更稳的做法是 loop 暴露
  指令消息的结构性标记，但为一条测试加生产代码不划算——记录，不动。
- 质疑 keep_recent_tokens=1 这种极端参数的代表性：场景为了让刀落下来用了
  极小 keep_recent，真实配置（20000）下重挂的触发路径相同但节奏不同。
  测试钉的是机制不是节奏，可接受；但预算常量校准（25 遗留 3）做的时候
  应该顺带跑一个真实参数的重挂场景。

## 下次怎么做更好

- 修假绿先读被测机制的实现（这次是 find_cut_point），把「测试为什么绿」
  讲清楚再动手——比直接调场景参数快，而且改出来的场景有解释。
- 留痕文档里的数字栏位可以先立占位符（「待填」），但绝不预写看似真实的
  具体值——占位符会提醒回填，假数字只会被忘掉。
