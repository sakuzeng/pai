# 14-session-capture 复盘

写于 `./test.sh` 全绿之后（**756 passed, 3 deselected**），交付宣告之前。

## 我学到了什么

**1. 「我看不见」比「我不会」更致命。**
feature 12 的四轮视觉修正全靠用户截图往返。我有 747 条测试、有终端模拟器、有 pty 探针——
**一次都没先于用户发现问题**。不是能力不够，是**从来没有一条通路能让我看到最终画面**。
补上这条通路只花了一个下午，而它本该在 feature 12 动工那天就存在。

**2. 验证工具本身也要被验证。**
第一张 PNG 里 `›` 与 logo 的 `█` 全是方块，我差点当成 pai 的 bug 去修。
其实是我的字体路由写错了（`ord > 0x2000 就当中文`）。
**一个不可信的验证工具比没有工具更糟**——它会让你有信心地追错方向。
所以改完之后加了「查不到字体的字符主动报出来」，并在注释里写死：
出图工具报的每一个「问题」，都要先排除是它自己的。

**3. 共用一份实现，是为了让两种验证互相钉住。**
把模拟器升进 src、让回放与测试共用，省的不是代码而是**分歧**：
两份实现意味着「测试全绿」和「图上是对的」可以同时成立又互相矛盾，
而那种矛盾没人会去查。

## 哪里走了弯路

**1. 同一个「探针带回车 = 花钱」的错误，我犯了三次。**
反向对照一次、TUI 冒烟一次、录制一次，每次都卡几分钟、花点钱，
每次我都说「下次注意」。第三次之后才想起来：**靠记性挡不住的事就该靠代码挡**。
现在 `probe.send()` 遇到会提交给模型的裸回车直接抛 `WouldSpendMoney`。
教训不是「要小心」，是**「说了三次下次注意，就该停下来做个守卫」**。

## 我现在质疑什么

**质疑一：录制不含用户按键，这个缺口比我写的严重。**
我把它记成一条「遗留」，但它意味着：我看得见结果，**看不见导致结果的操作**。
用户报「我按了 X 然后就坏了」时，录制帮不上忙——我还是得让用户复述。
真正完整的应该是**双向录制**（输入 + 输出，带时序），那正好也是 `script(1)` 的形态。
现在这个是半个。

**质疑二：这条能力没有进 `./test.sh`，所以它会腐烂。**
录制与回放有 8 条单测，但**「跑一次真 pai 然后出图」这条链路没有任何自动化**——
它活在我手敲的探针脚本里，而那个目录是 gitignore 的。
下次谁改坏了 `DockRenderer` 的 write 注入点，不会有任何东西变红。
建议把「起 pai → 录 → 回放 → 断言屏幕上有欢迎语」做成一条 e2e 测试。

**质疑三：我把它做成了「AI 的工具」，但它对用户同样有用而我没说。**
`pai-replay` 可以让用户把自己遇到的问题录下来发给任何人复现，
也可以给 pai 自己做文档配图。我在设计时只想着「省掉用户截图」，
**范围定窄了**——档案里的需求写的是「让 AI 看得见」，而它其实是「让任何人看得见」。

## 下次怎么做更好

1. **交互式功能动工的第一天就建「我能看见」的通路**，与测试基建同等优先。
   feature 12 的 T1 建了模拟器（看得见几何），但没建出图（看得见观感）——
   差的那一半正好是后来所有返工的来源。
2. **「下次注意」说到第二次就停下来做守卫**，不要等第三次。
3. **验证工具的第一次输出要当成可疑的**，先证明它自己是对的，再用它去证明别的。
