# 37-context-rewritten-event · 复盘

## 学到了什么

「一件事有两条并行的通知链」这个坏味道，识别它的判据比我原来想的更简单：
如果 A 与 B 在同一个位置、由同一件事触发、只是喂给不同的消费者，那它们就是
同一条链被抄了两遍。这次是「装配层要一个回调、观测流要一个事件」，
而回调的传递成本是穿八个调用点。

更值得记的是修法的形状：缺的东西不一定是「一个新东西」。这里三个候选里有两个
是加东西（新事件 / 新回调），选中的那个是给已经存在的事实起个名字
（`CONTEXT_REWRITING` 只是一个元组）。判据没有家，不等于要造一个新载体。

## 哪里走了弯路，为什么

改测试时替换区间取反了：新节的头在文件里排在旧节之后，我却按
`s[:start] + new + s[end:]` 拼，于是把中间那一段测试复制了一份。
测试还是绿的（复制出来的那份照样通过），是 `grep -c "def _command_kwargs"`
数出 4 个才发现。教训很具体：用「两个锚点之间」这种方式改文件时，
先断言 `start < end`，否则它不会报错，只会静默地把一段内容抄两遍。

第二处：新加的 TUI 测试我一开始写成了假测试——在 `term.start()` 上引爆之后就
结束了，而被测的那一行在 `on_event` 内部，引爆时压根没跑到。写的时候我以为
「照着上一条测试的形状抄」就够了，但上一条钉的是引爆点之前的一行
（`event_sink.set(...)`），我要钉的是引爆点之后才会跑到的一行——形状看着一样，
可达性完全不同。这类假测试在 R4#T1/T2/T3 已经清过一批，我又造了一个。

## 我现在质疑什么

一、把「作废跨轮状态」挂在观测通道上，是一次真实的耦合升级，而我在
docstring 里把它写成了「诚实边界」就放过去了。真实后果是：谁把 `on_event` 换成
一个会吞异常或过滤事件的实现（比如将来给 viz 做事件采样、或给 headless 模式
关掉观测），召回与规则的去重表就会静默不失效。观测流按定义是可丢的
（`EventTrace` 自己写失败都只 warn 一次），而正确性不该建在可丢的东西上。
候选 B（独立事件）其实没有这个问题——它也是事件，但语义上是「控制」而不是
「观测」。这条值得记着：如果哪天观测流真的开始被采样/过滤，第一个要查的就是它。

二、`CONTEXT_REWRITING` 是个元组，加新成员靠人记得。我写了一条防漂移测试，
但它只能校验「集合里的每个都是真事件」，校验不了「每个会改写上下文的事件都在
集合里」——与 TurnStart 那次的教训同族（登记表校验不了「真有人发」）。
真正能防住的写法大概是给事件类加一个标记（比如一个 mixin 或 dataclass 字段），
让「我会改写上下文」变成事件自己的属性而不是外部清单。没做是因为那要动
events.py 的扁平 dataclass 联合这个既有设计，代价比这次的收益大。

## 下次怎么做更好

给「新写的测试」加一道自查：写完立刻问一句「被断言的那一行，在这条测试里
真的会被执行吗」，答不上来就注入反证一次。本轮三处接线我都做了注入反证，
正是那一步把 TUI 那条假测试照出来的——但它是在我已经把假测试写完并看着它变绿
之后才照出来的。把注入反证从「交付前的验收动作」提前成「写完一条测试的下一步」，
成本几乎不变，能早一个环节抓住。
