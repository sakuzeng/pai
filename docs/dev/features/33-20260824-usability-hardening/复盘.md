# feature 33 复盘

## 学到什么

- 「让人使用」的最大缺口不在代码在文档：九个代码修复面里没有一个比
  「README 声称一半功能不存在」伤害大——新用户按旧 README 的认知，
  skills/MCP/resume 全都不会去用。文档的漂移速度远快于代码
  （代码有测试钉着，README 什么都没有），这次的对策是 README 不再抄
  会漂的数字、把机器对账的位置（STATUS）当唯一数字出处。
- 盘点式清扫会抓到登记之外的问题：`additionalDirectories` 在 docstring 与
  STATUS 里活了 13 天、从没接线，任何单条 TODO 都没登记它——只有带着
  「用户视角走一遍配置面」的盘点才撞得到这类「文档声称、实际没接」。
  它与 TurnStart 死事件是同一族病：登记表校验不了「真有人消费」。

## 哪里走了弯路

- 两处测试写错了预期后修测试而非实现（↑ 移动的段末收位、stub server 名），
  每处都先确认了实现语义是对的再动测试——顺序不能反，这是 feature 19
  记过的规矩，这次守住了。
- 无大弯路：九个面全部有 TODO/复盘预记的修法形状，本 feature 更像
  「按图施工」，证明了把修法形状记进 TODO 的习惯在偿还利息。

## 我现在质疑什么（必答）

- 「首启提示」半边我裁掉了（一次性 banner 读过即丢，双通道更可复核）——
  但这个判断没有用户数据支撑：真实新用户第一次被 bash 白名单咬到时，
  他大概率没跑过 /permissions 也没读完 README。dogfooding 或真有第二个
  用户后，这条要重看。
- once 刻意不采用配置的 bypassPermissions（防旧 settings 静默提权）——
  方向保守，但与「用户显式配置的就该生效」直觉相抵，告警文案把出路
  （--permission-mode）说清了，冲突暂记于此。
- README 一页塞下了全部配置参考，随功能再长会不可维护；届时该拆
  docs/ 下的用户文档，现在拆是预防性建设。

## 下次怎么做更好

- 配置键的接线该有机器校验：settings 出现过的键（文档/代码注释声称的）
  与装配层实际消费的键做一次对账测试，`additionalDirectories` 这类
  「声称未接」就会自己红出来。这次没顺手做（要定「声称」的机器可判口径），
  记一条 TODO 待评估。
- 用户视角盘点（拿 README 从头走一遍安装到配置）值得成为大版本前的固定
  动作，这次是用户点名才做的。
