# 55-baseline-consistency · 复盘

## 学到了什么

索引与正文一起使用同一个有缺陷的正则，会一起漏掉数据，看起来仍然一致。
这次旧正则只认 NN.，既没读到 ## NN. 的正文，也没有提示正文不完整；把形状补齐后才暴露 12 条缺项。
保留列表而非先 set 去重，才能让重复编号或重复索引成为错误。

同样，目录覆盖完整不等于状态一致：补齐总览后，还发现 05 的已验收和 16 的已交付没有同步。
所以本轮另加生命周期对账，并先取得红灯证据后再改数据。

## 哪里走了弯路

早期文档整理只检查目录和链接，没有把索引覆盖与状态一起验证，留下了后续手工对账。
新补的 05 行也先写成了已交付，直到用档案头部核对才纠正为已验收。
本轮把它作为真实失败保留，未把第一次补表描述成一次到位。

全量数字校验和 STATUS 的通过数字耦合：新增校验后，先按实际收集数登记明确标注的预期值，
再用全量实际输出替换；不能把等待验证时的预期写成已经实测通过。

## 我现在质疑什么

217 条开放项仍混有实现候选、范围限制、方法论与等证据事项，数量不能直接用来排期。
本轮只处理有明确审计证据的状态，不借机替用户裁掉功能候选；以后是否进一步拆分条目类型，
要先明确哪些已经确认实施、哪些只是记录，不能把「整理」当成重新决定产品路线。

结构测试也不等于文档语义正确。本轮能发现编号、漏项、重复、生命周期与当前通过数问题，
仍不能证明 README 所有行为描述或候选方案已经由真人批准；相关边界继续留在 TODO。
54 的偏差说明再次提醒：留痕不能替代事前确认，55 的继续授权不能追认之前的选择。

## 下次怎么做更好

索引变动时同时检查双向覆盖、唯一性和生命周期；对不同历史语法各保留一个明确案例。
核销 TODO 时把完成证据、原始登记、保留的剩余范围一起记录，避免把父项部分完成误作全部完成。
把历史原件与本次映射放进版本库中的 evidence，而非只留在临时目录；交付后再确认当前快照只保留实际结果。
