# 23-model-visible-is-recorded · 复盘

## 学到了什么

- 「唯一收口」与「按身份幂等」是两件可拆的事：CC 的 recordTranscript 两者都做，
  但前者不需要消息有身份、今天就能抄；后者依赖 uuid（A1）。把参照实现拆成
  「哪半的前提我有」再抄，比整块「抄/不抄」二选一有用。
- 不变量测试在写下时就绿是正常的，别因此觉得它没用——它钉的是「将来第 6 处
  append 的人」。注入反证（故意漏记一类消息）证明它真能红，这一步不能省，
  否则「写时就绿」与「永真断言」外表无法区分。
- `_inject_instructions` 的 insert 是收口的显式例外：例外要写进收口函数的
  docstring 并说明为什么落盘顺序仍一致（首次注入早于一切后续追加；
  压缩后重注入的会话整个被 replay 拒收）。留一个没解释的例外，
  收口就名存实亡。

## 哪里走了弯路，为什么

没有实质弯路。一处差点走偏：最初想给「收口完整性」写 getsource 式 lint
（loop 里不许再有裸 session.append）——feature 20 刚裁决过这类断言的边界，
回放不变量本身就是行为版的闸，lint 是重复保险，砍掉了。

## 我现在质疑什么

- 不变量测试只跑 loop 路径；REPL 侧 `_run_shell` 的「我执行了命令」转述
  与 `/clear` 重建有自己的成对 append，漏了不会红（已登记 TODO）。
  收口的边界画在 loop 是本轮拍板的范围，但「唯一入账口」这个词在 REPL 侧
  是名不副实的——下次动 interactive 的落盘时应把它们也并进 `_record`。
- `replay_messages` 对 compaction 一刀拒绝，对「录了一半的会话」（进程被杀）
  却照常拼——半截会话拼出来的对话结构可能非法（assistant 有 tool_calls 而
  tool 结果缺失）。evals 用它当 fixture 加载器时要不要校验配对完整性，
  届时再定。

## 下次怎么做更好

参照实现前先问「它的哪些机制依赖我没有的前提」，把依赖前提的部分显式挂到
对应的未来立项（本轮的 uuid → A1）——否则要么抄不动，要么抄来个空壳。
