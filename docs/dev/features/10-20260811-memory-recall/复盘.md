# 10-memory-recall · 复盘

写于交付当天（458 passed 之后，含真跑冒烟的修复）。「做了什么」在 [devlog.md](devlog.md)，这里只记可迁移的东西。

## 学到了什么

### 一、把「几条待办」当成「一个需求」看，第一件事是找它们之间的锁

TODO 里躺着三条独立条目（frontmatter / 新鲜度 / 召回层），用户的判断是「合成一个档案，
因为它们改同一个文件」。真正分析下来，共用文件只是表象，底下是一条硬耦合链：

粒度（主题追加 vs 一事一文件）× 索引是否必须全量 × 召回层是否存在

- 「一事一文件」只有在有召回层时才成立——否则索引行数 = 记忆条数，200 行上限提前撞；
- 反过来，「主题追加」会让 `description` 和 mtime 都只是半真半假
  （一个累积 50 条 bullet、跨三个月的文件，描述写什么？mtime 只反映最后一次）。

于是拍板顺序与 TODO 记的正好相反：必须先拍最贵的那条（召回层），
前两条的形状才有唯一解。可迁移的判断：合并几条待办时，先问「它们之间有没有
先后依赖」——如果有，待办列表里的顺序几乎一定是错的，因为它是按*发现顺序*记的，
不是按*决定顺序*。

### 二、读别人的源码之外，还该去读别人运行时产生的数据

走读笔记 `cc-memdir.md` 覆盖了读侧三个文件，但写侧格式（frontmatter 到底有哪些字段）
是空白。这次发现本机就跑着一个 CC 的记忆目录（`~/.claude/projects/<slug>/memory/`），
一手样本直接读出来四条走读没有的信息：`description` 与索引钩子是两个不同字符串、
`modified` 是写进 frontmatter 的 ISO 戳（与 mtime 并存）、`originSessionId`、
`node_type` 这层套娃。

可迁移：源码告诉你「它能做什么」，运行产物告诉你「它实际写成什么样」。
后者常常更便宜（不用反编译）也更准（没有死代码）。以后立档案时，
「有没有它的真实产物可读」应该和「有没有源码可读」一起问。

### 三、把一致性问题变成「结构上不可能」，比写检查代码便宜

索引原本是账本：`_ensure_indexed` 往 `MEMORY.md` 追加一行，去重靠子串匹配
（`if f"{name}.md" in existing`——文件多了 `a.md` 会在 `xa.md` 那行误命中）。
改成投影之后，四类补丁（新增/描述变更/文件被删/去重）全部消失，那个子串 bug
也跟着消失了——不是修好的，是没有地方可待了。

关键在于成本论证：扫描代码本来就要为召回写，索引重建只是同一个扫描结果的
第二个消费者。「零新增机制」是这个方案能压过账本方案的真正理由，
而不是「投影听起来更干净」。

## 哪里走了弯路，为什么

没走大弯路，但有一次判断是被测试逼出来的，不是想出来的。

`render_index` 有两个消费者（写盘的 `MEMORY.md` / 进上下文的索引）。
我最初默认两者渲染同一份文本——直到写 `test_render_index_without_now_has_no_relative_time`
时才意识到：相对时间是渲染时刻的函数，写进持久文件就会腐坏。
一条三个月前的记忆在磁盘文件里写着「今天」，正是新鲜度这个特性要防的东西，
而我差点亲手制造它。

为什么当时会那么想：拍板讨论停在「索引带描述与相对时间」这个层面，
没有区分「索引的两个出口」。讨论时把它当一件事，实现时它是两件事。
换个人大概率会踩同一个坑——因为「一个函数两个调用点」在设计图上看不出来，
只有在写「这个调用点该断言什么」的时候才会分叉。

## 我现在质疑什么

一、~~`json_object` 一次都没真验过~~ → 验了，结果比我担心的更糟，而我差点就那样交付了。
（用户授权后当天补跑。）我原本担心的是「provider 报 400」；真实情况是
provider 欣然接受，然后召回 100% 失效——两个 bug 叠加，且离线测试全绿、零告警：
`max_tokens=256` 被推理 token 吃光让 `content` 变空串，模型又把 `[type]` 装饰抄进文件名
让白名单全丢。我写的 30 条离线测试没有一条能发现它，因为假 provider 只会返回我
让它返回的东西——它测的是「我以为模型会怎么答」，不是「模型实际怎么答」。

留下来的判断：凡是「行为取决于真实模型输出形状」的代码，假 provider 只能测解析分支，
测不出契约。这类代码必须有一次真跑，而且真跑要看的不是「有没有报错」，
是「结果对不对」——第一次冒烟其实已经把 `选中=[]` 打在屏幕上了，
是我一开始只盯着「有没有 400」而差点滑过去。

二、「一事一文件 + 没有收缩机制」可能是本次交付里最大的债。
06 复盘质疑二说过「遗忘策略便宜的时候是设计期，贵的时候是数据已经脏了之后」，
我当时点头，这次却又一次把它推给了「等它真长起来」——而这次我明知道自己让它长得更快
（索引行数从「主题数」变成「记忆条数」）。CC 的解法在写入侧提示词里
（先查有没有已覆盖的、更新而不是新建、发现错的要删），pai 抄了「更新而不是新建」
（做进工具了），但没抄「删」。`remember` 结构上只能增和改，不能减。
这不是遗漏，是我选择性地只抄了容易做的那一半。

三、「description 一个字段兼任两处文案」省得对不对，我不确定。
CC 让模型写两份：frontmatter 的 `description` 给召回器读、索引行的钩子给主模型读。
我合并成一份，理由是「少一个字段」。但这两处的读者与用途其实不同——
召回器要的是「这篇讲什么，判断相关性」，主模型要的是「值不值得展开看」。
本机样本里那两串文字确实不一样，说明 CC 那边的模型自发地写出了不同侧重。
现在无从判断合并的代价，因为 pai 还没有足够多的记忆来观察。这条我建议等有数据再复议，
而不是现在改回去——但它值得记着，别过两个月忘了这是一个*选择*而不是*自然结果*。

四、召回块入 messages 之后，压缩会把它摘掉且不会重来。
指令消息有重注入兜底（D#42），召回块没有。长会话里压缩一次，之前召回的记忆就没了，
而 `RecallState.surfaced` 还记着「已经注入过」，于是再也不会重新召回。
这是本次设计里我最没想清楚的一处——`surfaced` 的语义是「已经在上下文里」，
但压缩恰恰会让这个前提失效。已登记遗留 6，但我现在觉得它比「遗留」更严重一点：
它让召回在长会话里单调衰减到零。

五、这次交付里最大的收获不是召回层，是「离线全绿、线上全废」这个具体形状。
已沉淀成 [K model-api/reasoning-models-max-tokens.md](../../../../knowledge/model-api/reasoning-models-max-tokens.md)
（换个项目仍成立：推理模型的 `max_tokens` 语义 + 模型会抄回提示里的装饰 +
「校验用白名单、匹配放宽」这个通用姿势）。
但更该记住的是它怎么被发现的：一次真跑、三个 query、五百个 token。
成本低到不该省，而我在没被授权时把它整个跳过了，还在遗留里写得像个可选项。

## 下次怎么做更好

「需要花钱才能验证的事」应该在拍板时就一次问掉，不要留到交付前。
本次 spec 写了「实现期必须真验一次」，措辞很坚决，但没写「谁来跑、要花多少钱」，
于是收尾时被我安静地跳过、降级成一条遗留。而真去问，用户一个「可以」就解决了，
成本是五百个 token——我替用户做了一个「这钱不该花」的决定，而那不是我的决定。

具体改法：拍板问答里凡是出现「照抄 X 的做法」，就顺带确认一句
「X 的前提在我们这儿成立吗，怎么验、验一次多少钱」。
本次两个 bug 的根都在这里：抄了 CC 的 `max_tokens=256`（前提是不推理的模型）、
抄了 CC 的白名单逐字校验（前提是它的模型会规规矩矩回文件名）。
抄来的东西带着它的前提，而前提不会自己跟过来。
