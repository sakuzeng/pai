# 07-20260810-permissions · 复盘

## 学到了什么

**「安全机制有没有牙齿」和「安全机制在不在」是两个独立的问题，要分别验。**
本次注入验证最有价值的一条不是「测试变红了」，而是：把求值顺序整个翻过来
（`deny → ask → allow` 改成 `allow → ask → deny`）之后，Task 3 那 7 条
复合命令测试**一条都没红**。求值顺序与「复合命令逐条要求」是两条正交的防线，
只验其中一条会给人「权限系统被测住了」的错觉。
可迁移的形式：**给一个防御性组件做变异测试时，注入点要覆盖每条独立的防线，
而不是找一个最显眼的常量翻过来交差。**这条够格进 knowledge/concepts/。

**第二条：拒绝的语义要和出错的语义分开。** 工具跑失败与工具不许跑，对模型是
两种完全不同的信号——前者该诱发重试，后者该诱发换做法。所以回填给模型的字符串
带了 `权限被拒绝，该工具调用未执行。原因：` 前缀，`is_error` 也刻意保持 `False`。
把两者混成一个「错误」字符串，模型会一遍遍重试一条永远不可能通过的调用。

## 哪里走了弯路，为什么

**spec 把 matcher 签名钉成三参，却又要求路径锚点——这两条从一开始就凑不到一起，
而我是写到 Task 4 才发现的。**

当时为什么没看出来：spec 第 2 节（匹配下放）和第 4 节（路径锚点）分开读都成立，
`(specifier, args, require_all)` 看着信息很充足。漏掉的是
「`/secrets/**` 的含义取决于**哪个设置文件写的它**」——这个信息既不在 specifier 里
（它就是 `/secrets/**` 本身），也不在工具参数里，它是**规则的属性**。
三参签名里根本没有「规则」这个东西的位置。

换个人会不会踩同一个坑：**会**。防呆的办法不是「审 spec 时更仔细」，而是
**写接口签名时，把每个参数的来源标出来**——specifier 来自规则、args 来自模型、
require_all 来自桶。标完就会发现「锚点来自规则」没有出口。

**第二处弯路是 plan 自己带的**：plan 说「全部完成后更新 STATUS」，
但 `test_status_reports_the_current_test_count` 是拿实时 `testscollected` 对账的，
Task 1 加完 7 条它立刻就红。真按 plan 走，中间六个 task 会全程带着一条红，
「先红后绿」的信号当场失真。改成每个 task 同步一次。

## 我现在质疑什么

**质疑一（够格升格成 decisions 复议）：`default_decision` 默认 `allow`，
配上「pai 没有只读命令免提示集合」，这个组合比 spec 写的时候看起来更糟。**

spec 里那句自主判断的理由是「与压缩、事件、记忆三次接线一致——不配置 = 行为与
接线前逐字相同」。做完之后我认为这个类比**不成立**：那三次接线，不配置的代价是
「少一个优化」；这次接线，不配置的代价是**权限层完全不存在**。
一个装了权限系统但默认全放行的 agent，和没有权限系统的 agent，在被利用时表现一样。
更麻烦的是它会产生虚假的安全感——STATUS 上写着「permissions 可用」。

不主张现在推翻（改默认值是破坏性变更，且没有只读命令集的话默认 `ask` 会烦到没法用），
但主张：**首启时若两层 settings.json 都不存在，应当明确告诉用户「当前无任何权限规则，
一律放行」**。已登记 TODO。

**质疑二：拍板问 2 的「匹配下放给工具」，我现在觉得只对了一半。**
`bash_matcher` 确实该住在 shell.py。但 fs 三件套共用的 `path_matcher` 与
「工具」的关系很弱——它真正依赖的是「这个参数是一条路径」，不是「这个工具是 read_file」。
将来加第五个碰路径的工具，得记得手动 `matcher_for` 挂一次，忘了就静默退回默认的
朴素 fnmatch（而那个实现连 `*` 跨不跨 `/` 都不管）。
按**参数语义**挂匹配器可能比按工具挂更对。没有登记为 TODO，因为现在只有 4 个工具，
改造的收益还抵不上改动面——但记在这里，加第五个 fs 类工具时应当重估。

**质疑三：`strip_wrappers` 的「带标志就不剥」是我推的，不是抄的。**
plan 只给了 `xargs -n1 npm test` 这一个例子。我实现成「任何以 `-` 开头的后续 token
就整个放弃剥离」。这对 `xargs` 是对的，对 `timeout -s KILL 30 npm test` 就偏保守
（会判不匹配 → allow 更难通过 → 安全方向）。保守的方向是对的，但它是**我猜的**，
不是官方语义。真实用户配了 `Bash(npm test *)` 又习惯写 `timeout -s KILL` 的话，
会遇到「规则明明写了却不放行」的困惑。

## 下次怎么做更好

**在 plan 的每个 task 里写明「这条测试在实现之前应该是什么颜色」。**

本次 Task 3 有两条测试（`test_env_runners_are_not_stripped_and_this_is_a_known_hole`、
`test_word_boundary_before_star`）在实现之前就是**绿的**——默认 matcher 的朴素 fnmatch
恰好给出同样答案。红→绿的数字看着是 `5 failed → 18 passed`，很漂亮，
但那 7 条里真正被这一步验到的只有 5 条。
我是写 devlog 时才注意到的，而这种「假绿」完全可能一直没人发现。

具体做法：plan 写测试清单时，每条后面标 `[红]` 或 `[本就绿·防回归]`。
标不出来的，说明还没想清楚这条测试到底在钉什么。
