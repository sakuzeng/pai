# 40-old-debts · 复盘

## 学到了什么

「触发条件」这个东西，写下来的时候是一份承诺，但承诺里少了一半：谁在什么时候来查。
本轮三件事里有两件的触发条件早就满足了（测试文件 10 个 → 实际 80 个；
某模块落地 → 早落地了），而它们能一直挂着，不是因为判据写得不好，
是因为判据没有查的人。可执行的改法是：写触发条件时同时写清「它会在哪个动作里
被顺带检查到」——比如「下次动这个文件时」「每次批清时」，而不是让它悬空等着。

第二条，也是这轮最实的一条：触发条件满足 ≠ 该动手。`compaction.py` 那条的字面
（「等 summarize 落地」）满足了，但同一条目里还写着参照（pi 893 行才拆），
而实际落地后是 392 行——预估的 +300 没有兑现。照着勾打钩就会拆一个不该拆的文件，
还会与 AGENTS 的「一个阶段一个模块」直接相抵。所以复核旧账时，
条目自带的参照与数字要一起读，不能只读结论那一句。

## 哪里走了弯路，为什么

搬家验收脚本被自己绊了两次，都不是被测代码的问题：旧 `write_memory` 的签名
`float | None` 在 3.9 运行期要靠文件头的 future import 才合法，我单独 exec 那个
函数节点时当场 TypeError；紧接着第一版比 mtime 时把「没传 mtime」的那组也算进去，
而那组本来就该不同。两次都是「验收工具自己有 bug」——而这类 bug 的现象与
「搬家搬坏了」一模一样，差点让我以为是 helper 写错了。
（这正是 instruments-lie 那篇讲的东西，只不过这次仪器是我临时写的验收脚本。）

抽 `commands.py` 时我先想的是「按行数把最大的那块切出去」，也就是奔着
`_run_tui`（304 行）去。想了一会儿才意识到那是错的切法：`_run_tui` 是真的复杂，
切开它只会得到两个互相调用的半个循环。正确的切法是按「谁在共用」——
命令簇被两条主循环共用，所以它才是那个不该住在任何一条循环里的东西。
判据从「哪块最大」换成「哪块被共用」之后，方案在两分钟内就清楚了。

## 我现在质疑什么

一、`tests/helpers.py` 现在是个杂物间的雏形。它装了 4 样东西，各自与不同的
子系统有关（权限、输入、记忆、REPL）。今天它们的共同点只有「被两个以上的测试文件用」
——这个共同点撑不起一个模块的语义。第三次往里加东西的时候就该按主题拆
（`helpers/memory.py`、`helpers/repl.py`），而不是继续往一个文件里堆。
我现在不拆是因为拆的判据还看不清，但这句话本身与我批评过的「等第三个再抽」
是同一套说辞——所以我把它写在这里，而不是写成一条自我安慰的 TODO。

二、`commands.py` 的函数签名普遍很长（`_handle_command` 收 14 个 keyword），
搬家没有改善这一点，只是把它搬到了新地方。真正的问题是这些命令需要几乎整个
会话状态，而我们没有一个「会话对象」把它们装起来（TODO 里那条「跨轮平行状态
已三件，到第四件该封 Session」说的正是这个）。这轮把它们聚到一处，反而让那个
缺口更显眼了——14 个参数并排放在一个文件里比散在两处更难看。

三、两篇新笔记我写完就交付了，没有验证过它们是否真的能被将来的自己用上。
knowledge/ 的一贯问题是「写的时候很清楚，用的时候想不起来有这篇」。
`todo-drift.md` 那篇尤其——它讲的正是「记录会失真」，而它自己也是一条记录。

## 下次怎么做更好

复核一条带触发条件的旧账时，固定读三样：条目的结论、条目自带的参照/数字、
以及当前代码的实际数字。本轮 `compaction.py` 那条如果只读结论就会拆错，
而三样一起读，两分钟就能得出「不拆」并写下重估判据。这条比「触发条件到了就做」
更接近真实情况——判据本身也会过期。
