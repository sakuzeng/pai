# 57-project-task-evals · 复盘

## 学到了什么

完整历史仓库快照不是把 src 放进临时目录就够了。原有测试依赖 tests 下的 helper，pytest 配置与 conftest 却又不能任意继承；本轮要同时保留 helper 导入、隔离原 conftest、断言 pai 来自历史 src，才得到可信的原始红与参考绿。

真实修复的父提交与参考提交让两道 bug 有可追溯来源；队列和边界题的错误实现则是人为评分探针。把这两种来源说清，比统称“真实 bug 任务”更重要。六题参考契约通过证明设施可达，不证明模型会做。

## 哪里走了弯路，为什么

相对输出目录的真实 CLI 冻结先失败，原因是评分器把相对 --confcutdir 原样交给更深一层 cwd 的子进程；单测一直传绝对 tmp_path，没有覆盖这个接缝。先补入口反证得到真实 1 failed，再统一 resolve 并得到最终新增 32 passed，而没有把错误 pytest 返回当成题目失败后继续冻结。

第一次材料验证还遇到 fake_llm/trajectories 导入错误；补 helper 路径时没有把原测试的 conftest 一起引回来。resume 题另冻结了两条已有相关回归的函数选择，避免把旧的假 header 最近会话测试当新 cwd 契约，未扩大为历史全量兼容。

全量第一轮唯一失败是 STATUS 的旧数量 1965 与选中 1997 不一致。保留 1 failed、1996 passed 的输出，更正当前收集口径后再完整运行，最终 1997 passed、8 deselected in 224.05s。没有把预计数量冒认已通过结果。

## 我现在质疑什么

六个历史题仍由同一执行者挑选和编写评分材料，两个集合各只有三题。来源真实与固定哈希不能消除选择偏差，也不能证明训练污染不存在。保留集只用于未来调参隔离，不应被描述成严格盲测；代表性条目仍保持开放。

冻结整个评分实现文件和依赖版本能阻止静默变化，也可能让无行为变化的格式修改触发漂移。这是本轮接受的严格性代价；不能为图方便自动刷新，更不能把一次刷新后的成绩与旧基线直接作因果比较。

STATUS 的“唯一当前通过数”与用例选中数量绑得很紧，本轮因此多跑了一次全量。这个门禁能抓漂移，但是否要把“上次通过结果”和“当前收集口径”分开，仍值得有成本证据时再评议；本轮没有改它的设计。

## 下次怎么做更好

入口先覆盖相对路径、cwd 变化和实际子进程，再写漂亮的接口单测。历史任务先证明原始失败是行为断言，不能接受缺依赖、缺参数或收集失败冒充 bug 复现。

下一轮接真实 once 前，先单独确认模型、重复次数、步数/token/时间边界与权限，新增运行适配并保存原始失败，不沿用 56 的九次费用授权。只用开发集排查策略，显式解封保留集时冻结候选和判据；不把本轮参考契约当模型成绩。该后续已登记 TODO。
