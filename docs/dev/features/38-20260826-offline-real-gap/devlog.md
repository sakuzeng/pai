## 2026-08-26 · 立项：先把「差距」拆成三类

用户指示「当前代码层面和真实使用的差距，我想改善这个」。

拆成三类再问覆盖范围，是因为三类的兑现方式完全不同：①离线其实能验只是没验的，
②只有真模型能验的，③只有真人真终端能验的。用户拍板三类都覆盖。

差值恒为 0 → 切点永远是「无可压」→ 自动压缩在所有 e2e 里结构上走不到。
2026-08-10 用户真跑报告过「压缩一次都没触发」，那条 TODO 一直开着；
而离线这边没有任何测试会因此变红——它们只是从来没走到过那一段。

## 2026-08-26 · T2：自动压缩在真进程里真的发生过

目标：兑现 2026-08-10 那条「压缩链路在真实使用中一次都没被走到过」。

`Session` 加 env 覆盖（`PAI_CONTEXT_WINDOW=20000`、`PAI_KEEP_RECENT_TOKENS=1000`），
脚本里两轮工具调用各自钉死 usage（4000 / 8000），差值 4000 跨过保留门槛。

两头都断言：屏幕上有「压缩：切于 N」，且假 provider 真的收到过一次不带 tools 的
请求（那是摘要请求，也是「压缩不只是打了行字」的唯一硬证据），
摘要请求里还得带着被压掉的那段历史。

第一次跑就出真结果，顺带把两件事从设计推论变成跑出来的事实：

```
› 看看那个文件
🗜 锚点不足（<2）无法定真实切点，本步暂缓压缩（估算 4022）
🗜 压缩：切于 2，估算 8022 → 929
● 压缩之后我接着答完了。
```

第二行就是 STATUS 已知缺陷 1 描述的「两步节奏」（压缩后锚点簿被清空，
要再等一轮真实 usage 才凑得够两个锚）——顺手把它也钉进断言。

一处小坑：断言里我写的是 `🗜️`（源码里的形状，带变体选择符 U+FE0F），
屏幕模型里是 `🗜`。改成不比 emoji，只比「压缩：切于」——断言钉的是
「用户看得见压缩发生了」，不是字形的字节形状。

改动：`tests/test_e2e_tui.py`。绿：`1 passed`。
注入反证：把假 provider 的 usage 退回固定值 → `1 failed`（正是它堵住了这条路）。

## 2026-08-26 · T3：流中途 Ctrl+C

目标：feature 15 遗留的另一条——掐得断，且 REPL 不死。

两处踩坑，都记下来：

其一，`session` fixture 等到 logo 出现就返回，但那时主循环还没开始读键盘——
第一版的提交根本没进去（屏幕上只有 logo）。加一句 `s.send("", until="/help 看命令")`
才是「真的可以打字了」的同步点。

其二，中断的时机不能用 `until` 当同步点：流式期间的增量要等这一轮收尾才进
scrollback，屏幕上看不到「正在吐」，于是 `until` 会一直等到整轮结束——
Ctrl+C 就落成了空闲态的那一档（第一版正是这么假绿的，屏幕上显示的是
「(输入已清空，再按一次 Ctrl+C 退出)」）。这里只能死等一个固定秒数，注释写明了原因。

断言除了「已中断」还加一条：整段答案不许完整出现在屏幕上。少了它，一个
「中断消息照打、但流照样跑完」的实现同样能通过——那正是「已中断」这三个字
最容易撒的谎。

注入反证做了两轮，第一轮选错了知识点：拆掉 `on_event(Interrupted(...))` 之后
测试照样绿（「已中断」还能从 `AgentEnd` 的文案来）。换成拆掉
`assemble(..., flag=flag)` 才红——`1 failed`。选错的那一次也记着：
反证选错位置会给出「测试没用」的假结论。

顺带收掉一处噪音：中断的流会让假 provider 往断掉的 socket 写，
socketserver 在 handler 返回之后 flush `wfile` 时才撞上 EPIPE，
handler 内部的 try 够不着（实测：包了 try 之后 traceback 照旧）。
在 `ThreadingHTTPServer.handle_error` 上吞，且只吞连接类错误——
假 provider 自己坏了必须看得见。真服务器本来也不会因为客户端走人而喷栈。

改动：`tests/test_e2e_tui.py`、`tests/fake_provider.py`。绿：`1 passed`。
