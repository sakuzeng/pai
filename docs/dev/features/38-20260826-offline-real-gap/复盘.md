# 38-offline-real-gap · 复盘

## 学到了什么

假的那一端把某个真实世界里会变的字段常量化，是一类独立的、很安静的失效模式。
它不像「假数据不真实」那样只影响断言的说服力——它会让下游依赖这个变化的判断
永远走同一条分支，于是一整段代码在这套仪器下不可能被执行。没有任何测试会因此
变红：它们只是从来没走到那一段。

判据可以写得很具体：给假的那一端列一张「它与真的哪里不同」的表，逐条问
「这处不同会不会让某条被测路径不可达」——不是「像不像」，是「可达不可达」。
特别值得查常量化的字段。已回流成 knowledge/engineering/instruments-lie.md
的第五种骗法。

第二条：同一个缺口，在两边各自被记了一次，中间十几天没接上头。用户 2026-08-10
在真实使用里报告「压缩一次都没触发」，那条 TODO 一直开着；离线这边所有压缩测试
全绿。两条记录都在，谁也没去问一句「离线绿而真实不触发，那绿的是什么」。
真正的教训不是「要 dogfooding」，是当离线与真实给出相反结论时，那本身就是
一条最高优先级的线索，而不是两条各自待办的条目。

## 哪里走了弯路，为什么

注入反证选错了位置一次：验「中断 e2e 是不是真的能红」时，我拆掉了
`on_event(Interrupted(...))`，测试照样绿，我差点据此下结论说这条测试没用。
实际是「已中断」这三个字有两个来源（事件渲染与 `AgentEnd` 文案），
拆掉一个还有另一个。换成拆 `assemble(..., flag=flag)` 才红。
反证选错位置会给出「测试没用」的假结论——和它本来要防的「测试是走过场」
同样有害，而且更容易让人把好测试删掉。

中断那条 e2e 的第一版是假绿：我拿屏幕内容当同步点（`until="这段答案很长"`），
而流式增量要等这一轮收尾才进 scrollback——于是它一直等到整轮结束，
Ctrl+C 落成了空闲态那一档，屏幕上明明写着「(输入已清空…)」而测试是绿的。
这与 feature 18 那次「假 provider 秒答时『模型正在答』这个状态根本不存在」
是同一个坑的第二次：用被测系统的输出当同步点，而那个输出恰好在被测的时间窗内
不存在。

## 我现在质疑什么

一、`--llm` 那两条冒烟，我离线只验了「参数名和签名都存在」，这远不够。
它们默认跳过，写错了要等到有人花钱才发现——而这正是本轮要治的那类病，
我在治它的同时又造了一个小号。更好的做法是让它们能对着假 provider 跑一遍
（把 client 与断言分开：管线部分对假 provider 跑，行为断言部分只在真模型下跑），
本轮没做是因为那要把测试拆成两半、结构变复杂。留着这个疑问。

二、把 `PAI_CONTEXT_WINDOW=20000` 配上默认 `reserve_tokens=16384`，
实际阈值只剩 3616，压缩几乎每步都想触发——我用它构造出了一次成功压缩，
但这个配置本身处在「已知退化区」（STATUS 缺陷 4：`window <= reserve` 时恒为 True）。
也就是说这条 e2e 验的是「压缩链路能跑通」，不是「压缩在正常配置下会被恰当地触发」。
后者要么等真实长会话，要么把 `reserve_tokens` 也做成可配。我倾向于后者是对的，
但那是另一条改动，本轮没顺手做。

三、`.pai/rules/tests.md` 这条规则我写完就交付了，没有验过它在真实会话里
到底有没有帮上忙。它现在的状态和它要治的病一模一样：写了，没验过。

## 下次怎么做更好

给「离线结论」与「真实观察」之间的矛盾建一条硬规矩：真实使用里报告的现象
（如「压缩一次都没触发」）如果与离线测试的结论相反，登记 TODO 时必须
同时写一句「离线那边绿的是什么」。本轮这条缺口能拖十几天，就是因为两边各记各的，
谁也没被逼着回答那一句。写下来五分钟，而它直接指向的就是仪器。
