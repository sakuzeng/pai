# 只有真人 + 真终端才验得了的（feature 38 第三类差距）

这份清单不是 TODO，是「机器验不了、必须有人坐在真终端前面看一眼」的那部分。
写下来的理由：不写的话它会以「测试全绿」的形式伪装成已验证——
而这正是 pai 反复踩的那类坑（K engineering/instruments-lie.md）。

跑法：`pai` 起交互模式（真 tty、不是管道），逐条看。
撞到问题就登记 TODO 并注明「手工清单第 N 条」。

## 前置

- 真终端（iTerm2 / Terminal.app / ssh 都算，各自结论可能不同——终端差异本身
  就是这份清单存在的原因之一）
- 有效的 `DEEPSEEK_API_KEY`（会花钱，几分钱量级）
- 在一个有内容的仓库里起 pai，不要在空目录里——空目录看不出边界与规则

## 一、中文 IME（feature 12 spec 验收标准第 11 条，至今未经真人验证）

1. 在输入行敲中文（拼音输入法），看候选框位置是否贴着光标。
2. 输入到折行之后再敲中文，候选框是否跟着跑到第二行。
3. 候选框弹出期间按 ↑↓：应该是输入法在翻候选，不是 pai 在翻历史。

基准线（离线量到的宽度契约）见
[features/12 evidence 手工清单](../../12-20260811-tui/evidence/20260811-终端反向对照/手工清单.md)。

## 二、resize（evidence 第 4 条：状态行按事件重算宽度而不是按 resize）

1. 让 pai 跑一个会打字的回合，中途把窗口拖窄。
2. 看状态行：缩窄后、下一个工具事件之前，屏幕上是否还留着按旧宽度渲染的那一行
   （症状是被终端折成两行，而 `\r\x1b[K` 只清得掉最后一个视觉行）。
3. 再拖宽，看有没有残留。

## 三、颜色与主题

1. 深色/浅色终端各起一次，看 dock 与工具行的颜色是否都读得清。
2. `NO_COLOR=1 pai` 应完全无色且不乱码。
3. 管道里 `pai "任务" | cat` 应无 ANSI、无 `\r`（这条也有自动测试，但真终端
   下的 TERM 差异只有真跑才看得到）。

## 四、鼠标（feature 16 的 ★ 悬案：拖选卡顿成因至今未确诊）

1. 在 transcript 区域拖选一段文字，感受有没有卡顿；有的话记下终端与行数。
2. 从后往前拖选，松手后是否复制成功（2026-08-11 修过一次的那条路径）。
3. `kill -9` 掉 pai，回到 shell 看鼠标是否还失灵（已知缺陷，兜不住，只确认现象）。

## 五、退出与恢复

1. 正常 `Ctrl+D` 退出：终端是否回到主屏、有没有残留 dock。
2. `kill -9` 之后：是否被留在空的备用屏里（13 复盘质疑二，已知兜不住）。
3. `pai --resume` 接着聊：提示里那两行「设置不跟着回来 / 录制于别的目录」
   （feature 35 加的）是否在该出现的时候出现。

## 六、规则与记忆（feature 36/38，与 `--llm` 冒烟互补）

1. 在项目里写一条 `.pai/rules/x.md`（带 `paths:`），让 pai 读一个匹配文件，
   `/memory` 里应看到它被标成「本会话已注入」。
2. 让 pai `remember` 一条事实，下一轮问一个能命中的问题，看召回块有没有真的注入
   （`/status` 与观测流 `pai-viz` 都能佐证）。
