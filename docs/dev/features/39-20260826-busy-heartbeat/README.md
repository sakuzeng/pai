## 候选方案与确认

心跳放哪，三条路：

- 候选 A·进程级心跳，`shell._wait` 每轮调（选中）。那个轮询循环已经存在
  （`POLL_SECONDS = 0.1`，本来就是为中断响应粒度设的），而且 bash 这条路
  跑在主线程上——给它一个心跳点，TUI 接上去 poll 键盘 + 重绘即可。
  形状照 `core/interrupt.py`：进程级单例 + `current()` / `set_current()`。
  理由与那边一模一样：`@tool` 从函数签名生成 schema，给 bash 加参数就会把它
  发给模型看，工具需要的运行期上下文只能从旁路进。
- 候选 B·给 `run_agent` 加回调、穿到 `scheduler.execute`：非并行批是同步调用
  `run_one`，中间根本没有等待循环可插——真正在等的是 bash 内部那个循环。
  也就是说 B 到最后还是要落到 A 的位置，只是多穿一路参数。
- 候选 C·独立输入线程：feature 12 拍板明确不做，本轮不翻案。

不抽 `Ref[T]`（TODO「第三个可变持有者出现时抽泛型」）：那条的触发条件是
「又一个装配期烤进闭包、运行期要换的东西」，而心跳是每次现取
（`heartbeat.current()`），不进任何闭包——与 `AskerRef` / `EventSink` 不是同一类，
触发条件没有满足。差点因为「凑够三个」就去抽，如实记一句。

## 结果与总结

干活期间的键盘不再像死了：一条跑着的长命令期间打的字当场上屏。
落点是 `core/heartbeat.py`（进程级心跳，形状照 `core/interrupt.py`）+
`shell._wait` 每轮一跳 + TUI 把读键盘那段抽成 `pump_keys()` 给事件路径与心跳共用。

顺带修掉一个此前谁也没登记过的真 bug：TUI 里 `!命令` 期间按 Ctrl+C 停不下来。
raw mode 关掉了 ISIG，Ctrl+C 只是一个字节，而命令跑着的时候没有人读键盘——
那个字节要等命令自己跑完才被看见。`_interruptible` 装的 SIGINT 处理器在这条路上
也是摆设。现在心跳每 0.1 秒读一次键盘，Ctrl+C 当场生效。

测试：`1500 passed, 5 deselected`（此前 1492），新增 8 条。
两条 e2e 是先红后绿的（不是靠推理），三处注入反证各自会红。
