## 2026-08-26 · 先用测试把两个缺陷照出来

第一条按登记写：长命令期间打字，屏幕上要看得见。用 `!sleep 3` 而不是让模型调
bash——这条路不过权限框，测试短且只测一件事，而两条路在这一点上是同一段代码。

写第一条时顺带想到第二条并且被证实了：TUI 的 raw mode 关掉了 ISIG
（`tty.setraw`），Ctrl+C 只是一个字节；而命令跑着的时候没有任何人读键盘——
于是那个字节要等命令自己跑完才被看见，中断标志永远来不及置位。
也就是说 TUI 里 `!sleep 300` 按 Ctrl+C 根本停不下来。
`_interruptible` 装的 SIGINT 处理器在这条路上也是摆设（raw mode 下压根没有 SIGINT）。
这条此前谁也没登记过。

红：两条 e2e 双双失败（打的字没上屏；`sleep 8` 等它自己跑完）。

## 2026-08-26 · 实现：心跳

`core/heartbeat.py` 形状照 `core/interrupt.py`（进程级单例 + `current()` /
`set_current()`），理由也一字不差：`@tool` 从签名生成 schema，
给 bash 加参数就会把它发给模型看，运行期上下文只能从旁路进。
回调抛异常一律吞掉——心跳是界面层的便利，不是正确性的一部分，
一个渲染 bug 不该把用户正在跑的命令连坐掉。

`shell._wait` 每轮 `beat()`，位置在中断检查之前：心跳本身就是「读键盘」，
用户这一下按的可能正是 Ctrl+C，先读再判才不会白等一轮。

TUI 侧把 `on_event` 里那段读键盘抽成 `pump_keys()`，事件路径与心跳共用一份——
事件流密的时候前者够用，一条不发事件的长命令期间只有后者还在跑。

红→绿：`tests/test_heartbeat.py` 5 条（ImportError → `5 passed`），
两条 e2e（`2 passed`）。

心跳的单测里钉的是次数与间隔而不是「跳过至少一次」：
只断言「至少一次」的话，一个「命令结束后补跳一次」的实现同样能过，
而那正好是本 feature 要修的那个病。

## 2026-08-26 · 注入反证照出两处我自己写坏的地方

三处反证跑下来，两处没红——都不是测试的问题，是实现的问题：

- 「心跳里的 `app.refresh()`」拿掉之后测试照样绿。查了 `driver.poll`：
  它自己已经在该重画的时候重画了（有输入 → 处理后 refresh；无输入 →
  `needs_tick()` 为真才 tick+refresh，空闲刻意不画）。那句 refresh 是多余的，
  删掉并把这段发现写进注释——留着一句无法证明其效果的代码，比没有更糟。
- 「退出不卸载心跳」拿掉之后测试照样绿。查出两件事：其一，我那条测试第一版是
  假的——它「调一下看有没有回声」，而心跳吞异常，卸没卸载都没有回声；
  其二（更要紧），心跳装在 `term.start()` 之前，而卸载在 try 的 finally 里，
  于是 start 自己抛异常那条路上压根不会卸载。装卸不对称。

修法：心跳挪进 try（与 finally 对称），测试改成断言「退出后是那个什么都不做的
默认心跳」。测试的引爆点也跟着挪——原来炸在 `term.start()` 上，那测的就成了
「装都没装」而不是「装了没卸」。

改完三处反证：不装心跳 `2 failed`、退出不卸载 `1 failed`、
`_wait` 不跳 `3 failed`。
