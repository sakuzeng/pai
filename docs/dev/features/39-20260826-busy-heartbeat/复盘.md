# 39-busy-heartbeat · 复盘

## 学到了什么

「没有人在读」这件事会同时吃掉两样东西，而只有一样看得见。这次修的是「打的字
不上屏」，顺带才发现同一段时间里 Ctrl+C 也是失效的——两者是同一个根因
（raw mode 关了 ISIG，键盘只剩字节，而没人读字节），但前者用户会抱怨，
后者用户只会觉得「这命令怎么按不停」，然后去开另一个终端 kill。
可迁移的判据：当一段代码把某个输入通道的语义从「操作系统替你处理」换成
「我自己处理」（raw mode、非阻塞 IO、自己解析协议）时，要列一张
「操作系统本来替我做了什么」的清单逐条接管——ISIG 就是被漏掉的那一条。

第二条：一个「多写的、无害的」语句，和一个「漏写的、有害的」语句，在测试上
的表现是一样的——都不会红。本轮的 `app.refresh()` 属于前者，
`heartbeat.set_current(None)` 装错位置属于后者，两个都是靠注入反证不红照出来的。
所以反证不红时的第一反应不该是「这条测试没用」，而该是「实现和我想的不一样」。

## 哪里走了弯路，为什么

心跳装在 `term.start()` 之前、卸载在 try 的 finally 里，装卸不对称——
异常路径上永远不卸载。写的时候我的注意力全在「装在哪能被 bash 看见」，
根本没想过「谁负责卸」。这类不对称在本仓库有先例（feature 31 把 MCP 的
atexit 关闭改成单出口 finally，理由一模一样），我却没有联想过去。
可执行的教训：写下 `set_current(x)` 的同一分钟就要写下 `set_current(None)`，
并且让它们在同一个 try/finally 里对着看。

我为卸载写的第一版测试是假的：「调一下心跳看有没有回声」——而心跳的契约就是
吞掉一切异常，于是卸没卸载都没有回声。这跟 feature 37 那次假测试是同一族
（钉的东西在那条路径上根本不可观察），一周之内第二次。

## 我现在质疑什么

一、`POLL_SECONDS = 0.1` 现在承担了两个职责：中断响应粒度（原本的）与界面刷新
粒度（本轮新加的）。它们对「多快算够」的要求不一样——中断 100ms 绰绰有余，
而打字回显 100ms 已经在人能感觉到的边缘（尤其连续快打时）。现在它们共用一个数，
将来谁想调都会牵动另一个。真要分开就得给 `_wait` 两个节奏，本轮判为不值当，
但这个耦合是我制造的，记在这里。

二、心跳只覆盖了 bash 这一条阻塞路径。MCP 工具调用（默认 60s 超时）是一次性的
`event.wait(总时长)`，那段时间里键盘照样像死了——我把它登记成了遗留，
但说实话，「同一个病在第二条路径上还开着」和「这个病修好了」之间，
差别比一条 TODO 条目看起来要大。用 MCP 的人撞到的会是一模一样的体验。

三、`!命令` 期间打字现在会进 steering 队列（因为 `pump_keys` 是共用的那一份），
而在此之前那些字是留在输入行里的。我没有为这个语义变化单独立断言，
理由是「与模型调 bash 时保持一致」听起来很顺——但「听起来很顺」不是证据，
真实使用里可能有人就是想在命令跑着的时候先把下一句敲好、等命令看完再回车。
撞到再说，但记着这是我顺手改掉的。

## 下次怎么做更好

给「注入反证不红」定一条动作：不红时先假设实现有问题，去读一遍被改坏的那行
真正在做什么，而不是先怀疑测试。本轮两处都是这么找出来的，但两次我都是先想
「测试是不是白写了」——顺序反了，浪费了一轮判断。
