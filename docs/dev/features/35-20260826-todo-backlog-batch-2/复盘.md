# 35-todo-backlog-batch-2 · 复盘

## 学到了什么

「按条目描述做」与「按代码现状做」是两件事，而且差得比想象中多。本轮 15 条里，
条目描述与代码现状对不上的有 5 条：3 条早就修完了（漏勾）、1 条的修法照做会引入
新 bug（pgid）、1 条只写了一半（`surfaced` 那条漏了 `/clear`）。也就是三分之一。
可迁移的形状是：待办清单会随着代码漂移而失真，而失真的方向不止「过期」一种——
还有「修法当初想对了、后来前提变了」和「当初只看见半个问题」。所以复核的问题不该是
「这条做了没有」，而是三问：它还在吗、修法还成立吗、它是不是只写了一半。
这条够格进 knowledge/concepts（与「测试为了让被测路径跑起来而注入的参数，
正是真实路径上会卡住的地方」同族：都是记录与现实之间的漂移），但本轮没写——
见「下次怎么做更好」。

另一条：一个「只改表示层」的改动要证明自己没改语义，最省事的办法不是加测试，
是拿旧实现当参照跑一次差分。`git show HEAD:path` 一行就能把旧模块拿到手，
两份实现对同一批样本比值，4090 条样本 36810 次比对跑完不到一秒。
比「补几条边界测试」强的地方在于：它不需要我先猜到哪些边界会出问题。

## 哪里走了弯路，为什么

一处真的走错并且已经改正：我在写 TODO 销账文案时，先把「全量 1448 passed /
155.98s」写了进去——那个数字当时根本没跑过，是照着上一批的数量顺手推的。
写完下一步才意识到，回头跑了真全量（1447 / 163.16s）并改正。
为什么会这样：销账文案和测试数字在我这里被当成了同一件事的两半，而「文案要连贯」
的惯性比「数字要真实」的规矩先起作用了。AGENTS 里「数字要真实」这条规矩防的正是
这个动作，我差一点就违反了它，且不是因为懒得跑，是因为顺手。

一处思路上的弯路：`/memory reload` 我最初想的是「重新加载并当场显示新内容」，
于是开始盘算怎么把 `instructions` loader 一路穿到命令处理函数（要动六个调用点）。
写到一半才反应过来注入点本来就在每轮开头——丢掉旧消息就够了，穿参数是在给
「立即生效」这个我自己加的需求付钱。原来的需求只是「改了文件要能生效」。

一处被测试当场纠正：`--resume` 的警告我第一版没把「设置」二字写进文案，
测试红了。断言钉的是说了什么，不是有没有多打几行字——这次是测试比我先想清楚。

## 我现在质疑什么

一、AGENTS.md 那条拍板的代价，可能比问的时候说的更大。问用户时我说的代价是
「本仓库自己跑 pai 会把 26KB 塞进上下文」，但真正的代价面更宽：任何用 pai 的仓库，
它的 `AGENTS.md` 都会每轮常驻——而那份文件通常是写给「开发这个仓库的人/AI」的
（构建命令、测试规约、提交格式），与「pai 这一轮要干的活」相关性未必高。
官方（CC）至今仍不直接读它，选择让用户显式 `@` 导入，这不见得只是保守。
真正该复议的可能不是「读不读」而是「读多少」：常驻整篇 vs 只在相关时加载
（正是 TODO 里那条「路径作用域规则」）。不推翻拍板，登记成复议候选。

二、`on_context_rewritten` 这个注入回调，现在只有一个消费者（清召回去重表），
而它的名字承诺的是一件更大的事。下一个「记着自己往上下文里放过什么」的东西出现时
（skills 重挂已经是半个了，只是它搭了指令重注入的车），这个回调要么变成事件、
要么变成一串回调。我倾向于它其实应该是 `events.py` 里的一条事件
（`ContextRewritten`），loop 已经在同一位置发 `Compacted` 了——现在这样是
「装配层要一个回调」和「观测流要一个事件」各修各的。没改是因为 `/clear` 那条路
不发 `Compacted`（它发 `ConversationCleared`），合并需要先想清楚两者的关系。

三、我这次给「三条退化路径」只治了一条（判定器崩溃），理由是「另两条是常态」。
但「参数不是 dict」真的是常态吗？模型发来的 `arguments` 不是 dict 意味着它发了个
非法调用，那一轮的工具调用大概率也要失败——这个信号在别处（`_run_tool` 的解析）
会被看见，所以我判它「不必在这里喊」。这个判断没有数据支撑，只是推理。
真跑起来如果发现并发退化频繁，第一个该查的就是它。

## 下次怎么做更好

把「学到了什么」第一段那条方法论当场写成 knowledge/concepts 笔记，而不是
留一句「够格升格」。TODO 里现在躺着三条「够格升格成 knowledge/concepts 的一条
方法论笔记」（2026-08-10 一条、2026-08-19 两条），全都停在「够格」上没人动——
本轮又添一条就是第四条。它们不是没时间写，是「升格」这个动作没有触发点：
不像遗留问题有「必须同步登记 TODO」的硬规矩。
具体做法：交付前扫一遍本轮 devlog 与复盘里出现的「够格升格」字样，有就当场写，
写不出 pai 锚点就地降级成 TODO 一行说明为什么写不出——总之不留「以后再说」。
