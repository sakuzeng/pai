# 17-viz-flow 复盘

日期：2026-08-13。前置：`./test.sh` → **1069 passed, 3 deselected**，全绿。

## 学到什么

**1. 「跑一遍真数据」是与单元测试并列的一道关，不是可选的加餐。**
本轮 8 个 task，**每一个** task 在测试全绿之后跑真实数据/真浏览器，都又发现了东西：

| 时机 | 发现 |
|---|---|
| T4 测试全绿后跑 8 个真实会话 | `!命令` 的记录被全判成「未完成」——3/8 假阳性，信号退化成噪音 |
| T5 测试全绿后真起 server + 真跑一回合 | 新起 pai 换了会话文件，页面静默停更（返回 0 条） |
| T6 全套（而非单跑） | 全局工具注册表泄漏，`单跑绿、全跑红` |
| T7 浏览器里一看 | 观测流与审计流重影（10 步里 3 步是重的）、字段撞名显示成 `bash → event` |

**没有一条是离线单测能发现的**——这句话 STATUS「下一步」候选 2 里早就写过
（「13/16 两轮共打回 13 条，没有一条是离线测试能发现的」），本轮又验证一次。
差别在于：这次我在每个 task 结束时主动去跑，而不是等交付后被打回。

**2. 「加起来有意义吗」是一个该常问的问题。**
用户指出把各步 `prompt_tokens` 相加当「计费」没有意义——缓存命中便宜 50 倍，
混在一起既不是钱也不是上下文大小。这个反问逼出了三个真正有意义的量
（上下文峰值 / 未命中之和 / 输出之和），比原来的一个数信息量大得多。
**一个数能被算出来，不代表它表示什么东西。**

**3. 结构上不可能出错 > 给每个已知情况打补丁。**
字段撞名（事件自己的 `kind` 被步骤判别字段 `kind` 覆盖）的第一反应是给
`PermissionDecided` 开个特例。真修法是把载荷整体套进 `data`——下一个撞名字段
不会再中招。同类：`_dispatch_command` 的 `on_event` 改成**显式必填**参数而不是
`kw.get(...)` 默认 None，漏传当场 TypeError 而不是静默不落盘。

**4. Python 闭包按名字查、不按值查，可以刻意利用。**
`on_event = compose(on_event, trace)` 放在 `set_notifier` / `make_recall` **之后**
也照样生效——那些 lambda 在调用时才查 `on_event`。于是不需要调整语句顺序，
`MemoryWritten`/`RecallFailed` 自动进事件流。反过来 `compose(on_event, ...)`
捕获的是旧值，不会自我递归。

## 哪里走了弯路

**1. plan 认账的风险认错了方向，真风险在没认账的地方。**
plan 写「interactive 三处装配点的 session 生命周期最可能返工」。实际：session
只建一次，装配点是 2 处不是 4 处，**零返工**。而真正的坑是 plan 完全没提的
——`_run_tui` **自建** `on_event`，导致 T3 的接线在 TUI（也就是日常用法）下**完全不生效**，
且 T3 的测试全注入了 reader 走纯 REPL，照不到。
教训：认账风险时，我看的是「这段代码复杂」，该看的是「哪条路径我的测试覆盖不到」。

**2. 修 bug 时自己埋了一个更严重的。**
修 TUI 落盘时用 `kw["on_event"]` 取了个没人传的键，KeyError 把整个 TUI 打崩（屏幕全空）。
只有 pty e2e 照得到，等 8s 超时才失败。feature 15 那套假 provider + 真 pty 这次值回票价。
补救是加了一条 0.1s 的快测直接调 `_dispatch_command`。

**3. 数字写错三次。**
spec 说「其余 11 种事件全落」（实际 13）、测试 docstring 写 12、STATUS 的测试数
在几轮编辑里被覆盖回旧值。前两个由 `test_every_event_type_is_covered_by_samples`
（反射比对 events.py）抓住，第三个由 `test_status_reports_the_current_test_count` 抓住。
**机器数的数字比人数的可靠**——这两条守卫都兑现了，但也说明我手写数字时不够小心。

## 我现在质疑什么

**质疑一：`ConversationCleared` 只解决了一半问题，`--resume` 会把它撕开。**
本轮用「发一个事件、画一条分隔线」区分 `/clear` 前后，前提是「一个进程 = 一个会话文件」。
可是 `--resume`（13 引入的缺口，TODO 挂着）一旦做出来，同一个文件里会有
**跨进程的时间跳跃**——上次退出到这次续上之间隔了三天。那时候「一段对话」的定义
就不只是 `/clear` 划分的了。现在这个设计不算错，但它的假设会被下一个功能打破，
**做 `--resume` 时必须回头看这里**。

**质疑二：把观测流做成默认常开，我没有量过代价。**
每个事件一次 `open(...,"a")` + write + close。一个回合十几个事件，感觉可忽略——
但「感觉可忽略」正是 AGENTS.md 里 `perf` 那条规矩明令禁止的说法
（「没有前后数字就不是 perf」）。长会话、并发批场景下会不会有可测的影响，
我**没有数字**。而且事件文件无上限增长（已记 TODO）。
如果要认真对待，该加一个开关或至少量一次。

**质疑三：`EVENT_SRC` 手写映射的「防漂移测试」防的是存在性，不是正确性。**
测试保证「键集合 == 事件类名集合」且「文件存在」，但**指错文件它照样绿**——
比如把 `Compacted` 指到 `core/loop.py` 也能过。这条边界我在代码注释里没写清楚，
现在补上：它防的是「忘了登记」，不防「登记错了」。
后者只能靠人看，或者哪天真去抓调用栈（问 2 的候选 B，当时以「更准确却更没用」否掉了
——现在看，也许该是「两个都要」：栈给准确位置，映射给可读位置）。

**质疑四：跨项目会话列表是对的，但它顺手扩大了读取面。**
现在 viz 会列出 `~/.pai/projects/**` 下**所有项目**的会话，包括别的仓库的。
本地单人工具、只绑 127.0.0.1，这不算安全问题；但「在 A 项目开的页面能读到 B 项目的
对话内容」这件事本身值得写在明处。当时是为了解决「playground 里跑、仓库根看」
这个真实痛点，我认为取舍正确，只是**没有和用户确认过这层含义**。

## 下次怎么做更好

1. **认账风险时按「测试覆盖不到哪条路径」列，而不是按「哪段代码复杂」列。**
   本轮如果 plan 里写一句「TUI 路径的测试全走注入 reader，任何装配改动都照不到」，
   bug 1 会在动工前就被想到。
2. **每个 task 的「绿」定义为：单测绿 + 全套绿 + 真数据跑一遍。**
   本轮是自发这么做的，效果明确（8 个 task 抓出 6 个问题），值得固化成习惯。
   代价很小——真数据就在 `~/.pai` 里躺着。
3. **手写的数字一律配一条机器校验，或者干脆不写。**
   spec 里的「11 种」纯属多余：那个数字不写也不影响任何人理解设计。
4. **前端改动后必须重启 server 再验**（进程内直读的端点不会热重载）。
   这次浪费了一轮困惑。waku 的 `static/README.md` 专门写了这条，值得抄进 pai 的
   viz 说明里——已在 devlog T7 记下。
