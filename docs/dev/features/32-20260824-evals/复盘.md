# feature 32 复盘

## 学到什么

- 「fixture 就是会话日志本身」（dsh llm-replay）这条设计在 pai 身上兑现得
  异常便宜：v1 格式（24）+ `build_messages`（24）+ fake_provider（15）三块
  地基都在，派生器本体不到 50 行。基建按不变量修好，下游功能就是接线——
  E3 当时说「replay_messages 是 evals 地基」，这次是兑现的一天。
- 外部世界断言的价值在注入反证里现形：掐断 tool_calls 透传后，评测红在
  「重放没有产出 问候.txt」——如果当时断言的是 stdout 关键词，这个注入
  多半还是绿的（收尾文本照常回放）。dsh 那句「关键词探测会让作弊的 agent
  通过」不是修辞，是这次亲眼看到的分叉点。
- 评测与测试的口径隔离要在配置层做死：testpaths 不动 + 独立入口，
  STATUS 对账数字与评测互不牵连，两边的「绿」各自有明确含义。

## 哪里走了弯路

- 铸造夹具时拼隔离 HOME 用了错误的相对基准（cd 进 proj 之后 `$PWD` 已变），
  会话落进嵌套错位的目录——损失只是找文件多花两分钟，但这类脚本化真跑
  以后要先 `pwd` 锚定绝对路径再拼。已记 devlog。
- 第一版把「含 compaction 拒绝」想成可以靠 replay_messages 现成拒绝——
  读源码才发现 feature 24 已把它升级成「按条目重建不再拒收」；拒绝责任
  只能派生器自己担。教训：引用「某函数会拒绝 X」这类记忆时先查当前源码，
  行为在演进（这条本身就是 STATUS/档案里写过的升级，我引用的是旧知识）。

## 我现在质疑什么（必答）

- 回放评测测的到底是什么？脚本是从录制回合派生的，模型侧永远「答对」，
  它真正评的是 harness 在同样模型输出下的行为稳定性（工具执行、权限、
  落盘）。这更像一条高价值回归测试而不是「评测」——它与 tests/ 里 e2e 的
  边界（评测=可积累的工件+外部世界判分？）目前是靠目录与入口划的，
  概念上没有完全立住。等任务集扩起来后如果两边长得一样，该合并回 tests。
- `--dangerously-skip-permissions` 被铸造与两条评测共同依赖——评测姿态
  绕开了权限层，意味着权限相关的回归评测永远测不到。下一份夹具应该
  录一个带 allow 规则（而非 bypass）的回合。
- 工件 runs.jsonl 目前没有消费方（没有汇总器/对比器）。按「不预防性建设」
  的戒律它本该等压力再建——但没有消费方的落盘格式容易悄悄漂，schemaVersion
  字段是唯一的锚。第二个消费方出现前，这块是最可能长歪的。

## 下次怎么做更好

- 夹具铸造应当脚本化（一条命令：跑任务 → 校验产物 → 复制入库 → 写溯源），
  这次是手敲的四步；第二份夹具时先把脚本沉下来。
- 引用既有函数的拒绝/兜底行为前，先 grep 当前实现——本仓库演进快，
  「我记得它会拒绝」的记忆半衰期只有几个 feature。
