# 20-e2e-for-seams · 复盘

## 学到了什么

- 注入反证的靶子是「旧断言的盲区」，不是「历史 bug」。深破坏（把 `\n` 拆分整个拿掉）
  谁都能抓红，证明不了新断言比旧的强；只有旧断言恰好放过的浅突变
  （`trace=None`、1 格缩进的浅阶梯）才能当场演示「旧的绿、新的红」。
  这条换个项目照样成立：给断言做反证，先问「旧的会放过什么形态」，再注入那个形态。
- 断言的期望值锚到源头文本（`interactive.HELP` 常量、测试自己的 `answer` 变量），
  不硬编码魔法数——「阶梯」的定义因此从「缩进小于 12」变成「屏幕缩进 ≠ 源头缩进」，
  定义对了，断言自然严。
- getsource 换行为断言有个通用手法：把装配的终点换成间谍（monkeypatch 入口函数或
  构造器），真跑一次装配路径，断言「递到手里的对象」。间谍挡在贵的那层（pty、网络）
  前面，测试还是快的。
- 「逐步换成行为断言」不该读成「全部换掉」：证无（符号缺席）、钉注释、字面量 lint
  这三类的对象就是源码文本，扫源码不是妥协而是唯一手段——裁决写进 docstring，
  下一个见到 `getsource` 的人不用再判一遍。

## 哪里走了弯路，为什么

- 第一发注入反证选了深破坏（`theme.wrap` 不拆 `\n`），红是红了，但红在
  `StopIteration`（标记行整块找不到）——这种破坏旧断言也抓得住，等于什么都没证明。
  当时为什么会那么想：顺着「历史上的原病」去注入，默认「复现原 bug 就是最好的反证」。
  但原病正是旧断言（写歪了的那版）想抓的东西，它的盲区在别处。回头补了浅阶梯注入才算证成。
- 注入后跑测试，拍脑袋写了个错误的测试类名，得到 `no tests ran`——差点把「没跑」
  当成「红了」。注入反证的判据必须是「跑了且红在预期的那行断言」，缺一样都不算数。

## 我现在质疑什么

- 队列间谍测试断言 `built == ["all"]`（恰好一条）。若未来合法地需要第二条队列
  （比如 followUp 复活），这条会红。我认为这是想要的——它逼改动者回到 18 号档案的
  拍板记录——但也可能被下一个人当成误伤直接放宽。docstring 里已写明拍板出处，赌它够用。
- viz 路由测试对 `/api/structure` 的真实 GET 每次起子进程跑 collect，是五个端点里
  最贵的一个。本文件全量 30 条约 15s，可接受，但若将来端点变多，这条会是第一个该
  换成「只打 HEAD 级探测」的候选。
- STATUS 的「1182 passed」口径实际是 collected：今天真实输出是
  `1181 passed, 1 skipped`（skip 是 R4#26 已登记的 Pillow 缺失那条）。
  对账测试认 collected，账是平的，但「passed」这个词与事实差 1——不另立新账，
  等 R4#26 修掉自然归位。
- 第 1 条（2026-08-19 做的）漏写了档案 devlog，本轮补记——「一步一条不攒着」
  在跨会话接力时最容易断，机器只校验「交付时复盘存在」，校验不了中途的账。

## 下次怎么做更好

注入反证动手前先写下「预期红在哪一行断言、报错长什么样」，跑完对着核——
红错了位置（本轮的 `StopIteration`）就当没证成，回去换注入点。
