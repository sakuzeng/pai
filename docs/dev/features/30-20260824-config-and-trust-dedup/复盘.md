# 30 · 复盘（四问）

## 学到什么

- 「合并阈值」写进 docstring 真的有用：feature 13 当年拒绝合并时留下的
  「等第三个读者出现时再合并」不是敷衍——它把「现在不做」变成了带触发条件的
  决定，这次优化检查一眼就判断出条件命中（而且翻倍）。拒绝做某事时写下
  「什么时候该做」，比单纯拒绝多值一倍。
- 文案参数化是 refactor 保行为的便宜手段：信任门禁两侧文案不同（skills 讲
  目录、mcp 讲子进程），把机制抽走、文案整段作参数传回，两侧输出逐字不变，
  208 条既有测试一条断言没改。比「顺手统一文案」克制——统一文案是行为变化，
  要走 feat/fix 不是 refactor。
- 消费方保留领域解析、原语只管读盘，是这次风险可控的关键：权限求值链、
  hooks 校验、mcpServers 白名单一行没动，改的只有 IO 入口。

## 哪里走了弯路

- 原语初版在函数体里塞了句无用的 `from typing import Tuple` 占位（写注释
  写岔了手），提交前清掉——小事，但说明「边写边想」的代码要过一遍再跑测试。
- 全量套件在 STATUS 数字更新前就挂了后台，数字对账测试有竞态红的风险
  （更新落在它执行前就绿、落在后就红重跑一轮）——正确顺序是先改 STATUS
  再挂全量，这次记住。

## 我现在质疑什么

- 质疑 warn 文案统一的边界：权限层坏 JSON 的告警从「权限设置…本层规则按空
  处理」变成中性的「设置文件…本层按空处理」，严格说用户可见输出变了——
  refactor 判据打了个小折（devlog 如实记了）。辩护是：没有任何测试或文档
  依赖旧文案，且新文案对四种消费者都成立。若较真，未来可以让原语接受
  可选的语境前缀，但为一条告警加参数不值。
- 质疑 project_trust_gate 的参数个数（7 个具名参数）：机制通用化的代价是
  签名变宽。第三个消费者出现时若参数继续膨胀，该改成 TrustTexts dataclass；
  现在两个消费者，先不动。

## 下次怎么做更好

- 「先改 STATUS 数字再挂全量」写进肌肉记忆（本会话第三次撞数字对账，
  前两次靠护栏，这次靠预判——预判成本更低）。
- 拒绝一个 refactor 时照 feature 13 的样子留触发条件，别只说「不值得」。
