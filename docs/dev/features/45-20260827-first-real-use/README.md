## 需求

用户 2026-08-27 问「还有什么可以优化的呢」。盘点后我给出的最大一条不是代码：

feature 41～44 连着四轮加的能力（`read_file` 的 offset、`search_files`、
`run_tests`、`git_read`、`edit_file` 的 `near_line`、diff 回执、markdown 渲染），
需求全部是**我自己从代码里推断的**——用户给的是方向，具体缺什么由我判断。
而 feature 38 留下的 `evidence/手工清单.md` 六节，末尾原话是
「本清单尚未被人跑过」。也就是说 pai 到今天为止没有被人真正用来干过一件活，
而我在优化一个我没见过它被使用的东西。

用户选了「先真用一次」。

范围切分（这一条必须写在前面，否则交付时会假装跑全了）：

- **我能跑的**：真模型 + 真 pty + 真任务。覆盖工具链路、权限、TUI 渲染、
  压缩、会话落盘。
- **只有真人能跑的**：中文 IME、鼠标拖选、resize、颜色主题、不同终端
  emulator 的差异。我没有这些，跑不了就是跑不了——交付时给用户一份收紧过的
  清单，不假装自动化了。

验收标准：

1. 至少三件**真任务**（查一处实现 / 改一个函数 / 加一条测试）在真模型上跑完，
   每一处摩擦当场记下来，不事后回忆。
2. 发现要分级：真 bug / 体验摩擦 / 我的推断被证伪。第三类最要紧——
   它直接说明前四轮哪里做错了。
3. 本轮不修任何发现（除非是会让后续观察失真的阻断性 bug，且要写明为什么破例）。
4. 手工清单那半交付一份收紧过的、可勾选的版本给用户。

## 结果与总结

跑了。四次真运行（真 pai 进程 + 真 pty 100×40 + 真模型 deepseek-v4-flash +
真仓库/仓库副本），三件真活，一次 A/B 实验。累计约 20 万 token。
完整记录见 [evidence/发现清单.md](evidence/发现清单.md)；
只有真人能跑的那半收紧成 [evidence/手工清单-收紧版.md](evidence/手工清单-收紧版.md)
交给用户。夹具在 `pai_playground/real_run/drive.py`（已 gitignore）。

**最重要的一条是证伪**：feature 41～44 四轮工具建设的收益被提示层卡住了。
`build_system_prompt` 生成的整份系统提示里只有**一句**工具引导，
而它是给 `edit_file` 的；`search_files` / `run_tests` / `git_read` 一句都没有。
而模型**确实听了那唯一一句**（两次精确替换，用得对，连 docstring 都如实更新）。

A/B 实验（副本里加三句引导，跑同一个问题）：bash 调用 4 → 3，权限弹窗 4 → 3。
单独验 `run_tests`：对照组里任务明说「跑测试」而它零次被选中、走 bash、
7 次弹窗、烧完预算没做完；实验组 **1 次调用、0 弹窗、9 秒完成**，
尾部判决 `26 passed` 完整保留。

也就是说：工具本身是对的（一旦被选中，效果就是设计时想要的样子），
错的是我一直在加工具而没有同时告诉模型什么时候用它们。

第二条证伪：「把活从 bash 摘出来」只摘走了一半，剩下的三次 bash **有结构性原因**，
不是模型不听话——没有工具能回答「这个项目长什么样」（`pwd && ls` 是必然开场），
且 `search_files` 不接受单个文件当搜索根（当场验过报错）。

验收标准四条的对账：

1. 三件真任务 —— 做了（查实现 / 改函数+加测试 / 跑测试），每处摩擦当场记录。
2. 发现分级 —— 分了四档：A 证伪 2 条、B 真缺陷 3 条、C 摩擦 4 条、D 正面确认 5 条。
3. 本轮不修 —— 一条没修。副本里的实验改动随副本一起丢弃。
4. 手工清单交付 —— 收紧版六节，每条给出「看到什么算过 / 什么算不过」，并按
   「撞上的概率 × 撞上有多难受」重排。
