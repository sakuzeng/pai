# 45-first-real-use · 复盘

## 学到了什么

**加工具和让工具被用上，是两件事，而我四轮只做了前一件。**

feature 41～44 我每一轮都做了拍板、TDD、注入反证、真跑冒烟，
每一轮交付时我都相信自己在「让 pai 能用」。但那些冒烟全是我**直接调函数**
验的——`run_tests(filter="exec")`、`git_read("log", …)`、`render(sample, 40)`。
我从来没有验过「模型会不会自己想到调它」。
而真跑第一次就给出了答案：任务明说「跑测试」，`run_tests` 零次被选中。

这个盲区的形状很清楚：我把工具当成了**能力**（存在即有用），
而对模型来说工具是**选项**（要在十个里挑一个）。
验能力用单测，验选项只能用真模型。这两件事我此前一直混在一起。

第二条：**一句提示的杠杆比一个工具大**。`edit_file` 那句引导是 feature 22
顺手写的一行，而它是整份提示里唯一被模型听进去的工具指导；
我为 `run_tests` 写了 19 条测试、一个 settings 键、一条装配接线测试，
换来的是零次调用。三行提示 vs 三百行实现，收益差了一个数量级。
以后加工具时，「怎么让模型知道该用它」应该和「工具怎么写」一起进拍板问题。

第三条，关于 A/B。我本可以就停在「模型不用新工具」这个观察上，写进 TODO 收工。
花十几秒多跑一次实验组，得到的是一个**可证伪的因果结论**：
加引导 → run_tests 被选中 → 0 弹窗 9 秒完成。
观察告诉我「有问题」，实验告诉我「问题在哪、改了会怎样」——
而下一轮该做什么，只有后者答得上。

## 哪里走了弯路，为什么

第一次真跑我没有自动应答权限框，于是进程在弹窗上等了整整 4 分钟，
超时退出，我只拿到一屏「正在等你回答」。那 4 分钟纯属浪费，
但它意外地成了 C2 那条发现（计时器把等人的时间算进了「用时」）——
如果我一开始就自动应答，这条永远不会被看见。

不算真的弯路，但值得记：**观察类任务里，"跑错了"的那一次往往也是有信息的**，
前提是你去读它而不是直接重跑。

## 我现在质疑什么

一、这次真跑的仍然不是「真实使用」，是**我扮演用户跑的自动化脚本**。
我自动应答了每一个权限框（一律选「允许这次」），而真实用户会犹豫、会拒绝、
会去看那条命令到底要干什么——C1 那条「弹窗文案是内部术语」的严重程度，
我其实判断不了，因为我根本没读那些文案就按了 1。
真正的第一次使用还没发生，只是从「零次」变成了「半次」。

二、我把 A1 的结论写成了「瓶颈在提示层」，但 A/B 的数字其实没那么漂亮：
bash 调用 4 → 3，只降了一次。`run_tests` 那条对比很戏剧（0 次 → 1 次搞定），
但那是我**专门挑了一个只需要 run_tests 的任务**去验的。
真实任务里工具选择是混合的，而混合场景下引导只帮了一点点。
我在结论里让 run_tests 那个漂亮数字盖过了整体那个平淡数字——这是选择性引用。
真实的说法应该是：引导对「有专用工具且意图明确」的场景很有效，
对「探路型」步骤基本没用，而探路型步骤占了剩余 bash 调用的三分之二。

三、我一条都没修，这是拍板时说好的。但发现清单里 B1（英文单词被劈开）
是我自己在 44 复盘里承认过的欠账，也就是说它已经被我推迟过一轮了。
「本轮只观察」在这里既是纪律，也是我第二次不修它的理由。

## 下次怎么做更好

加工具的拍板问题里固定加一问：**「模型怎么知道该用它？」**
候选至少两个（写进 system prompt 的引导句 / 只靠工具描述），
并且交付验收里要有一条「真模型会选它」——哪怕只是一次十几秒的真跑。
这一条比我此前所有的单测都更接近「这个功能有用吗」。
