# 53-four-frictions · 复盘

## 学到了什么

**改文案会让一批测试变成空断言，而它们不会变红。** 这轮把「持久化位点」换成人话，
`test_boundary` 里有一条 `assert "持久化位点" not in d_exec.reason`——文案改掉后它永远成立，
测试照绿，可它本来是要钉住「EXEC 的理由不能是危险写那句」。全靠我改 `in` 的时候顺手看见了
旁边的 `not in`。可复用的一条：**改一个字符串常量时，`grep` 它的所有出现，
`not in` 那些比 `in` 那些更危险**——前者失效是静默的。

第二条：判据跟着文案走是对的，但要改成「说没说清那件事」而不是「换一个词继续匹配」。
这轮五条既有测试改完之后，断言的是「有没有路径」「有没有说关不掉」「有没有说出后果」，
比原来的「术语在不在」更难被下一次改文案破坏。

第三条：`45-C3` 那条的真正价值不是把 20 万改成 50 万，而是发现「再说一句就接着做」这件事
**一直成立但从没说过**。`spent_tokens` 是 `run_agent` 的局部变量，REPL 下一轮天然重新计数；
用户 2026-09-10 撞顶时以为活儿断了。改默认值只是缓解，说出来才是修复。

## 哪里走了弯路

- 预算的两条测试第一版都错在同一处：忘了预算检查在「发下一次请求之前」（D#22 自己定的），
  于是 `max_total_tokens=1` 在第一步根本不触发。我写测试时想的是「上限设成 1 肯定超」，
  没想「什么时候检查」。
- footer 的 `~` 断言忘了 conftest 把 `$HOME` 隔离了——写死 `/Users/sakuzeng/...` 在测试里
  不是家目录。这是测试环境与真实环境的差异，第三次栽在这上面（前两次在 memory 与 paths）。

## 我现在质疑什么

- `run_agent` 为了一句话的措辞多了个 `interactive` 参数。loop 的签名里混进一个纯展示用的开关，
  形状不好看；更干净的是让调用方传收尾语，或者把「怎么收尾」整个交给 modes 层。
- 50 万同样没有依据。比 20 万宽，但「一个中等任务要烧多少」我只有 131820 这一个数据点。
  这是第十个「看着顺眼就定了」的常数（前九个在 41～47 那几轮）。
- 权限文案这轮按「说清三件事」验收，而它到底好不好用我判不了——45 那次我自动应答了每个弹窗、
  根本没读文案。这条遗留从 45 带到 53 还没消。
- 等人计时只在 TUI 暂停。纯 REPL 没有 dock 也没有计时显示，所以现在不漏；哪天给 REPL 加计时，
  这个洞会自己出现，而不会有测试变红。
- 四条塞进一次交付是对的吗？它们互不相干，合起来只是「同一批发现」。好处是一次跑全量、
  一份档案；坏处是 devlog 里四件事的红绿混在一起，将来 blame 一条要先分辨。
  下次同类批量修，或许该一条一个提交、一份档案。

## 下次怎么做更好

- 改字符串常量前先 `grep` 它的全部出现，特别看 `not in` 的断言。
- 写「触发某个熔断」的测试之前，先回去看那个熔断在哪一步检查。
- 批量修（多条无关的小修）时，提交按条切，档案仍合成一份。
