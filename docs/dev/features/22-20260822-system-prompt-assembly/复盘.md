# 22-system-prompt-assembly · 复盘

## 学到了什么

- 「内容断言全真 ≠ 接线成立」再次出现：once 的三条内容断言（含 bash、
  不含 ask_user_question）对旧常量恰好也全真，必须补一条判别断言
  （`system != SYSTEM_PROMPT`）才逼出装配接线。与 feature 20 阶梯断言
  「先跑真实形态再写断言」同族：写断言前先问「旧行为下它是不是也绿」。
- 装配缝的第三个入口最容易漏：`_run_shell` 在「首个动作是 `!命令`」时建
  system 消息——不接线的话那条路建出常量，且 messages 非空后整个会话再也
  换不掉。找全入口的办法是 grep 谁在建 `role: system`，不是只看主路径。

## 哪里走了弯路，为什么

没有实质弯路。值得记的是省掉的弯路：用户一句「参照 CC」把原本要在
A/B 之间猜的取舍（字符串参数 vs builder 回调）变成了检索题——CC 的
getSystemPrompt 由调用方算好传给 query，B 的「单一事实源」优势在
「装配层本来就持有 tools」面前不成立。

## 我现在质疑什么

- 生成的 prompt 丢掉了旧常量里的每工具一句描述（「bash（跑命令）」），
  理由是 schema 走 API——但 DeepSeek 对 prompt 里有无工具概述的敏感度
  没实测过，若真实使用发现模型选工具变差，该回来加一层可选描述段。
- `_run_turn` 每轮都重新生成 prompt（结果逐字相同所以无害），但「无害」
  依赖「生成是纯函数且工具集轮间不变」——将来若工具集会话中途变化
  （MCP 连接/断开），messages[0] 不会跟着变，这正是 CC 用
  DANGEROUS_uncachedSystemPromptSection 单独处理 MCP 段的原因。E4 立项时要回来看。

## 下次怎么做更好

装配类改动先列「谁在建这个东西」的完整清单（grep 构造点）再动手，
本轮 `_run_shell` 是靠既有 `_system_prompt()` 函数注释才想起来的。
