## 六个探针与结论

| 文件 | 问的问题 | 实测结果 |
|---|---|---|
| `A_no_stream_options.jsonl` | `stream=True` 但不传 `stream_options`，有没有 usage？ | 有。43 块，usage 在末块（`finish_reason=stop`、choices 非空）。`prompt_cache_hit_tokens` / `reasoning_tokens` 全在 |
| `B_parallel_tool_calls.jsonl` | 并行 tool_calls 的 chunk 序列形状 | 76 块。2 个并行调用串行分片（index=0 先完整发完才轮到 index=1）；`id`+`name` 只在该 index 的首块，`arguments` 逐字符分片（`{` / `"` / `city` / …）；`finish_reason=tool_calls` 与 usage 同在末块。usage 只有一份 |
| `C_non_streaming.jsonl` | 同一请求不流式的对照组 | 同样 2 个 tool_calls、同样一份 usage。流式与非流式在「一次响应一份 usage」这点上没有差别 |

## 三条与预期不符的

1. `stream_options.include_usage` 在 DeepSeek 上是空操作（D vs E vs A 三方对照）。
   官方文档（`refs/deepseek-api/api/create-completion.md`）写的是「设为 true 时在 `[DONE]` 之前
   传输一个额外的块，此块 usage 有值而 choices 始终是一个空数组」。实测：传不传、传
   true 还是 false，usage 都在带 `finish_reason` 的末块上，choices 从来不为空，
   也从来没有那个额外块。
   踩法：按 OpenAI 惯用写法 `if not chunk.choices: usage = chunk.usage` 组装，
   在 DeepSeek 上这个分支永不触发，usage 静默丢失 → 预算熔断与锚点一起哑掉。
2. CC 那条「并行工具调用 usage 重复累加」不适用于 pai（B + C）。
   CC 的成因是 Anthropic 协议下每个 content block 变成一条独立 assistant 记录、共享同一个
   `message.id`（`src/utils/tokens.ts` 的 `getAssistantMessageId` 就是为此存在）。
   OpenAI 兼容协议下一次响应只有一份 usage，与并行几个工具无关。
   见 TODO P3 那条「接流式前必修」——前提需要重写。
3. `arguments` 是逐字符分片的（B）。`{"city": "北京"}` 这 16 个字符分了 9 块发。
   任何「拿到 tool_calls delta 就 `json.loads`」的写法必炸；必须按 `index` 累积到
   `finish_reason` 出现才解析。

## 花费

5 次真实请求，prompt 合计约 1.5K token、completion 合计约 0.6K token。按 v4-flash 单价
不到 1 分钱。C 那次命中缓存 384 token（与 B 同 prompt），顺带证实缓存字段在流式与非流式下
口径一致。
