# 11-streaming · 复盘

## 学到了什么

**「文档读全了」和「知道它怎么跑」是两件事，而且差距不是边角。**
这次前置精读把 CC 的 `StreamingToolExecutor`、`Tool.ts` 的能力标志、DeepSeek 的
`stream_options` 全读了，然后真打了 5 次请求——**三条结论里有两条与文档相反**：
`include_usage` 是空操作、文档说的「choices 为空的额外块」根本不存在。
按文档写出来的代码会让 usage 静默丢失，而 usage 正是预算熔断与上下文锚点的唯一输入。
这条已沉淀成 [K concepts/streaming-tool-calls.md](../../../../knowledge/concepts/streaming-tool-calls.md)。

**「必修前置」也可能是抄错的前提。**
TODO 里挂了半年的「接流式前必修：并行工具调用会让 usage 重复累加」，来源是 CC 的一句注释。
真相是：那是 **Anthropic 协议下「一个 content block 一条 assistant 记录」的后果**，
不是流式的固有属性。pai 走 OpenAI 协议，一次响应就一份 usage。
更有价值的是它反过来给出的判据——**问「一次 API 响应在我的数据结构里变成了几条记录」**：
一条就没这个问题，多条就需要同源识别。**这是自己的建模选择决定的，不是协议强加的。**

**把论证的前提钉进代码，而不是留在文档里。**
本轮「权限按批前置是安全的」这条论证，依赖「并发批里全是只读工具」。
所以调度器要求**两个标志都为真**才并发——而不是只看 `concurrency_safe`。
不这么写的话，将来加一个「并发安全但会写」的工具，那条论证会**静默失效**，
而文档里的推理还躺在那儿看着像成立的。

## 哪里走了弯路，为什么

**我在拿到探针结果之前，就把一个推论当结论讲给用户了。**
我说「流式下 usage 默认根本不返回，必须传 `stream_options`」——那是从 OpenAI 协议推的，
实测正好相反。当时为什么会那么讲：因为那个推论**同时解释了**所有已知事实
（文档这么写、OpenAI 确实这么做、pai 从没跑过流式），自洽感很强。
自洽不是证据。**代价其实很小**（下一条消息就纠正了），但如果当时没做反向对照，
它会被写进 spec，变成「必须传 include_usage」这条永远不会被质疑的多余代码。

**Task 2 的一条测试红得莫名其妙，根因是我自己编了夹具数字。**
`test_side_queries_stay_non_streaming` 要断言「第 3 次 create 是摘要请求」，
我随手编了组 usage 数字，结果压缩没在那一步触发。
旁边就有一条现成的测试，注释写着「850 而非看起来够用的 700」——**那组数是被调过的**。
教训：抄场景就要连数字一起抄，夹具里的数字往往是有人踩过坑才定下来的。

**Task 6 我先写了实现再补测试**，违反 AGENTS.md 的硬规矩。
当时的心理过程是「echo 这么简单，写出来比描述快」——这正是那条规矩防的东西。
补救做了注入反证（两条注入各打红对应的一条），证明测试有鉴别力；
但**红阶段真正的价值是「先想清楚契约」**，那部分丢了就是丢了，没找补回来。

## 我现在质疑什么

**质疑一：`MAX_TOOL_WORKERS = 8` 和它旁边那段注释，可能是「合规的形式」而不是有用的东西。**
我按 TODO 那条「给照抄来的常数建一条检查习惯」，在常量旁写清了「这个数从哪来、
依赖什么前提」。但说实话——pai 目前**唯一**的并发安全工具是 `read_file`，
模型一轮最多发过 3 个，8 这个上限**在可预见的未来永远不会被触及**。
写一段严肃的注释去解释一个不会生效的常量，是不是把「留痕」做成了仪式？
更诚实的做法也许是直接写「暂时不限并发，等真撞上再加上限」。**倾向于下次遇到时选后者。**

**质疑二：「所有事件都在主线程发」这个决定，把并发的可观测性弄没了。**
理由是对的（不给 modes 层强加线程安全要求）。但后果是：并发批的 `ToolStart` 在派发**之前**
一次性发出、`ToolEnd` 按原顺序发出——于是屏幕上看不出「谁先跑完」，
甚至看不出并发到底有没有真的发生。
**用户唯一能感知到并发的方式，是总时间变短了**。这对一个学习驱动的项目是个损失：
做了并发却看不见并发。也许该加一个只在事件里带时间戳的轻量做法，而不是改线程模型。

**质疑三：流式默认开、不加开关，我当时给的推荐可能低估了 `once` 的用法。**
拍板时我说「YAGNI，流式是严格更好的体验」。但 `once` 是**给脚本用的模式**——
`pai "..." > out.txt` 这种用法下，逐字写和一次性写的区别是：输出里现在多了
`🤖 ` 前缀和空行，且 stdout 被写了很多次。测试里那条既有断言被改期望值，
就是这个变化的第一个信号，我当时把它当成「预期内的代价」轻轻放过了。
**如果 pai 将来要被别的程序调用，这里迟早要回来。**

**质疑四：中断掐在流中途时丢弃半条 assistant 消息，用户体验上是自相矛盾的。**
屏幕上明明打出了半截答案，上下文里却没有——下一轮问「你刚说的那个」它会不知道。
我给的理由（没有 usage、token 数无从得知）是**实现视角**的；
从用户视角看，「看得见的东西不算数」才是那个奇怪的地方。
可以考虑追加时按估算记 token（反正锚点本来就允许估算段），值得复议。

## 下次怎么做更好

**把「反向对照」从这一轮的特例变成路线图阶段的固定动作。**
本轮它是用户在开工指令里点名要求的（带着 feature 09 的教训），结果一次就撞出三条
文档读不出来的事实，其中一条直接决定了核心代码怎么写。
具体做法：在 `roadmap.md` 的「前置精读」清单下面加一行固定项——
**「反向对照：拿 N 个真实场景跑一遍，把与文档不符的地方记进 evidence」**，
和「前置精读」一样是勾选项。这比「记得要验证」这种自我提醒可执行得多。
