# 36-path-scoped-instructions · 复盘

## 学到了什么

「同一个相对路径，在两层里有两个基准」是个能骗过一整批测试的坑。本轮那个真 bug
（`_relative` 拿项目根去拼模型给的相对路径）之所以七条测试全绿，是因为测试都在
项目根下跑——cwd 与项目根恰好是同一个目录，两个基准重合，错的代码给出对的答案。
只有当我为了另一个原因去想「子目录启动会怎样」时它才现形。
可迁移的形状：只要一段代码把路径在两个坐标系之间搬运（cwd 相对 / 项目根相对 /
绝对），就必须有一条测试让这两个坐标系不相等，否则那批测试证明不了任何东西。
这与 pai 已有的两条方法论是同族（「测试为了让被测路径跑起来而注入的参数，
正是真实路径上会卡住的地方」、「基准为了让被测代码生效而注入的到达形态，
恰是真实路径上不会出现的」）——这次是「测试环境恰好让两个本该不同的值相等」。

第二条：`fnmatch` 对路径 glob 是错的（它的 `*` 跨 `/`），而这个错在单元测试里
极难被注意到——`*.md` 匹配 `docs/a.md` 看起来「也挺合理」。选标准库函数之前
要先问它的语义边界是什么，而不是它的名字听起来像不像。

## 哪里走了弯路，为什么

Task 3 没做到先红后绿：`select_and_render` 和 Task 1/2 在同一个模块里一次写完了，
于是它的测试是绿于到达的。原因很具体——我按「文件」而不是按「task」组织了动作，
写 `rules.py` 时顺手把整个模块补完整了，而 plan 里它们是三个 task。
补救做了（五次注入反证逐条证明测试会红），但补救不等于没走弯路：
如果那五次里有一次没红，我已经写下去的实现就得回头改，成本比先写测试高。

一处判断上的弯路：我一开始想让规则目录也支持「不带 paths = 常驻」（照官方），
写 spec 写到一半才反应过来这与本需求的收益命题直接相反——降低常驻成本的功能里
再开一条常驻通道。这个反应来得算及时（还没动代码），但它说明我当时是在
「对齐官方」的惯性里做事，而需求池那条登记明明白白写着「用户要的是在 pai 上做，
不是对齐官方」。决定性细节写在需求里了，我还是差点漏掉。

## 我现在质疑什么

一、`MAX_RULES_PER_STEP = 3` 这个上限可能是错的形状。它按「条数」截断，
而真正该管的是 token。三条各 3000 字符的规则比五条各 200 字符的贵得多，
但现在前者放行、后者被截。当初选条数是因为它简单可测；正确的做法大概是按
累计字符数截（与 skills 的总预算同款），而 `MAX_RULE_CHARS` 已经把单篇管住了，
再加一个总额就够，条数上限反而是多余的。没改是因为改它要重新想「超了之后
先丢谁」，而本轮没有真实数据说明哪种截断更常触发。

二、`on_context_rewritten` 现在有两个消费者了（召回去重表 + 规则注入表），
35 复盘质疑二说的「它可能该是一条事件而不是回调」证据更足了。但我这轮还是没改——
理由是「两个还不构成模式，第三个再抽」（与 34 复盘质疑一那条 `Ref[T]` 同一套说辞）。
我现在怀疑这套说辞被我用得太顺手了：它对「抽象形状还看不清」的情况成立，
但这里的形状是清楚的（loop 已经在同一位置发 `Compacted`），拖着的真实成本是
每加一个消费者就要多穿一遍参数——本轮就穿了六个调用点。

三、「触发面含写/编辑」这条偏离官方的选择没有证据。我给的理由是「一条
`src/**/*.py` 的规则在改这个文件时同样该生效」，听起来合理，但官方只在读时触发
可能有它的道理（写之前通常先读过，重复触发是浪费）。真跑起来如果发现规则总是
被 write_file 触发而那时模型已经读过一遍了，这条就该收回。

## 下次怎么做更好

按 task 而不是按文件组织动作：写完 Task N 的测试就停下跑一次红，再写 Task N 的
实现，哪怕这意味着同一个文件要打开三次。本轮 Task 3 的绿于到达就是因为
「反正在同一个文件里，顺手写完」——而 plan 之所以把它拆成三个 task，
正是因为它们各自有独立的验收。具体做法：plan 里的每个 task 开头先写一行
「本 task 的红长什么样」，写不出来就说明这个 task 拆错了。
