## 需求

出处：[需求池](../../需求池.md)「待评估」2026-08-19 条，用户原话（不转述）：

*"子目录指令懒加载、路径作用域规则（对应官方 .claude/rules/ 的 paths: frontmatter）。
这个我想之后在pai 上做，写入todo或者需求池"*

2026-08-26 用户在「阶段 1-7 全部交付后下一程接哪件」里选了这一条，正式升格立项。

两条是一件事：触发点都是「模型读到某个文件时」，分开做会把同一条管线铺两遍。

官方行为（2026-08-19 查官方 memory 文档核实，笔记
[K memory/claude-memory.md](../../../../knowledge/memory/claude-memory.md) 第二节）：

- 子目录里的 `CLAUDE.md` / `CLAUDE.local.md` 启动时不加载，等读到该目录下的文件才注入；
- `.claude/rules/*.md` 带 `paths:` frontmatter（glob）的只在读到匹配文件时加载，
  不带 `paths` 的与 `.claude/CLAUDE.md` 同优先级、启动即加载；
- 压缩之后，项目根 `CLAUDE.md` 会重注入，而嵌套的与 path-scoped 的不会，
  它们等下次读到对应文件时再回来。

需求池里已经写死的两处决定性细节，评估时不许丢：

1. 用户要的是「在 pai 上做」，不是「对齐官方」——所以官方第三条那个取舍
   （压缩后不重注入）可以不抄；pai 现在对指令是全部从磁盘重读（D#42），
   嵌套的走哪条要先决定。
2. 真正的收益在路径作用域那条，不在懒加载：常驻层是 pai 四家对照里最薄的一环
   （PAI-04 诚实边界），而 `paths:` 正是官方用来降低常驻成本的机制。
   懒加载单独看收益存疑（pai 典型用法是单仓单目录），它更像 `paths:` 的副产品。

补一条 2026-08-26 才有的背景：本轮 feature 35 把 `AGENTS.md` 纳入了指令发现
（D#43 复议），常驻成本因此又涨了一档——[35 复盘质疑一](../35-20260826-todo-backlog-batch-2/复盘.md)
提的正是「该读多少」，与本需求是同一个问题的两面。

验收标准（怎么算做完）：待 spec 定稿时写死。方向上至少要有：
带 `paths:` 的规则文件在读到匹配文件之前一个字都不进上下文（反向守卫）、
读到之后进得去、压缩之后按拍板的那条路处理、已注入过的不重复注入。

## 候选方案与确认

三个必答问题来自需求池那条登记，逐问给候选。拍板问答原样存档。

### 问 1：「模型读到了某个文件」这件事在哪儿被看见（挂点）

- 候选 A·loop 的工具结果回填处：loop 在 ③ 那一步已经手握本轮每个 tool_call 的
  `args`，新增一个注入回调（形状同 `instructions` / `recall` / `on_context_rewritten`），
  装配层把它接到 memory 侧。好处是一处覆盖全部工具、loop 仍不认识记忆；
  代价是 loop 要多认一个概念（「这一批碰了哪些路径」）。
- 候选 B·fs 工具内部上报：`read_file` / `write_file` / `edit_file` 各自调一个
  模块级收集器（形状同 `memory_tool.set_notifier`），loop 一行不改。
  代价是每加一个碰路径的工具就要记得上报——与 07 复盘质疑二点名的
  「按参数语义挂匹配器可能比按工具挂更对」是同一个坑，会静默漏。
- 候选 C·权限层 gate：`before_tool_call` 已经对所有声明了路径语义的工具算过
  `get_paths_for_permission_check`，一处就能拿到全部路径且不会漏新工具。
  代价是语义偏了——它是「被判定时」而不是「被读到时」，连被拒绝的调用也会触发注入。

三个候选都有同一条边界：`bash` 里的 `cat` 不算「读到」（bash 不声明路径语义，
与 D#52「bash 不参与目录边界判定」是同一条判据）。这条边界要写进 spec 而不是留给实现。

### 问 2：注入时机与压缩锚点簿怎么共存

- 候选 A·当作第二个召回块：在下一轮开头以一条 user 消息注入（走 `_extend`），
  与召回块同款；锚点簿本来就允许消息在轮与轮之间增长，不需要动它。
  压缩之后靠本轮刚建好的 `on_context_rewritten` 清「已注入过」表 →
  下次读到同一个文件时重新注入。与 D#42「指令全部从磁盘重读」方向一致，
  官方那条「嵌套的不重注入」不抄。
- 候选 B·并进那条指令消息：把 path-scoped 段拼进 `INSTRUCTION_HEADER` 那条消息。
  上下文里只有一条指令消息，看起来最干净；代价是那条消息位于 messages 中间，
  改它的内容会让已落盘的 entry 与内存里的不一致（feature 23 的「模型可见即已记录」
  不变量正卡在这里），要么每次改都补一条新条目，要么破一次不变量。
- 候选 C·抄官方：压缩后不重注入 path-scoped 的，等下次读到再回来。
  最省 token，但与 pai 现在「指令全部从磁盘重读」的做法不一致，
  且会造出一种沉默的失效（压缩后模型看不见规则、而它以为自己看过）。

### 问 3：本轮做几条

- 候选 A·只做路径作用域规则（`.pai/rules/*.md` 的 `paths:`），子目录懒加载不做：
  需求池自己判过「真正的收益在前者，后者是副产品」。范围最小，一条管线一次做透。
- 候选 B·两条一起做：管线本来就是同一条，`paths:` 匹配与「子目录 PAI.md」
  只是同一个触发点上的两种规则来源。多出来的成本主要在发现逻辑与测试面。
- 候选 C·只做子目录懒加载：对齐官方的最小差，但把用户点名的那半边留在外面。

### 确认

2026-08-26 用户一轮拍板，三问全选 A（推荐项）：

问 1 选 A·loop 的工具结果回填处。一处覆盖全部工具，且不会因为「加了个新的碰
路径的工具忘了上报」而静默漏——B 的那个坑 07 复盘质疑二已经点过名。
路径怎么从 args 里取仍然下放给工具自己（`Tool.get_path`，与「匹配语义下放给
工具」同一条既有架构约束），loop 只负责问一句、收集、交给注入回调。

问 2 选 A·当第二个召回块。下一轮开头以一条 user 消息注入（走 `_extend`），
锚点簿不用动（它本来就允许消息在轮与轮之间增长）；压缩之后靠 feature 35 刚
建好的 `on_context_rewritten` 清「已注入过」表，下次读到同一个文件重新注入。
官方那条「嵌套的与 path-scoped 的压缩后不重注入」刻意不抄——与 D#42
「指令全部从磁盘重读」方向一致，且不抄的理由是它会造出沉默的失效
（压缩后模型看不见规则，而它以为自己看过）。

问 3 选 A·只做路径作用域规则，子目录懒加载留成后续小改动。
需求池自己判过「真正的收益在前者」。

拍板之外、写 spec 时定的一处偏离官方，单独记档（够格的话升格 decisions）：
`.pai/rules/` 里不带 `paths:` 的文件本轮不加载、warn 指路「要常驻就写进 PAI.md」。
官方那边它们是常驻的，但本需求的收益命题就是降低常驻成本——在同一个功能里
再开一条常驻通道与目标相反，而 PAI.md 已经是常驻指令的家。

## 结果与总结

pai 的指令层从「只有常驻一档」变成两档：`.pai/rules/*.md`（与
`~/.pai/rules/*.md`）里带 `paths:` 的规则，只在模型这一步真的碰到匹配文件时
才进上下文，碰不到就一个字都不占。

交付面（六个 task，红→绿数字见 [devlog](devlog.md)）：

1. `core/rules.py`：递归发现两级规则目录、`paths:` 认行内与 YAML 列表两种写法、
   坏文件 warn 后跳过。
2. 自己写的 glob→正则翻译（`**` 跨目录、`*`/`?` 不跨 `/`、目录前缀比到分隔符
   边界）——不用 `fnmatch`，它的 `*` 会跨 `/`，那是错的语义且很难被测试注意到。
3. 选择与渲染：去重（`RuleState.injected`）、单篇 4000 字符截断、每步最多 3 条
   且超了要说、包 `<system-reminder>` 并声明「不是用户指令」。
4. loop 挂点：工具结果全部回填之后收集「这一步碰过哪些文件」（路径怎么取仍下放
   给 `Tool.get_path`），交给注入回调；只算真跑过的调用。
5. 装配接线：装配期扫一次、跨轮持有、once 与 REPL/TUI 三条路都接上；
   `on_context_rewritten` 一并清注入表（feature 35 那条通道的第二个消费者）。
6. `/memory` 列出规则、`paths` 与「本会话已注入」——这层的失效方式天然是沉默的。

测试：全量 `1481 passed, 3 deselected in 163.84s`（此前 1447），新增 33 条。
一条纵切（真装配 + 真工具跑一轮，读到匹配文件之前/之后各断言一次）配注入反证：
拆掉 loop 里那句 `_extend` 即 `2 failed`。

交付过程中自己查出并修掉一个真 bug：相对路径原本按项目根解析，而模型给的
相对路径是相对 cwd 的——子目录里启动 pai 时两个基准不是同一个（feature 27
撞过的同一个场景）。

与官方不同的四处，都是刻意的，理由见 [D#75](../../decisions.md) 与 spec：
不带 `paths:` 的不加载、触发面含写/编辑、压缩后重新注入、`bash` 里的 `cat` 不算。
