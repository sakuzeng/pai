# 36-path-scoped-instructions · spec

## 背景与问题

pai 的指令层现在只有一档：常驻。`AGENTS.md` / `PAI.md` / `PAI.local.md` 沿途全收，
拼成一条 user 消息注在 system 之后，每轮都在上下文里（压缩后还会从磁盘重读重注入）。
好处是简单可靠，代价是常驻成本随规约变长线性上涨——本仓库自己的 `AGENTS.md`
就有 26KB，而它对「改一个 TUI 渲染函数」这类具体任务里的大多数轮次都不相关。

四家对照里 pai 的常驻层最薄的评语（PAI-04 诚实边界）说的正是这件事：
官方有第二档——`paths:` 作用域规则，只在模型读到匹配文件时才进上下文。

## 目标（做什么）

1. `.pai/rules/*.md`（项目级）与 `~/.pai/rules/*.md`（用户级）递归发现。
2. 带 `paths:` frontmatter（glob 列表）的规则文件，只在模型这一步真的碰到匹配
   路径时，才把正文注进上下文。
3. 注入形态与召回块同款：下一轮开头一条 user 消息，包 `<system-reminder>`，
   明说这是框架按你刚碰的文件加载的规则、不是用户指令。
4. 已注入过的不重复注入；上下文被改写（压缩 / `/compact` / `/clear`）之后作废，
   下次再碰到同一个文件重新注入。
5. `/memory` 要能看见规则文件（列出来 + 标出哪些已注入），否则这层机制的失效
   方式又是沉默的。

## 非目标（明确不做什么）

- 子目录指令懒加载（问 3 拍板：留成后续小改动，同一条管线，加一种规则来源即可）。
- 不带 `paths:` 的规则文件本轮不加载，warn 指路「要常驻就写进 PAI.md」。
  这是对官方的一处刻意偏离，理由见「设计要点」第 5 条。
- `bash` 里的 `cat`/`sed` 不算「碰到文件」（bash 不声明路径语义，同 D#52 的判据）。
  这条是已知豁口，写进文档与测试，不假装堵住了。
- 不做 glob 的完整 gitignore 语义（否定模式 `!`、字符类等）。本轮只认
  `*` / `?` / `**` / 目录前缀这几种，其余原样当字面量。
- 不引 PyYAML：`paths:` 用 pai 自己的 frontmatter 子集（见设计要点 2）。

## 设计要点

1. 挂点（问 1·A）。`loop` 在一步的工具结果全部回填之后，向本步真的执行过
   （未被权限拒绝、未被中断）的每个 tool_call 问一句路径——问的方式是
   `Tool.get_path(args)`，即路径语义仍下放给工具自己声明（与 `path_access_for`
   /「匹配语义下放给工具」同一条既有架构约束）。收集到的路径去重后交给注入回调
   `on_paths_touched(paths) -> str`；返回非空就以一条 user 消息 `_extend` 进上下文。
   loop 因此仍然不认识规则、不认识记忆——与 `instructions` / `recall` /
   `on_context_rewritten` 是同一种注入形状。
   - pi：无此机制（指令层只有常驻一档）。
   - CC：官方 `.claude/rules/` + `paths:`，触发点是「Claude 读到文件时」。
   - dsh：无此机制。
   - pai：照 CC 的语义，但触发面比它宽一点——读、写、编辑都算「碰到」
     （一条 `src/**/*.py` 的规则在改这个文件时同样该生效，管线一模一样）。

2. `paths:` 的写法。pai 的 frontmatter 是自家子集（`parse_frontmatter` 明文
   「不引 PyYAML」），所以 `paths:` 认两种形状，都在 `rules.py` 里自己解析：

   ```markdown
   ---
   paths: src/**/*.py, tests/**
   ---
   ```

   以及 YAML 列表块形状（`paths:` 下面若干 `  - src/**/*.py` 行）。
   两种都认是因为第二种是官方文档里的写法，用户从 CC 抄一份过来必然是它——
   只认第一种的话失效方式是沉默的（`paths:` 值为空 → 当成没有 paths）。

3. 匹配。路径先归一成「相对项目根」（拿不到项目根就用 cwd），再与每条 glob 比：
   `**` 跨目录、`*`/`?` 不跨 `/`；模式以 `/` 结尾或本身是个目录名时，
   匹配它之下的一切。绝对路径与界外路径不参与匹配（规则是项目内的事）。

4. 去重与失效（问 2·A）。`RuleState.injected` 记已注入过的规则文件名，
   与 `RecallState.surfaced` 同款；`assemble` 的 `on_context_rewritten` 一并清它
   （feature 35 刚把这条通道建好，这里是它的第二个消费者——正好检验那个回调
   是不是该升格成事件，见 35 复盘质疑二）。

5. 不带 `paths:` 的文件不加载（偏离官方）。官方那边它们是常驻的、与
   `CLAUDE.md` 同优先级。pai 不抄：本需求的收益命题就是降低常驻成本，
   在同一个功能里再开一条常驻通道与目标相反；而 `PAI.md` 已经是常驻指令的家，
   两个入口做同一件事只会让「我的指令为什么没生效」多一处要查的地方。
   代价：从 CC 抄规则目录过来的人会看到 warn。warn 里给出路。

6. 预算。单篇规则正文上限沿用召回那条的 `MAX_RECALL_CHARS = 4000`（同一类
   「一段进上下文的外部文本」该同价）；一步之内最多注入 3 篇（一次工具批里碰
   五六个文件是常态，全注进去就把降成本变成了涨成本）。两个数都是未实测的
   经验值，按「照抄来的常数要写来路」的规矩在常量旁写明。

## 验收标准

1. 带 `paths:` 的规则文件，在模型没碰到匹配文件之前，一个字都不进上下文
   （反向守卫：assemble 之后直接开跑，请求里搜不到规则正文）。
2. 模型 `read_file` 一个匹配文件之后，下一轮请求里有该规则正文，且带
   `<system-reminder>` 与「不是用户指令」的声明。
3. 同一条规则不会因为再碰一次同类文件而重复注入。
4. 压缩之后「已注入」表作废：再碰一次同一个文件，规则重新进上下文。
5. 不匹配的规则永远不进；不带 `paths:` 的文件不进且 warn 一次。
6. `bash("cat 匹配的文件")` 不触发注入（已知豁口，测试写明这是刻意的）。
7. 单篇超 4000 字符截断并说明；一步超过 3 篇时只注前 3 篇且说明还有几篇没注。
8. `/memory` 列出规则文件与它们的 `paths`，并标出本会话已注入哪些。
9. `./test.sh` 全绿，STATUS 数字同步。
