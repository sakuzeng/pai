# 19 候选方案

三条各自独立拍板——它们同属输入/信号层，但取舍互不相干。

## 问 1：`flush()` 提前把拆包的方向键裁决成 Esc（R4#13）

`flush()` 本身没错，错在调用时机：它被设计成「超时后」调用，而 busy 期的
`poll(timeout=0)` 让「无新数据」这个条件在拆包间隙就成立。

### 方案 A·让 flush 认时间

`KeyDecoder` 记下缓冲区最后一次进字节的时刻，`flush()` 只在「距今 ≥ 阈值」
时才真的裁决，否则原样留着等下一包。阈值取 50ms 量级。

- 好处：`poll(timeout=0)` 与 `poll(0.1)` 用同一份逻辑，调用方不用知道差别；
  修的是「凭什么判定它是 Esc」这个判据本身。
- 代价：给 decoder 引入时间依赖，测试要注入假时钟（arbiter 已有先例）。
- 风险：阈值又是一个「照抄来的常数」——要写清它从哪来。真人按 Esc 与终端
  发转义序列的时间差是数量级的（人 >100ms，序列 <1ms），50ms 有物理依据。

### 方案 B·busy 期不调 flush

`poll()` 加一个参数，timeout=0 时跳过 flush，只有真超时那次才裁决。

- 好处：改动最小，不引入时间依赖，decoder 保持纯状态机。
- 代价：把「什么时候可以裁决」这个知识放进了调用方；将来第三个调用点出现时
  还得记得传对参数——与 R4#1 那条「取第一个值」同类的隐性契约。
- 风险：busy 期真按 Esc 会一直悬着，直到下一次带超时的 poll 才生效
  （实际影响小：干活期间本来就有定时 poll）。

## 问 2：`PASTE_END` 丢失后 pasting 态无出口（R4#14）

### 方案 A·给 pasting 态挂超时

复用 `flush()` 的时机：距最后一次进字节超过阈值仍没等到 `201~`，
就把已攒内容按 paste 吐出来并复位。

- 好处：与问 1 方案 A 共用同一份「时间」机制，两条一起修反而更简单；
  用户视角是「粘贴的内容照常进来了，只是晚了一点」。
- 代价：真实的大段粘贴若在网络终端上分片很慢，可能被误判成结束而切成两段。
  阈值要比问 1 的大（粘贴分片间隔可达数百毫秒）。

### 方案 B·只给一条逃生键

不挂超时，但让 `Ctrl+C`（0x03）在 pasting 态下强制复位并产生 interrupt。

- 好处：不引入时间判断，不可能误切粘贴内容；用户有明确手势可自救。
- 代价：得先知道「按 Ctrl+C 能救」——而症状是「键盘全死」，用户第一反应是 kill。
  这条更像逃生口而不是修复。

## 问 3：SIGWINCH 同步重入（R4#12）

这条要动 feature 12 拍过板的东西：当时明确选了「同步不去抖」（对齐 CC 的
`handleResize` 刻意不去抖 + 同尺寸丢弃）。

### 方案 A·处理器只置标志，主循环重画

信号处理器把 `resize_pending` 置位就返回；`driver.poll()` 醒来时统一重画。
pi 与 CC 都是走事件循环的（它们的信号处理器不直接画）。

- 好处：从结构上消灭重入——处理器再也不碰 stdout，`RuntimeError: reentrant call`
  与「两帧字节交错」一起没了。
- 代价：resize 到重画之间多一个 poll 周期的延迟（最多 100ms）。
  且这是对 feature 12「同步处理」那条拍板的修改，须在 decisions 里
  记一条复议（不是推翻「不去抖」——去抖与同步是两件事，本方案仍不去抖）。

### 方案 B·只给 DockRenderer 补重入门

照抄 `AltScreenRenderer` 的 `_drawing` 标志，重入时直接 return。

- 好处：改动最小，与既有实现对称，不动任何已拍板的语义。
- 代价：只挡住一半。重入门能防「两帧交错」，但防不了
  `RuntimeError: reentrant call`——那个异常在 Python 的 buffered IO 层抛出，
  发生在我们的标志之外。也就是说最狠的那条失败仍在。
- 风险：会给人「已经修好了」的错觉。

### 方案 C·A + B 都做

标志位延迟重画（治根因），同时给 DockRenderer 补重入门（治将来别处再触发重入）。

- 代价：改动面最大，且 B 在 A 之后其实是冗余的防御。
