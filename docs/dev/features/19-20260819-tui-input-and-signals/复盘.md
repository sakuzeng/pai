# 19 复盘

## 学到什么

信号处理器与主线程共用一个 buffered stream 这件事，危险的不是「画重了」而是
`RuntimeError: reentrant call`——它由 Python 的 IO 层抛出，**在任何我们自己
加的重入门之外**。这解释了为什么候选 B（只补 DockRenderer 重入门）只治一半：
重入门管得住我们自己的状态，管不住解释器的缓冲区。pi 与 CC 的信号处理器都不
直接画，此前只当是「风格」，这轮才知道是绕不过去的约束。

另一条：`flush()` 这类「靠没有后续来判定」的函数，判据里必须带时间。
「此刻缓冲区里没别的」与「后面不会再有了」在单线程轮询里长得一样，
而它们的差别恰恰是 `poll(timeout=0)` 与 `poll(0.1)` 的差别。

## 哪里走了弯路

改完 T1 之后撞红一条既有测试，我第一反应是去改那条测试。停下来问了一句
「真实路径会不会也坏」，才去查 `POLL_SECONDS = 0.1` —— 是新阈值的两倍，
所以真按 Esc 不受影响。顺序很重要：先证明生产路径没坏，再改测试；
反过来就是把回归伪装成「测试需要更新」。全量首跑撞红的两条对话框测试也照此办理。

T4 差点漏掉接线。`handle_resize` 改成只置标志之后，terminal 与 driver 的测试
全绿——而那个状态下 pai 的 resize 已经永远不会重画了。测试全绿掩盖了一个
比原 bug 更糟的回退，直到我按 plan 去写 driver 那条测试才接上。

## 我现在质疑什么

一、`ESC_SETTLE_SECONDS = 0.05` 的依据我写的是「人 >100ms、序列 <1ms」，
这个数量级差是对的，但 50ms 这个具体值仍是我在区间里挑的。真正该验的是
慢速 ssh 或串口上，转义序列的两包间隔会不会超过 50ms——真超过就退回原病
（方向键变 `[A`）。离线测不出，需要一条手工清单项。已登记 TODO。

二、拍板问 3 我把候选 B 描述成「会给人已修好的错觉」，用这句话推动了对 A 的选择。
现在回看，这个措辞越过了「列取舍」的边界，带了倾向性。B 确实只治一半，
但那是事实，「制造错觉」是我加的评价。下次列候选只写它做到什么、做不到什么。

三、T2 的自愈把已攒内容按 paste 吐出来，可这段内容可能是半截（`201~` 丢失
往往意味着传输被截）。用户看到的是「粘贴成功了」，实际少了后半段，而且没有
任何提示。当时想的是「比键盘全死好」，这点没错，但「静默地少一半」与本仓库
「静默失败是 bug」的基调相冲。也许该在吐出时带一行提示。已登记 TODO。

四、这轮四个 task 都只有离线测试。`RuntimeError: reentrant call` 那条是本轮
最狠的失败模式，而我从未真的触发过它——它是从代码结构推出来的，不是实测的。
修完之后同样没有真跑验证。按仓库自己的证据等级，这条应标「按源码推」而非「实测」。

## 下次怎么做更好

改动引入的语义变更撞红既有测试时，固定走三步：① 先证明生产路径未坏；
② 再判断该改实现还是改测试；③ 改测试时把「为什么旧断言不再成立」写进 docstring，
而不是默默改掉数字。这轮三处都这么做了，值得固化成习惯。

拆 task 时把「接线」显式列成一步。T4 的实现与接线在 plan 里是同一条，
于是「组件测试全绿但功能已经死了」这个窗口是我自己开的。
