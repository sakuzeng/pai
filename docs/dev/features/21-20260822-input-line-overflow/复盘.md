# 21-input-line-overflow · 复盘

## 学到了什么

- 注入反证的复原手段必须与「修复是否已提交」匹配：未提交的修复，
  复原用 `git checkout <file>` 会把修复连注入一起冲回 HEAD——本轮真的发生了，
  且复原后的「确认跑」输出 `3 failed` 被我当成收尾扫过去了。可迁移的规矩两条：
  ① 对未提交修复做注入，加/删注入用脚本，别碰 checkout；
  ② 复原后的确认跑必须读数字，「跑完了」不是「绿了」。
- 零宽字符的处理会自己组合出正确行为：`display_width` 把组合记号计 0 列
  （R4#19 同日先修）之后，折行算法不需要任何「别把组合记号劈开」的特判——
  0 列永远不触发断行，天然粘在基字符后面。把正确性做进底层原语，
  上层就不用打补丁。
- e2e 断言里的「footer」这类结构判据要按内容特征写不能按位置猜：
  第一版 `"y" not in footer` 忘了状态行里有 cwd 路径，路径里有字母 y。
  判据该写成「不是我造的那种行」（不带提示符、不含连续 10 个 y）。

## 哪里走了弯路，为什么

- 上面那次 checkout 事故。为什么会那么想：这一批前面十几次注入反证里，
  `git checkout` 一直是复原的标准动作——但前面那些场景要么是 test-only 轮次
  （src 本来就干净），要么注入的文件与修复的文件不同。习惯化的动作没有跟着
  前提变化重新检查。发现靠的是复原跑的红数字扎眼，不是靠警觉。
- main-screen e2e 第一版断言误伤自己（footer 含路径），红了一次才改对。
  代价小，但说明「先跑一遍看真实形态再写断言」这条（feature 20 阶梯断言的做法）
  这次没执行——直接凭想象写了 footer 的样子。

## 我现在质疑什么

- 折行后 dock 高度随输入增长，极端情况（粘几千字符）dock 会吃掉大半屏幕；
  main-screen 下 dock 高于终端行数时 `_repaint` 的相对移动是否仍正确没有专门
  测试。pi 对超宽有 fail-loud，pai 对超高什么都没有。真实使用大概率撞不到
  （粘几千字符的输入本身罕见），但「没测过」要说出来。
- 折行续排行的两格缩进是我定的（对齐提示符宽度），没有问用户——它属于
  「实现细节」还是「形态的一部分」拿不准。若用户看了觉得该顶格或该带记号，
  改一行就行。
- ↑↓ 仍翻历史不进显示行（遗留 2）：CC 在多行输入里 ↑↓ 是移动光标，
  历史要光标在首行才触发。pai 现在的行为在长行上可能让人意外（想上移光标
  却换出了历史条目）。这条也许比点击定位（遗留 1）更早被撞到。

## 下次怎么做更好

对未提交修复做注入反证前，先把「复原命令」写成与注入对称的脚本
（同一段 python 的 add/remove 两半），根本不给 checkout 出场机会。
