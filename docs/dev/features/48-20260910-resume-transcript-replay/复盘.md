# 48-resume-transcript-replay · 复盘

## 学到了什么

CC 恢复一个会话时没有「回放」这个动作。`ResumeConversation` 把 `initialMessages` 交给
`<REPL>`，`REPL` 把它当 `messages` 状态，同一个 `<Messages>` 负责画——恢复之后屏幕上有什么，
只取决于「这份数组会被画成什么」。pai 抄到了形状，抄不到机制：pai 的 transcript 是 commit
出来的 append-only 日志，不是从 messages 派生的视图，所以每一处「状态变了 UI 要跟」都得
手写一次，`TuiApp.replay` 就是这样一处。这不是这一轮能改的，但值得写下：日志式 UI 的
代价不在第一次渲染，在第二种来源出现的时候。

第二条：文案与代码脱节了 13 天没人发现。feature 35 加的那句「system prompt 都按当前环境
重新装配」有测试盯着——盯的是文案存在。断言文案存在的测试证明不了文案是真的；
这轮的 `test_resume_rebuilds_system_prompt…` 断言的是发给 provider 的第一条消息里没有旧内容，
那才是文案在说的事。

第三条：真实轨迹再次抓到我的假设。第一版测试写「恰有一条最终回答」，真实会话零回答——
整段是一次被预算掐断的 run。这份夹具的价值恰恰在它「不正常」：并发工具批、规则注入、
steering 注入、以 user 结尾，编是编不出这个组合的。

## 哪里走了弯路

- 对 events 流的第一次判读写错了（「两条 AgentEnd 都是 budget」，实际一条 AgentEnd、一条
  SteeringInjected）。原因是我的检索脚本把 `ToolEnd` 也匹配进了「end」，看了六条 ToolEnd
  就下结论。复核后才改成实情——查证据的脚本本身也要看一眼输出对不对。
- 给 `!命令` 的回放形态改了两次主意（用户色带 vs 单条工具行），最后按「用户行上面已有命令，
  不重复」定成单条 `! 命令` 工具行。这种小决定应在写测试前定，而不是边写边改。

## 我现在质疑什么

- `!命令` 活轮次全量上屏、回放折叠一行，两条路形态不一致。CC 两条路是同一段代码所以不会
  不一致；pai 要一致就得把活轮次也改成折叠——这轮怕扩 diff 没动，但「同一个东西两种画法」
  正是 CC 形状里最该抄的那一半。登记 TODO。
- 拍板问 3·A 把 system 换成新 id。一条不是指数，但每次 resume 都多一条 system，24 复盘质疑三
  「文件数 × 全量」的账又重了一点；而 CC 的根治法（system prompt 不进转录）在 pai 的格式 v1 里
  做不到——system 消息是 `build_messages` 重建的一部分。哪天格式 v2 时该一起考虑。
- `history_items` 靠四个固定头认注入消息。它能工作，是因为这四个头都是 pai 自己造的且没变过；
  哪天 recall 或 rules 换了外壳，回放会把注入当成用户话画出来而没有任何测试变红。CC 用 isMeta
  一个字段解决——pai 的 messages 没有 pai 自己的元数据层，这是比 resume 更根本的形状问题。
- 回放的历史与本次对话之间没有分隔，只有末尾的恢复提示算一道边界。CC 也没有。
  但 CC 的用户在同一个终端里连续看着，而 pai 用户是「打开就看到一屏旧东西」——先记着，看真用。
- 夹具 131KB。用了真实轨迹是对的，但仓库里最大的测试文件是一份工具输出的全文，
  下一份同类夹具值得截短正文并注明。

## 下次怎么做更好

- 引用任何「文案说 X」之前，先 grep 代码是否真做了 X。这次是顺带发现的，不该靠顺带。
- 写真实轨迹的断言之前，先用脚本把它的形状（角色序列、事件类型计数）打出来看一眼，
  再写数字——「至少一条答案」这种假设，一行脚本就能证伪。
- 查证据的脚本输出也要复核：匹配条件宽了，看到的就是别的东西。
