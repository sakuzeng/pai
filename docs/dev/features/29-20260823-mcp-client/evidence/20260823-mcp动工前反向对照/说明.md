## 真实探针（claude 2.1.239）

P1 · 全链与命名：`--allowedTools "mcp__probe__echo_token"` 下要求模型调用工具。

- server 日志依序收到 `initialize` → `notifications/initialized` → `tools/list` →
  `tools/call`；回答一字不差回显了暗号 `MCP-PROBE-TOKEN-2933`。
- `tools/call` 的 `params.name` 是原始名 `echo_token`（不带 `mcp__probe__` 前缀）——
  「线上走 raw name、前缀只在模型侧」三家一致（dsh 命名不变式 3 在 CC 同样成立）。
- `_meta` 里带 `claudecode/toolUseId` 与 `progressToken`。
- ⚠️ 版本漂移实据：initialize 的 capabilities 是
  `{"roots": {"listChanged": true}, "elicitation": {}}`——反编译 2.1.88 源码写的是
  `roots: {}`（空对象），与官方文档「v2.1.203 起支持 roots/list_changed」对上。
  引用 CC 源码谈 MCP 时必须带版本号（与 skills 反向对照同一条教训）。

P2 · isError 语义：要求模型调 `always_fails` 并原样转述错误。

- 回答一字不差含 `PROBE-FAILURE-DETAIL-7381`——`isError: true` 的 content 文本
  完整到达模型。与 CC 源码（isError → throw McpToolCallError(errorDetails)）一致：
  内部是异常，但错误细节走「工具失败回填」路径给模型。pai 的「工具错误不 throw、
  转字符串回填」架构约束与此殊途同归。

P3 · 连接失败的可见性：配置 `command: /nonexistent/...` 的 server，问模型能不能调。

- ⚠️ 与文档不符：官方文档说 v2.1.205 起「配置的服务器无法连接时，Claude Code
  告诉 Claude 哪个服务器失败及其连接错误（经 ToolSearch 结果）」。实测 2.1.239
  两跑：第一跑模型只做泛泛猜测（「可能根本不存在或未安装」，无具体错误）；
  第二跑显式要求引用 ToolSearch 里关于该 server 的原文，模型引回来的是无关的
  内置工具文档。机制未查明（可能与触发条件或 stdio spawn 失败路径有关）——
  只记实测事实，不编解释。对 pai 的含义：连接失败要不要告知模型是要自己拍板的
  设计点，别把文档那句当成已验证的行为。

原始产物：探针 server 脚本、两份 mcp-config、probe.log 在会话 scratchpad
`mcp-probe/`（会话级临时目录，关键内容已如实转录于本文）。

   client 侧同量级。D4 教训（SDK 隐式行为咬人）进一步支持手写路线。
