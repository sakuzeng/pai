## 一、最贵的一条教训：测试覆盖了产物，没覆盖用途

REPL 的历史功能，测试有两条：「按 cwd 分文件」「连续重复只记一条」。两条都绿。
但**历史文件从没被读回 readline**，所以 ↑ 一直是死的——直到用户问「本机能测什么」，
我准备写「按 ↑ 翻历史」时顺手 `grep readline`，才发现一行都没有。

两条测试测的是**产物**（文件里的内容对不对），没有一条测**用途**（这文件到底给谁用）。
spec 里那句话是「`readline` 提供 ↑/↓ 与 `Ctrl+R`；历史按 cwd 分文件存」——
我实现了后半句，测了后半句，然后以为整句都做完了。

**下次怎么做更好**：spec 里每条能力后面跟一句「怎么验证它真的能用」。
「历史按 cwd 分文件存」的验证是 `cat` 文件；「↑ 能翻出上一轮输入」的验证是**按一下 ↑**。
写下来就会发现后者根本没有对应的测试手段（要真终端），那就该在 spec 里标成
「只能人工验」，而不是让它消失。

## 二、破坏性改动的姿势：把旧行为抄成常量当锚

`on_event` 从收字符串改成收事件对象，是这轮唯一的破坏性改动。做法是把改造前 loop.py 里
五处 `on_event` 的**原文**抄进测试当 `LEGACY_*` 常量，断言 `render_text` 逐字复现。

好处不是「防止行为变化」——而是**让行为变化必须显式发生**：谁想改文案，就得改那个常量，
而那一行会出现在 diff 里被人看见。这比「小心一点别改坏」可靠得多。

顺带的收获：这套锚在 `once` 模式上生效，但**默认处理器的回归它照不出来**——
我把 `once.py` 的 `on_event=print` 忘了改成 `print_event`，屏幕上会打一串 dataclass repr，
而所有测试都注入了假 handler，全绿。补的那条 `capsys` 测试才是真正的守门人。
**教训**：断言「传进去的东西」不等于断言「用户看到的东西」。

## 三、中断是数据路径，不是异常路径

直觉做法是让 Ctrl+C 抛异常一路弹出。但 D#2 早就定下「`tool_call_id` 配对由 loop 唯一负责，
任何分支都回填 tool 消息」——一轮 3 个 tool_calls 只回 1 条，下一轮请求就是 400。

所以中断的正确形态是：置标志 → 剩余 tool_calls **各回一条「已取消」** → 干净返回。
REPL 里同理，干活期间的 SIGINT 只置标志不抛 `KeyboardInterrupt`——抛了会把已完成的工作
连同栈一起丢掉，而官方对中断的承诺恰恰是「保留迄今完成的工作」。

**可迁移的判断**：当一个「异常情况」需要**留下痕迹**（配对、审计、可续），
它就不该走异常路径。异常擅长的是「放弃并向上传播」，不是「有序收尾」。

## 四、冒烟真跑抓到了测试抓不到的东西

`printf ... | pai` 跑一次，撞出「一次 401 让整个 REPL 带栈退出」。
测试全绿也照不出来，因为测试里的 client 从不失败。

**为什么这条重要**：once 模式崩了无所谓（本来跑完即退），REPL 崩了等于把整段对话丢掉——
而 REPL 这一层的**全部价值**就是「对话留着」。同一个异常，在两个模式里的严重性差一个数量级。
**教训**：新加一层的时候，先问「这层的价值是什么」，再问「什么会让这个价值归零」。

## 五、注入反证比测试通过更能说明问题

`killpg` 那条测试，我按计划做了注入反证（换成 `proc.kill()` 看是否变红）。
**它确实红了，但红在我没预料的地方**：不是「孙进程还活着」那条断言，而是更靠前的
「没拿到 PID」——因为杀不掉整组时，后台 `sleep` 仍握着 stdout 管道，`communicate` 收不到
EOF，连已产出的输出都一起丢了。

同一个根因的两个症状，而我原本只知道其中一个。**注入反证的价值不只是「证明测试有效」，
还在于它会告诉你「错误实现的真实后果」——那往往比你以为的更糟。**

## 六、诚实边界这次守住了，但差点没守住

「steering 在纯 REPL 无真实输入源」这条，从拍板问答一路写到 spec、代码注释、STATUS、TODO。
四处都写了「结构与注入点已就位，等 TUI/流式才通电」。

差点没守住的是 readline：如果用户没问「本机能测什么」，我大概会在某个总结里写
「历史、↑/↓、Ctrl+R 都做了」——因为 spec 这么写的，测试也绿。
**边界的诚实靠的不是态度，是有没有一条能证伪的验证手段。**

## 我现在质疑什么

（2026-08-10 补：这一节是新规矩要求的必答项。以下都是**交付之后**才看清的，
写下来不等于要推翻，但下次拍同类板时应该被摆在台面上。）

**一、问 3 选 B（中断做到工具执行中途）的代价，我当时没说全。**
我列的代价是「要动 `core/tools/shell.py`」。实际代价大得多：`start_new_session=True`
让子进程脱离终端会话，于是**它再也收不到终端发的 SIGINT**——我为了能杀干净，
先切断了「Ctrl+C 天然传到子进程」这条最简单的路径，再用「信号置标志 + 轮询」把它补回来。
换句话说 B 不是「在 A 之上多做一点」，是**换掉了整套信号模型**。
如果拍板时这么说，A（只做步边界中断）的性价比看起来会不一样。

**二、Task 8（状态行）是我追加的，而且我把它接成了 REPL 的默认行为。**
用户问的是「这些能实现吗」，我答完顺手做了，还改了 `run_interactive` 的默认 `on_event`：
状态行开着就不再滚动打 `🔧`。这等于**默认改变了已交付功能的输出形态**，
而它从来没被拍过板。更克制的做法是默认关、显式打开。这条我倾向于认为当时越界了。

**三、`is_error` 只覆盖 loop 自造的错，那状态行的红叉几乎永远不会出现。**
工具内部异常被 `Tool.run` 吸收成字符串，红叉只在「参数非法/未知工具」时亮。
做一个几乎不触发的 UI 状态，是不是不如先不做、等 `Tool.run` 的返回契约改了再补？

**四、砍掉 `turn_end` 省下的是几行，代价是阶段 5 要回头改渲染层。**
理由「不流式时它不携带新信息」成立，但如果阶段 5 必然把它加回来，
这是不是过度追求「当下最小」？——我仍倾向于当时的选择，但理由应该是
「现在加会误导读者以为有分层」，而不是「省代码」。

## 下次怎么做更好

拍板问题里的「代价」一栏，必须写**二阶代价**（这个选择会连带换掉什么机制），
而不只是「要改哪几个文件」。第一条质疑就是这么漏的。
