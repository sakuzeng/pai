# 50-tool-group-collapse · 复盘

## 学到了什么

CC 的分组是后处理：每帧从 messages 重新派生 UI，所以「把连续的工具折成一条」只是渲染前对
列表做一次 reduce。pai 的 transcript 是 commit 出来的日志，同一件事只能写成状态机——持有当前组，
四种断点把它定格。这是 48 复盘那条「日志式 UI 的代价不在第一次渲染，在第二种来源出现的时候」
的第三次兑现（回放是第二次，组是第三次）。三次之后我已经确定这不是巧合：pai 缺一层
「渲染用的消息视图」，每个新的呈现形态都在重新发明它的一角。

第二条：CC 的「加深背景」根本不是我以为的东西。截图看着像工具块有底色，源码里
`backgroundColor` 只在 `useSelectedMessageBg` 为真时出现——那是光标选中行。如果不读源码，
我会给所有工具行铺一条底色，然后用户会问「为什么和 CC 不一样」。照 CC 的第一步永远是
搞清 CC 到底做了什么，而不是它看起来做了什么。

第三条：契约翻转要写在测试名里。feature 16 真跑打回来的「单行结果不可展开」在这轮被反转了
（组总是可展开），我把新测试名改成「still expands to the command and its output」并在
docstring 写明反转理由。将来有人 blame 到这条，看到的是「为什么变」，不是「有人删了断言」。

## 哪里走了弯路

- 第一版活跃组不接受展开，理由是「它还在变」。五条真跑测试立刻红了：用户点一个在跑的组
  会「点了没反应」——恰恰是 feature 16 那条真跑反馈最讨厌的事。CC 对进行中的组同样给
  `(ctrl+o to expand)`，我一开始没看那行 JSX。
- e2e 等「(^O 收起)」等了 8 秒：展开后摘要行被一百多行内容顶出了视口。测试改了，
  但它照出的是真缺陷（登记 TODO），不是测试写错。

## 我现在质疑什么

- 活轮次的 `!命令` 还是全量上屏。48 就登记过，这轮回放侧走了组，活轮次仍是 `_run_shell(out=commit)`
  直接吐文本——同一件事两种画法的差距反而更明显了。该改活轮次，没改是怕这轮 diff 再扩。
- 展开长组之后用户不知道怎么收。CC 没这个问题是因为 ctrl+o 是全局模式切换，不是就地展开；
  pai 选了就地展开（拍板问 3 照 CC 的 verbose 形态，但 pai 的 verbose 是局部的）。
  这是「形状照 CC、机制不同」在用户体验上第一次露出代价。
- `⎿` 提示没做 700ms 最短停留。快工具一帧闪过，现在时那一行看起来像在抖。CC 特意写了
  `MIN_HINT_DISPLAY_MS` 说明它真的被抖过。
- dock 活动区（跑着的工具 + 明细）与组的 `⎿` 提示信息重叠。拍板时我写了「dock 原样保留」，
  真用后如果两处都在动，该收掉一处。
- 回放的组把整个第一问的 10 个并发批折成一条「读了 15 个文件，看了 1 个目录，跑了 6 条命令，
  跑了 1 次测试」——信息密度对了，但一条 37 消息的会话在屏幕上只剩三行。是不是太少了，
  要看真用。

## 下次怎么做更好

- 「照 CC」的任何视觉判断，先找到那个 `backgroundColor` / `dimColor` 是在什么条件下成立的，
  再决定 pai 的对应物。
- 涉及「进行中」状态的条目，第一条测试就该是「进行中时点它有没有反应」。
- 展开类交互的 e2e 要带一条「展开之后怎么收回来」，不只是「展开了没有」。
