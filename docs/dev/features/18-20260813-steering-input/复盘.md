# 18-steering-input · 复盘

## 学到了什么

「两家做法不同时该抄哪家」通常是伪问题。 真正该问的是：
这两家各自的做法里，哪一半是被它自己的其他约束逼出来的？

本次的实证：CC 的 `next` 在「模型纯答话」的轮次上会退化成新开一个 query——
这不是它的设计选择，是它单层循环 + `needsFollowUp` 作为唯一退出信号的副产品
（`query.ts:558` 注释原话 *"the sole loop-exit signal"`*）。
pi 的双队列也不是设计，是它把「什么时候发」的决定权推给集成方的结果。
剥掉这两处约束之后剩下的才是可以拿的东西——于是 pai 拿了 CC 的单队列 + pi 的第二出口（D#68）。

这条可迁移，是 `knowledge/concepts/` 的候选（暂未立笔记：只有一个案例，
再撞到第二次再升格，否则就是把一次经验写成方法论）。

第二条：机器护栏的价值在「它拦住你的那一刻」才看得见。
T2.5 新增一个事件类，被两道测试当场拦下——`EVENT_SRC` 键集合断言（viz 的「机制住哪」）
与 `SAMPLES` 覆盖断言（观测流样本）。写 plan 时我把这两处记成「(a) 方案的成本」，
实际用起来它们是收益：没有它们，新事件会安静地在 viz 上缺一格、在观测流里没有样例，
而没有任何测试会红。「多改一处」与「护栏」在成本表上长得一模一样，要到被拦住时才分得出。

## 哪里走了弯路，为什么

弯路一：抛拍板问时，我把「笔记两节并读的推断」当成了可以拿来抛问的依据。

问 3 我写的是「CC 的 mid-turn 实际是批量灌的，依据是笔记第二/四节并读，
拍板前建议复核」。用户没有选，而是回了「cc是怎样做的呢」——去读源码之后，
推断的方向对、说法不准（「同档 FIFO 逐条」是 `dequeue()` 这个函数的语义，
不是注入路径的行为；两个 drain 点实际都批量）。

当时为什么会那么想：笔记是自己前一天写的，读起来有「已经查过了」的错觉。
换个人也会踩——笔记天然把「我核实过的」与「我推断的」排版成一样的正文，
除非像我那次一样显式标注「未复核」。这次标了，所以只花了一轮就纠正。

弯路二：写 e2e 时，直接抄了 feature 12 那条同类测试的形状。

12 的 `test_typing_while_busy_lands_in_the_queue` 用 `wait=0.05` 然后发第二行，
它一直是绿的——但它只断言「两个答案都出现了」，而那在两种语义下都成立。
我抄了这个形状，于是连着两轮假绿：
① 假 provider 秒答，「模型正在答」这个状态根本不存在；
② 加了 `delay` 之后仍假绿，因为两行输入落进了同一批 `driver.poll()`
（那个「一次读干净」是给鼠标事件合并用的设计）。

当时为什么会那么想：「有一条现成的、绿着的同类测试」本身就是最强的错误暗示——
它让人跳过「这条测试到底钉住了什么」这一步。
真正把我拉回来的是读观测流（`.events.jsonl` 里两次 `AgentStart`、零条 `SteeringInjected`），
不是继续推理。

## 我现在质疑什么

质疑一（针对用户拍的板，问 2）：删掉 followUp 之后，「不要打断你，干完再看」这个意图
在 pai 里现在无法表达，而我给出的支持理由可能不成立。

抛问时我写「CC 的交互式用户根本没有降级手势」——这是事实，但它对 pai 不构成论据：
CC 用户不需要降级手势是因为他们有 Esc（abort 当前工具但不杀整轮）这条独立出口，
而 pai 的 Ctrl+C 是进程级标志（D#40），一按就是整轮结束。
pai 恰恰是那个更需要「排队」选项的实现，而我们把它删了。

这条够格升格：真跑几天之后如果撞到「想补一句但不想打断当前计划」的场景，
就是 decisions 复议（D#68 的第二半）。暂不改——现在改就是凭空发明手势，
没有证据也没有参照实现。已在下面「下次怎么做更好」里给出取证方式。

质疑二（针对我自己写进 plan 的取舍）：轮末残余「一条消息一轮」这条偏离，
理由站得住，但代价没量过。

我给的理由是「`run_agent(task)` 的 `task` 同时喂给 `AgentStart` 与 `recall()`，
拼成一个字符串会把这两处弄脏」——成立。但如果用户真的在轮末连打三句，
现在是三次完整的模型往返，而 CC 是一次。这个场景有多常见我不知道，
没有数据。若将来发现常见，正确的修法不是拼字符串，而是让 `run_agent` 收
`tasks: list[str]`（`AgentStart` 取第一条、`recall` 取拼接，两处各自决定）。

质疑三（针对 `MAX_QUEUE_ROUNDS = 8`）：这个数字是拍脑袋的。
理由（防用户一直打字导致死循环）成立，但 8 没有任何依据——
撞上界之后的行为是「剩下的留到下一轮」，所以选错的代价很小，但它现在没有任何提示：
用户不会知道自己有 3 条话被推迟了。已登记 TODO。

## 下次怎么做更好

一条具体的：给「同类的现成测试」加一次显式的反证检查，而不是照抄它的形状。

具体做法（这次事后补做了，下次要在写完测试的当下做）：
把被测的那行实现临时拆掉，跑一遍，确认恰好是针对它的那几条变红。
本次的实测形状值得记下来——拆掉 `loop.py` 的出口② 之后是
`2 failed, 4 passed`：两条针对出口②的红，另外四条（中途出口、命令处理）照常绿。
「红得精准」比「全红」更能说明测试钉对了地方：如果全红，说明这些测试其实在测同一件事。

顺带：feature 12 那条 `test_typing_while_busy_lands_in_the_queue` 至今没有反证，
它在两种语义下都绿——它是一条「不会失败的测试」，本次只改了它的 docstring。
下次动到它时应当补反证或删掉它。
