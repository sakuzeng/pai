# 34-todo-backlog-batch · 复盘

## 学到了什么

「重排版一个冻结夹具」不是零风险操作，而我按零风险对待了。拉平
FROZEN_TOOL_SCHEMAS 缩进的脚本去找「顶层收尾 `]`」，撞上的却是
`"required": [ "path" ]` 的内层 `]`，于是括号被移到了错的位置——
而结果仍是合法 Python，48 条测试照样全绿。冻结夹具的全部价值在于「它没变」，
所以改它的排版必须用「值相等」来验收，不是用「测试还绿」来验收：
最后是 `ast.literal_eval` 比对 HEAD 与当前的字面值才拿到了证据。

可迁移的形状：凡是改动只应影响表示层（缩进、引号、换行、格式化）而不应影响
语义的，验收标准就该是「解析后的值逐字相等」，而不是下游断言的绿。
这类改动恰恰是最容易被「反正测试是绿的」放过去的一类。

另一条：类型注解也能撒谎，而如实写 `Any` 有时才是正确答案。给 `usage_fields`
的 `response` 找类型时，非流式是 SDK 的响应对象、流式装配后是 pai 自己的结构、
各家 SDK 的类型还不通用——写死任何一个都是在文档里放一句假话。`Any` 加一句
「为什么只能是 Any」比一个漂亮但错的类型有用。这与「不用 Any 除非确有必要」
不冲突：必要性是要论证的，论证写在 docstring 里。

## 哪里走了弯路，为什么

一处真弯路：给 `Anchor` 换具名字段之后，我按新字段名顺手把调用点写成了
`anchor=latest.tokens`。看着完全对——字段名就叫 tokens，参数就叫 anchor——
但空锚簿返回 `Anchor(None, 0)`，`tokens` 是 0 而不是 None，
而 `context_tokens` 把 0 当成「真有一个 0 token 的锚」走了锚定分支，
工具 schema 那几百 token 就此从账上消失。

为什么会那么想：旧代码是 `anchor, anchor_index = anchors.latest()`，
「第一个位置」同时承载了两个含义——它是 token 数，也是「有没有锚」的哨兵。
换成具名之后哨兵含义没有名字了，于是它就丢了。教训是：把位置元组换成具名字段时，
要单独问一句「原来靠位置隐含表达的东西，有没有一个也换到名字上」——
这里是「无锚」这个状态，它在新结构里的判据是 `index is None`。
现在这条差别本身有一条测试钉着。

一处不算弯路但值得记：`test_the_tui_path_swaps_the_event_sink` 第一版
调 `interactive._run_tui(...)` 想跑真身，结果调到的是自己刚装上的间谍替身——
monkeypatch 之后模块属性已经被换掉了。真身得在装间谍之前先留一个引用。

## 我现在质疑什么

一、`EventSink` 与 `AskerRef` 现在是两个几乎一模一样的可变持有者，
第三个「装配期烤进闭包、运行期要换」的东西出现时就是三个。当时选择照
`AskerRef` 的形状复制一份，理由是「有现成的形，读者一眼认得出是同一件事」——
但复制到第三份就该抽了。抽成什么形状我现在也说得出：一个泛型 `Ref[T]`，
`get/set/__call__`。没有立刻做是因为两份还不构成模式，第三份出现时应该动手。
够格的话登记 TODO。

二、TUI 事件通道这条修法治的是「装配之后才建 TUI」这个顺序，而不是顺序本身。
更根上的问题是：为什么装配必须发生在 TUI 之前？如果 TUI 先起、装配后做，
就不需要任何可变持有者。我没有去动这个顺序，因为它牵扯到装配期就要用真人通道
（skills / MCP 信任门禁要问人）——而那正是 `AskerRef` 当年存在的理由。
所以这两个持有者可能都是同一个更深问题的症状：装配期需要一个「还没建好的 UI」。
这个怀疑我没有证据支撑到能提方案的程度，先留在这里。

三、`read_file` 截断这条我按 R#17 写的「零成本做法」做了提示语，
但提示语是给模型看的，而「模型会不会真按提示去 `sed -n` 分段读」这件事
本轮完全没有验证——离线测试只能断言提示语里有那几个字。这与
「测试全绿但真实不可用」是同一类风险。真正的验收要么是一次真模型冒烟，
要么就该老实做 offset 参数（那是可测的）。我现在倾向于后者才是正解，
零成本做法只是把成本转移到了模型身上。

四、本轮把六条「其实早就修了、只是漏勾」的条目核销掉了——这是第三次发生
（2026-08-09 一次、2026-08-24 一次、今天一次）。反复出现说明这不是记性问题
而是流程缺口：修的时候在别的档案里，销账要回到 TODO 这个全局文件，
而「回去划掉」是一个纯靠自觉的动作。已经有一条规矩要求登记，
但没有任何机制要求核销。

## 下次怎么做更好

给「漏勾」建一条可执行的检查，而不是再提醒一次自己。具体做法：
每次交付写复盘之前，把本次改动碰过的源文件列表跑一遍 grep，
在 TODO 里搜这些文件名/函数名出现在哪些还开着的条目里，逐条问一句
「这次是不是顺手把它关掉了」。这个动作只需要一次 `git diff --name-only`
加一次 grep，五分钟内能做完，而它正好对准了漏勾发生的机制——
漏的从来不是「我不知道这条待办」，而是「我不知道我刚才路过了它」。
