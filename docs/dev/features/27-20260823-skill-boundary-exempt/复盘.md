# 27 · 复盘（四问）

## 学到什么

- 「先查参照再拍板」在这轮直接改写了结论。一轮拍板时我推荐的是「两根进
  additional」（最小 diff）；用户一句「cc 是怎样做的呢」逼出的走读发现
  CC/dsh 都没让 skill 加载过路径层——修法从「把目录塞进边界」翻成
  「这个工具压根不该在边界里」。最小 diff 和正确建模不是一回事，
  25 复盘那句「评审语言里的照 X 要先验证」这次轮到了自己的推荐上。
- 一个 bug 的修复顺带收掉了半个相邻 bug：软链 skill 的正文加载与子目录
  启动是同一个根因（路径建模）长出的两个症状，豁免位一刀下去两个都好，
  剩下的软链附属文件问题范围立刻清晰。按根因修比按症状修便宜，
  前提是复核阶段把症状群摸全了。
- 豁免位这类「权限层开口」的安全边界靠两样东西钉：声明条件写死在
  docstring（入参无路径语义 + 路径来自受信来源，缺一不可），优先级
  守卫测试（deny/ask 规则在前）——将来第二个工具想豁免时，这两样就是
  评审清单。

## 哪里走了弯路

- 没走大弯路，但有一处差点走偏：一轮拍板的推荐（两根进 additional）如果
  用户直接采纳，脱节的建模会被永久固化，「未知名回 cwd」的绕法也会留着。
  用户的追问救了方案——AI 推荐标记不该被当成免检章。
- 优先级守卫与附属文件两条测试绿于到达（钉的是既有链语义，不是新行为）。
  与 25 复盘同款「红的鉴别缺失」，但这次是刻意的：它们是防回归的守卫不是
  行为规约，devlog 里如实标注了。

## 我现在质疑什么

- 质疑豁免位的粒度：`boundary_exempt` 是工具级布尔，将来若出现「部分调用
  该豁免、部分不该」的工具（比如带可选路径参数的），布尔就不够了——
  到时候该学 capabilities 的 `(args) -> bool` 形态。现在只有 skill 一个
  豁免者，不预支这个复杂度。
- 质疑「skill 名维度的 allow/deny/ask 规则」缺席的后果：CC 有
  `Skill(name)` 规则可配，pai 只有 model_invocable。用户想「禁掉某个
  项目 skill 但不删文件」时，pai 现在的出路只有 deny 整个 skill 工具
  （粒度太粗）。等真实需要，但这个缺口是 D#73 刻意不抄清单里最可能
  先被撞到的。
- 质疑 once 装配里用户级根进 additional 的必要性是否该复核：豁免位落地后，
  additional 只为附属文件的 read_file 服务了。25 遗留 6（整目录读免问）的
  代价没变，但收益面缩小了——如果将来附属文件场景证明罕见，这条 additional
  可以撤，25 复核发现的 acceptEdits 写面问题也会随之消失。已在 TODO
  acceptEdits 条目上有登记，不重复立项。

## 下次怎么做更好

- 拍板选项里凡有「照参照系」的候选，先花半天把参照系的真实做法查实再开
  AskUserQuestion——这次是用户追问触发的，下次应该是默认动作（25 复盘
  已写过一次，这次是同一课的变体：连自己的推荐也要过这道检查）。
- 复核发现的问题群修其一时，主动复跑其余问题的复现脚本——这次冒烟脚本
  三场景一把重跑才发现软链半边已好，若不跑，TODO 里会留一条过期的中级项。
