# 46-tool-steering · 复盘

## 学到了什么

**「生成出来一看就不对」这件事，只有真生成出来才知道。**

`render_tree` 我改了三版，两次都是把输出打到屏幕上一看就发现不行：
第一版 `tests/` 的 60 个文件把预算吃光、`src/` 只剩一个包名；
第二版深度优先加全局上限，`src/` **整个没出现**——而提示语还一本正经地说
「还有 N 项未列出」。两次的离线测试都是绿的：我断言了「有上限」「说清了截断」
「排序稳定」，唯独没有也无法断言「这份摘要有用」。

这与 feature 44 的空文件头、45 的工具选择是同一族的第三次：
**输出的质量不在任何断言的视野里**。区别是这次我一开始就把它打出来看了，
所以两个问题都是几分钟内发现的，而不是等到真跑。
可执行的一条：凡是「生成一段给别人看的文本」的函数，写完先打出来看一眼，
再去写断言——顺序反过来的话，断言会锚在我脑子里那个想象的输出上。

第二条：**A/B 让我第一次能对提示词做迭代，而不是猜。** 第一轮跑完看到剩下两次
bash 是 `cat` 与 `ls`，当场就知道该补哪两句引导。这在以前是做不到的——
以前我只能推断「模型大概会用哪个工具」。

## 哪里走了弯路，为什么

补完 `read_file` 与 `list_dir` 那两句引导之后我又跑了一次，结果**更差**
（12 次调用、5 次弹窗，模型跑到父目录去搜了）。我当时的第一反应是
「是不是我加的那两句把提示词搞乱了」，差点回滚。

停下来想了想才意识到：我在拿 n=1 跟 n=1 比。前一次 7 调用、这一次 12 调用，
中间隔着一个非确定性的模型。真正该做的是回到那三条针对性强的 `--llm` 测试，
跑三遍看稳定性（结果全过）。

这个弯路本身是有价值的：它让我把「端到端真跑」和「针对性验收」分清楚了。
前者是**观察**，用来发现问题、指导下一步改什么；后者是**测量**，用来判断改对没有。
我在 feature 45 里把观察当成了测量（那份发现清单里 A/B 的数字），
这一轮差点又犯一次，只是这次自己拦住了。

## 我现在质疑什么

一、我在 feature 45 的发现清单里写「A1 是收益最大的一条」，理由是那个
`run_tests` 0 → 1 的对比。这一轮做完之后我更不确定了：`--llm` 测试证明的是
「意图明确时模型会选对工具」，而真实会话里大量步骤是探路，探路时模型选什么
基本不受这几句引导影响。也就是说 A1 真正解决的可能只是一小部分——
而我用一个精心挑选的场景把它说成了「收益最大」。这与 45 复盘里我自己批评过的
「选择性引用」是同一件事，我批评完之后又做了一次。

二、`list_dir` 是我加的第七个工具，而这一轮的核心发现恰恰是「加工具的边际收益
在递减，因为模型未必选它」。真跑里 `list_dir` 被选中过一次、也被 `ls` 顶掉过一次。
我没有任何数据说明它值不值那份 schema token——而它每一轮对话都要花。

三、结构摘要的三个常数全是我看着**本仓库**的输出调出来的。本仓库有
14 个顶层目录、深层的 docs/knowledge 树，这个形状很特别。
换一个只有 `src/` 和 `tests/` 的项目，深度 2 可能太浅；
换一个 monorepo，120 项可能连顶层都列不完。我又一次把「在我这台机器上看着顺眼」
当成了默认值——这已经是第五个了（前四个记在 TODO 里）。

## 下次怎么做更好

把「观察」与「测量」在文档里分开写，用不同的词。
本轮 devlog 里那张端到端表格我标了「数字很吵，不拿它声称改进」，
而 `--llm` 那三条我写了「跑三遍稳定」——这两句话的区别应该是**格式上**明显的，
而不是靠读者细读。
可执行做法：档案里的「结果与总结」只许引用可重复的测量；
单次真跑一律进 devlog 的「观察」一节，且必须连不利的那次一起贴。
