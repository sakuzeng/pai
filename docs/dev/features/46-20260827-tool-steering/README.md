## 需求

用户 2026-08-27 从 feature 45 的发现清单里点名「A1 + A2 一起做」。

- **A1**：`build_system_prompt` 生成的整份系统提示里只有一句工具引导，
  而它是给 `edit_file` 的；`search_files` / `run_tests` / `git_read` 一句都没有。
  而模型确实只听了那一句。A/B 实测：`run_tests` 在任务明说「跑测试」时零次被选中、
  走 bash、7 次权限弹窗、烧完预算没做完；加一句引导后 1 次调用、0 弹窗、9 秒完成。
- **A2**：「把活从 bash 摘出来」只摘走了一半。剩下的 bash 调用有结构性原因，
  不是模型不听话——① 没有工具能回答「这个项目长什么样」（`pwd && ls` 是两次真跑里
  的第一个调用，且必然弹窗）；② `search_files` 不接受单个文件当搜索根
  （当场验过：`错误：搜索根 …/output.py 不存在或不是目录`）。

两条必须一起做的理由（也是用户点名一起做的理由）：单做 A1 只把 bash 从 4 次降到
3 次，因为剩下的三次里有两次是探路；单做 A2 则模型仍然想不到去用新工具。

诚实边界（45 复盘质疑二，抄在这里免得自己忘）：A/B 的整体数字是平淡的
（bash 4 → 3），`run_tests` 那个 0 → 1 的漂亮对比是我专门挑了一个只需要它的任务
验出来的。引导对「有专用工具且意图明确」的场景有效，对探路型步骤基本没用——
而后者正是 A2 要补的那一格。

验收标准：

1. **必须有一条能证明「真模型会选它们」的验收**，而不是断言提示语里有那几个字。
   feature 45 的全部教训就是离线全绿证明不了这件事。
2. 注入的项目结构要有规模上限，且超了要说清截了多少、去哪看。
3. `search_files` 吃单个文件不许改变它吃目录时的任何行为。
4. 新工具照 feature 43 的 `roots.py` 接线（`path_semantics`），
   不再手写第四份「默认根解析 + matcher 包装」。
5. 每条改动做注入反证；`./test.sh` 全量绿，STATUS 数字同步。

## 候选方案与确认

四处形状由用户 2026-08-27 用 AskUserQuestion 一次拍板，四问全选推荐项。

### 问 1：工具引导写在哪里？

模型有两个决策时刻：读系统提示时、在 schema 里挑工具时。

- 候选 A·两处都写（用户选中）。system prompt 里按工具条件化加引导句
  （照现有 `edit_file` 那句的形状），同时收紧 `bash` 的工具描述
  （「先确认没有更合适的专用工具」）。两个决策时刻各盖一个。
  诚实边界：A/B 数据只覆盖了 system prompt 那一半，工具描述那一半是外推。
  代价：同一件事说两遍，将来加工具要改两处。
- 候选 B·只写 system prompt。我 A/B 实验用的就是这个，有数据，改动最小。
  代价：模型真正「挑哪个工具」那一刻看的是 schema 里的工具描述，
  而 system prompt 在很前面——长会话里它离决策点越来越远。
- 候选 C·只收紧工具描述。就近，且符合「schema 与代码同源」（加工具时只改工具自己）。
  代价：零实测数据；且要在 bash 的描述里写「别用我」，读起来很怪。

用户选 A。

### 问 2：「这个项目长什么样」怎么给？

- 候选 A·装配期注入 + 新工具兜底（用户选中）。开场把工作目录 + 一份紧凑的结构
  摘要注入 system prompt（这一步直接消掉 `pwd && ls`，顺带修掉 45-C4
  「模型不知道自己 cwd」）；再加一个 `list_dir` 工具，给会话中途新建的目录兜底。
  CC 就是这两手都有。代价：本轮从两件变三件；摘要每个会话固定花 token。
- 候选 B·只加 `list_dir` 工具。不花固定 token，不会过时。
  代价：模型仍要「想到」调它，而那正是 A1 要解决的问题；且开场那一步仍然要花
  一轮工具调用与延迟。
- 候选 C·只做装配期注入。改动最小且直接消掉最高频的那条 bash。
  代价：会话中途模型自己建了目录/文件，摘要就过时了，而它没有任何办法重新看一眼
  ——只能回去走 bash。
- 候选 D·扩展 `search_files`：`pattern` 为空且不给 glob 时输出目录树。不加新工具。
  代价：一个工具三种模式（内容搜 / 文件名搜 / 目录树），schema 表达不出三者互斥，
  模型更容易用错——而我在 feature 41 复盘里已经质疑过「两种模式塞在一个工具里」了。

用户选 A。

### 问 3：目录结构的规模怎么控？

- 候选 A·深度 + 条目双上限，复用 `SKIP_DIRS`（用户选中）。默认深度 2、总条目上限，
  噪音目录直接复用 `search_files` 的那份名单；超了截断并说清截了多少、去哪看。
  不依赖 git，任何目录都能用。代价：不尊重 `.gitignore`（同 `search_files` 的既有诚实边界）。
- 候选 B·走 `git ls-files`。天然完美尊重 `.gitignore`。
  代价：非 git 仓库完全用不了，得再写一条回退路径；且刚建还没 `add` 的文件看不见
  ——而那恰恰是 agent 刚写完想确认的那些。
- 候选 C·只列目录不列文件。最紧凑。
  代价：模型想知道「这个目录里有哪几个文件」时仍无处可去，
  而真跑里它第二次 bash 干的正是这件事（`find src -name '*.py'`）。

用户选 A。

### 问 4：怎么验收「模型真的会选它们」？

- 候选 A·写成 `--llm` 测试（用户选中）。给定意图跑真模型，断言它选中了专用工具。
  默认跳过，`./test.sh --llm` 一条命令验。这正是 45 复盘「下次怎么做更好」那条的
  落点，且仓库已有这个形状（`tests/test_llm_smoke.py` 的头部注释写着
  「写下来是为了让『验一次』变成一条命令」）。
  代价：跑才花钱；模型有随机性，断言得写成能容忍的形状。
- 候选 B·只写离线单测（断言提示语里有那几个字）。零成本、稳定。
  代价：证明不了模型会选——而 feature 45 的全部教训恰恰是这个。选它等于把刚学到的
  那条丢了。
- 候选 C·手动真跑一次，把工具调用序列贴进档案（就像 feature 45 这次）。
  代价：不可重复。下次有人改了提示词，没有任何东西会变红——
  而那正是四轮工具建设默默失效的机制。

用户选 A。

## 结果与总结

做了，全量 `1683 passed`（此前 1656）。过程见 [devlog.md](devlog.md)。

- **A1**：`build_system_prompt` 加五句条件化引导（read_file / search_files /
  run_tests / git_read / list_dir），`bash` 的工具描述收紧成「先确认没有更合适的
  专用工具再用它」。两个决策时刻各盖一个（拍板问 1·A）。
- **A2 前半**：新增 `list_dir` 工具 + 装配期把 cwd 与项目结构摘要注入 system prompt
  （拍板问 2·A）。顺带修掉 45-C4「模型不知道自己 cwd」。
- **A2 后半**：`search_files` 接受单个文件当搜索根。
- **验收**：`tests/test_llm_steering.py` 三条 `--llm` 测试（拍板问 4·A）。

验收标准五条的对账：

1. 有一条能证明「真模型会选它们」的验收 —— 三条 `--llm` 测试，真跑三遍
   全过（8.11s / 7.06s / 6.92s）。这是本轮唯一能证明它有用的东西。
2. 结构摘要有规模上限且说清截了多少、去哪看 —— 有，且**两次调整都是生成出来
   一看就不对**（见 devlog：`tests/` 吃光预算、`src/` 整个消失）。
3. 单文件不改变吃目录的行为 —— `test_directory_behaviour_is_byte_for_byte_unchanged`
   逐字比对整段输出。
4. 照 `roots.py` 接线 —— `list_dir` 用 `path_semantics("path")`，没写第四份。
5. 注入反证 7 条全红；全量绿；STATUS 同步。

**端到端的数字很吵，如实说**：同一个真实问题跑两次，一次是 7 调用 / 2 弹窗
（对照 45 的 8 / 4），一次是 12 调用 / 5 弹窗（模型自己跑到父目录去搜了）。
本轮不拿这些单次数字声称改进——n=1 不是测量。三个数（含更差的那次）都贴在 devlog 里。

## 遗留问题

每条已同步登记 TODO（「feature 46 遗留与发现」节）。

- 端到端效果没有可信的测量方法：单次真跑方差极大，而多次跑要花钱花时间。
  `--llm` 测试只验「给定意图会不会选对工具」，验不了「整条轨迹变好了没有」。
- `list_dir` 在真跑里被选中过一次、也被 `ls` 顶掉过一次。引导句写了，
  但没有数据说明它有多稳。
- 结构摘要的三个常数（`MAX_ENTRIES=120`、`MAX_FILES_PER_DIR=8`、`DEFAULT_DEPTH=2`）
  都是看着生成结果调出来的，**只在本仓库上调过**。
- 摘要不尊重 `.gitignore`（拍板问 3 的直接代价）：本仓库的 `pai_playground/`
  是 gitignore 的，照样出现在摘要里。
- 引导句已经五句，都堆在 system prompt 里；加第六个工具时这一段会开始显得长。
