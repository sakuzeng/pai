## 需求

用户 2026-08-26：「还有输出的 md 的预览而不是原文，还有表格等，这些和交互外观
有关的都需要优化」。

模型的回答是 markdown，而 TUI 今天原样打出来：`## 标题`、`**粗体**`、
围栏代码块的三个反引号、以及最难读的表格（`| a | b |` 那一堆竖线在中英混排时
完全对不齐）。

动工前核实的四条（每一条都决定了候选长什么样）：

1. **TUI 里答案不是逐字上屏的**。`MessageDelta` 只累加进 `app._streaming`，
   直到 `AssistantMessage` / `AgentEnd` 才由 `_flush_answer` 一次性 commit。
   这是结构性的——scrollback 的行一旦交出去 pai 就够不着（feature 13 的形态）。
   于是 md 渲染最难的那个问题（表格没收完没法排版）在 TUI 里根本不存在。
2. REPL / once（`modes/echo.py`）是真的逐字写 stdout，那里渲染与流式是真冲突。
3. 运行时依赖只有 `openai` + `python-dotenv`，没有任何渲染库。
4. `tui/width.py` 的 `display_width` 已经是 CJK 感知的、且会剥掉转义符；
   `theme.wrap` 折行时也整段吞掉转义序列不计列。表格列宽必须靠它们——
   用 `len()` 会把中文算成 1 列，那正是 md 表格在中英混排下对不齐的原因。

验收标准：

1. 中英混排的表格要真的对齐——判据是「每一行的 `display_width` 相等」，
   不是「看起来还行」。
2. `color=False` 时一个转义符都不许吐（theme 的既有硬约束）。
3. 渲染结果要能跟着窗口宽度重排（走 `dynamic_entry`），拉宽窗口表格跟着变。
4. 不认识的 md 语法要原样透出，不许吃掉内容——渲染器把一段文字弄丢，
   比不渲染糟得多。
5. 每条改动做注入反证；`./test.sh` 全量绿，STATUS 数字同步。

## 候选方案与确认

四处形状由用户 2026-08-26 用 AskUserQuestion 一次拍板，四问全选推荐项。

### 问 1：md 渲染在哪几条路上做？

- 候选 A·只做 TUI（用户选中）。TUI 里答案一次性 commit，与流式没有冲突；
  且 transcript 能按宽度重排，拉宽窗口表格跟着变。
  代价：REPL / once 仍是原文——但那两条路本来就是「管道友好」的定位
  （once 的输出常被别的程序吃，给它上色加框反而是害）。
- 候选 B·TUI + REPL 都做。代价全在 REPL：要么攒完再渲染（等于放弃逐字上屏，
  那是 feature 11 交付的东西，且长答案时屏幕会冻住好几秒），
  要么逐字流完再重打一遍渲染版（同一段内容在屏上出现两次）。两条都是真损失。
- 候选 C·不做完整渲染，只把最刺眼的（代码块、表格）美化一下。
  代价：「对齐表格」本身已经需要完整解析表格语法了，而解析器一旦存在，
  再支持标题与列表只是多几行——这条省不下多少。

用户选 A。

### 问 2：自己写还是引第三方库？

- 候选 A·自己写一个子集（用户选中）。复用现有的 `width.display_width`
  与 `theme.paint` / `theme.wrap`，不引入第二套宽度/颜色体系。
  代价：只能支持一个子集，表格列宽算法要自己写。
- 候选 B·引 `rich`。现成、好看、支持完整。代价三条：运行时依赖从 2 个变成 7 个
  左右；rich 自带一套宽度/颜色/主题体系与 `tui/width.py`、`tui/theme.py` 并存，
  而两套宽度计算正是 feature 13「满屏阶梯」那类 bug 的温床；
  且它输出成品字符串，而 pai 的 transcript 要的是「给宽度返行数组」，接口对不上。
- 候选 C·引一个只做解析的小库（markdown-it-py / mistune），渲染仍自己写。
  代价：解析不是这里的难点（难点是终端排版与列宽），买到的东西不多；
  而一个完整的 CommonMark AST 会把人推向「那就把剩下的元素也渲染了吧」。

用户选 A。

### 问 3：渲染哪些 md 元素？

- 候选 A·块级 + 行内基本集（用户选中）。标题、围栏代码块、表格、有序/无序列表
  （嵌套一层）、分隔线、引用块；行内的粗体/斜体/行内代码。
  不做：链接、图片、脚注、任务列表、嵌套表格。
- 候选 B·基本集 + 链接。代价：pai 没有网络工具，回答里链接本来就少；
  且长 url 会把行撞爆，又多一条折行规则要写。
- 候选 C·只做代码块 + 表格 + 行内代码。代价：解析器都写了，标题与列表只是
  多几行；而一份渲染一半的输出反而比全原文更奇怪。

用户选 A。

### 问 4：表格比终端还宽时怎么办？

- 候选 A·按列压缩 + 单元格截断（用户选中）。先按各列最宽内容定列宽，
  总宽超了就按比例压（给每列一个最小宽），单元格超列宽就截断加 `…`。
  代价：截断会丢信息，但丢得看得见；且 TUI 里窗口拉宽会按新宽度重排，
  信息会回来——这一条是 TUI 独有的，打进 scrollback 就回不来了。
- 候选 B·窄屏降级成「列名：值」的键值块。一个字不丢。
  代价：没了对齐，而表格的价值就在对齐（纵向一眼扫下去比大小）；
  且行数翻好几番，5 行 × 4 列变成 20 行。
- 候选 C·不管，让它横向溢出。代价：终端一折表格就碎，比原文还乱；
  且这正是 feature 12/13 反复踩过的那个坑（「我以为写了 1 行、实际占了 3 行」）。

用户选 A。

## 结果与总结

做了，全量 `1656 passed`（此前 1628）。过程见 [devlog.md](devlog.md)。
本轮没有够格升格进 decisions 的取舍：形状选择都在既有决策之内，
与三家参照也没有新分歧（CC 同样自己渲染 md，pai 只是子集更小）。

- `src/pai/tui/markdown.py`：按行扫描分块（围栏 / 标题 / 分隔线 / 表格 /
  引用 / 列表 / 段落）+ 行内（粗体、斜体、行内代码，成对才算标记）。
  复用 `width.display_width` 与 `theme.paint`，不引第二套宽度/颜色体系。
- `app._answer_entry` 走 `dynamic_entry`：表格跟着窗口宽度重排。
- `settings.markdown_enabled`（`tui.markdown`，默认开）+ 装配接线：
  纯视觉改动留一个退得回去的口子。

两处在实现中做的调整，都记在这里而不是悄悄做掉：

1. **代码块不做右边框**（拍板时的预览是完整的框）。左栏 + 上下沿少了「每行补到
   定宽」这一步，于是长代码行可以折行而不是截断——截断的代码复制出去是坏的。
2. **单换行按硬换行处理**，不按 CommonMark 的软换行。这条是既有 e2e 撞出来的
   （见 devlog）：对话文本与文档文本在这一点上取向相反。

验收标准五条的对账：

1. 中英混排表格真的对齐 —— 判据用了两条：每行 `display_width` 相等，
   以及**每一列的起始列号在每行相同**（后者更强：等宽可以靠尾部补空格蒙混）。
2. `color=False` 一个转义符不吐 —— 一条断言；另有一条钉「上色不改变任何一行的
   显示宽度」，否则有色终端上表格会塌。
3. 跟着宽度重排 —— 接线测试直接对 `TranscriptEntry.render(24)` 与 `.render(90)` 断言。
4. 不丢内容 —— `test_nothing_is_lost` 逐个断言实义词还在；
   另有整体逐字比对与「没有 md 语法的文字渲染前后一模一样」两条守卫。
5. 全量绿 + STATUS 同步 —— 都做了。注入反证 9 条全红；另在真渲染上冒烟两次，
   第二次看出中文标点顶行首并补了禁则处理。

## 遗留问题

每条已同步登记 TODO（「feature 44 遗留与发现」节）。

- REPL / once 仍是原文（拍板问 1 的直接代价，不是疏漏）。
- 链接不渲染（拍板问 3 明确不做）。
- 框线字符（`─ ━ │ • ◦ ┌ └`）是 East Asian Width = Ambiguous，
  部分 CJK 终端按 2 列画，会让这些行整体右移一格。表格分隔行已避开（用 ASCII `-`），
  其余没避。
- 表格极窄时每列只剩一个省略号（`MIN_COL_WIDTH` 在极端宽度下压不住）。
- 代码块没有语法高亮，整块一个颜色。
- 禁则只做了「避头」，没做「避尾」（行尾的开引号/开括号）。
