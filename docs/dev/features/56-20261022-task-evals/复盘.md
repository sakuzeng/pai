# 56-task-evals · 复盘

## 学到了什么

评测隔离至少有配置发现、pytest 配置加载和执行/判分三个边界。新 cwd/HOME 不保证祖先指令不加载；confcutdir 不会隔绝另一棵源码树的 conftest；退出 0 不保证实际断言被执行。
这些机制已沉淀为 [知识笔记](../../../../knowledge/engineering/evaluation-isolation.md)，进程组机制链接既有笔记，不复制正文。

## 哪里走了弯路，为什么

我先写了完整推荐 spec，再让用户整体同意，省略了应展开的取舍。用户追问后恢复逐项候选，原始问答保留；已确认的范围和费用没有再问一次。
我还把同步选择工具的 Default 限制泛化成「必须切 Plan」，而异步单选随后在同一模式下明确收到回传。根因未查明就给出切模式结论，是把局部报错当整体能力判断。
评分实现初版相信 JUnit 的 type 属性和测试退出码，随后被参考解/空测试/全跳过/祖先 conftest 反证推翻；红输出全部保留，不能靠最终全绿抹掉这些过程。

## 我现在质疑什么

三个任务各三次均成功，仍然不能证明真实开发已经可靠。题目很小、需求明确、没有长期上下文；100% 容易给后续功能选择带来错误信心。
同时存在 5 次 bash 请求被拒绝，说明只看成功率会漏掉绕路成本。当前没有对照组，无法归因于提示词或权限策略；不在这组数据上调题调提示词。
这些问题沿用 TODO 的 feature 47 案例代表性/保留集、bash 场景与测量收益条目，没有为本轮结果额外制造一个已确认 bug。

## 下次怎么做更好

开始写 spec 前先列出已确认与未确认的取舍；把影响结果含义的候选一次讲清，再由用户选择，不让用户替实现文档做笼统背书。
下一次要改提示词时，先准备独立的真实任务/保留集，再冻结判据做重复对照；保留本轮原始基线，不用同一组失败题既调参数又验收益。具体触发和出处见既有 TODO。
