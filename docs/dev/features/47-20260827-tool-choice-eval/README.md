## 候选方案与确认

四处形状由用户 2026-08-27 用 AskUserQuestion 一次拍板，四问全选推荐项。

### 问 1：主路线——降方差，还是加样本？

- 候选 A·先降方差，测单步选择的分布（用户选中）。不跑整条轨迹：固定上下文，
  只看模型「下一步调哪个工具」。每次只是一次很短的 completion，成本极低，
  且直接测的就是我这几轮改的东西（工具选择）。
  代价：只测一步——模型可能第一步选对、后面仍然绕路。
- 候选 B·加样本：固定任务集 × N 次 × 统计量。真正测整条轨迹。
  代价：贵且慢（实测一个只读任务约 20k token / 13s，一个改代码任务 131k / 59s），
  且实测方差之大（7 调用 vs 12 调用）让 N=5 未必分得开。
- 候选 C·两者都做。覆盖最全，但第二套的成本与阈值我一个数据都没有，
  很可能先做出来再发现 N 取多少是另一个问题。

用户选 A。

### 问 2：temperature 怎么处理？

- 候选 A·只给评测用低温，产品行为不变（用户选中）。
  代价（诚实边界）：测的是「改动带来的差异」，不是「你真实的体验」。
- 候选 B·产品默认也调低。好处是测的就是真用的。
  代价：这是一个改变所有人体验的改动，而我手里一个数据都没有——
  恰恰是因为没有测量手段才要做这一轮，先改默认再建测量是把顺序反了。
- 候选 C·不动 temperature，靠加样本压方差。代价：样本要花钱，而实测方差很大。

用户选 A。**实现时发现这条不需要任何产品改动**：评测夹具直接调 API
（不经 `run_agent`），`temperature=0` 传在它自己的请求里。
所以 `config.py` 与 `loop.py` 一行没动，`pai` 的行为逐字不变。

一处两个答案组合起来才看得清的推论：`temperature=0` 会让**同一个 case 采样多次
退化成同一个点**，所以「分布」必须来自**多个 case 各采一次**，而不是一个 case
采多次。这与拍板预览里那个 `17/20` 的形状一致，且换来了确定性与可重复。

## 预先注册的期望

写于实现完成、跑第一次之前。跑完在「结果」一节逐条对照，
**不许事后改这一节**（改了就等于没预注册）。

案例集：18 条固定的（意图 → 期望工具）。其中 14 条专用工具该赢，
4 条 bash 该赢（防止指标奖励「一律选专用工具」）。
两个变体各跑一遍：`有引导`（feature 46 之后的真实提示词）与
`无引导`（feature 46 之前那份提示词的原样抄写，冻结在测试里当对照组）。

1. **有引导的总命中率 ≥ 14/18。** 低于这个说明引导没起作用，或案例集写得不合理。
2. **有引导 − 无引导 ≥ 3 个 case。** 这是「引导有用」的最低门槛；
   低于 3 说明 feature 46 的收益在单步选择上也不明显，
   那我在 45/46 两轮里对 A1 的判断就要重估。
3. **bash 该赢的 4 条，两个变体都 ≥ 3/4。** 引导不该把 bash 挤掉——
   把「一律不用 bash」当成进步是这个指标最容易被玩坏的方式。
4. **同一变体连跑两次，总命中率相差 ≤ 1 个 case。** 这是「可重复」的门槛；
   不满足的话 `temperature=0` 没有买到它该买的东西，整个方法作废。

## 结果与总结

测量建成了，而它报的第一件事是我上一轮的改动效果为零、且有一处回归。
过程见 [devlog.md](devlog.md)（含三次被证伪的中间跑）。

### 预注册的四条，逐条对照

| 预注册 | 期望 | 实测（定稿） | |
|---|---|---|---|
| 1 有引导总命中率 | ≥ 14/18 | **14.80/18（82%）** | 兑现 |
| 2 有引导 − 无引导 | ≥ 3 个 case | **0.00** | **证伪** |
| 3 两变体负例 | 都 ≥ 3/4 | 有引导 2.60/4、无引导 3.00/4 | **证伪** |
| 4 同一变体重复性 | 差 ≤ 1 个 case | 采 1 次时 14/14/16；**采 5 次后满足** | 先证伪、修方法后兑现 |

预注册这一节**没有改过一个字**（改了就等于没预注册）。

### 三条结论

一、**加引导与不加引导，在这个 18 case 的单步测量上分不出来**（14.80 vs 14.80）。
唯一稳定占优的是「跑一下这个项目的测试」（80% vs 60%），正是 feature 45
实测发现的那一条。也就是说引导在**它被设计来解决的那个意图上**有效，不外推——
我在 45/46 里说的「瓶颈在提示层」讲大了，那是从一个精心挑选的场景外推出来的。

二、**引导把 bash 该赢的场景弄差了**：首次定稿有引导 2.40/4、无引导 3.20/4，
「起一个 http server」5 次里 5 次去选 `list_dir`。只写「别用 bash 干 X」
而不写「bash 是用来干什么的」，模型学到的是「少用 bash」而不是「按活选工具」。
本轮据此补了一句给 bash 划回地盘，2.40 → 2.60，**仍低于无引导，没修完**。

三、**`temperature=0` 在这家 provider 上不给确定性**。逐字冻结的对照组提示词
三次跑出 14/14/16；直接探针：同 case 同提示词采 6 次，5:1。
这推翻了本轮方法的原始前提，而抓到它的正是预注册第 4 条——
它写的就是「不满足的话整个方法作废」。修法是每条 case 采样 5 次按命中率计分。

### 一处计划外的产品改动

补 bash 那句引导不在本轮计划里（拍板问 4 明确「只做测量」）。
加它的理由：这一轮交付的就是「能抓到回归的测量」，而它抓到的第一个回归是我
上一轮引入的——建好工具却把它报的警搁着，比不建更糟。
改动只有一句提示词，且被这套测量本身覆盖着。
