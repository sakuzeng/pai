## 预注册的四条，被自己的检查连打两次（2026-08-27）

判据写于跑第一次之前，存在档案 README 的「预先注册的期望」一节。

**第一跑**（每条 case 采一次，无项目上下文）：
有引导 15/18、无引导 14/18，差 1（预注册要 ≥3）。负例：有引导 3/4、无引导 2/4。
→ 预注册 2、3 未兑现。

看未命中的内容，发现夹具有两处**与数字好不好看无关**的真缺陷：

1. **没给项目上下文**。我发的是裸系统提示，模型两眼一抹黑，
   「跑一下测试」之前先 `list_dir` 看看有什么其实是合理的。
   测量的上下文必须像真实使用，否则测的是模型在一个不存在的处境里的行为。
2. **改函数那条 case 本身没有正确答案**。`edit_file` 需要精确原文，
   所以「先 `read_file` 再改」才是对的行为，而我把它记成了未命中。
   改成把原文写进意图里。

**第二跑**（修好夹具，仍每条采一次）：有引导 15/18、无引导 14/18——差还是 1。

**第三跑**：有引导 14/18、无引导 **16/18**，对照组反超。
而对照组的提示词是**逐字冻结**的，三次却给出 14/14/16。

于是直接探针：同一份冻结提示词、同一个 case、采 6 次 →
`run_tests` 5 次、`list_dir` 1 次。**`temperature=0` 在这家 provider 上不给确定性。**

这推翻了整套方法的前提（低温 ⇒ 一个 case 采一次就够）。抓到它的正是
预注册第 4 条——它写的就是「不满足的话整个方法作废」。

## 修方法：每条 case 采样多次（2026-08-27）

`Outcome.picked` → `Outcome.picks`（元组），`hit` → `hit_rate`（浮点），
`score` 按命中率求和而不是数布尔。取多数会把 3/5 与 5/5 抹成同一个数，
而那正是改提示词时要看的东西。`SAMPLES = 5`，18×5×2 = 180 次请求约 5 分钟。

## 测量的第一件事：抓到我自己上一轮的回归（2026-08-27）

5 次采样后的定稿：

| | 有引导 | 无引导 |
|---|---|---|
| 总命中 | 14.80/18（82%） | 14.80/18（82%） |
| bash 该赢的 | 2.60/4 | 3.00/4 |

两条结论，都不客气：

一、**加引导与不加引导分不出来**。预注册 2（≥3 个 case）被决定性证伪。
唯一稳定占优的是「跑一下这个项目的测试」（80% vs 60%），
正是 feature 45 实测发现的那一条——引导在**它被设计来解决的那个意图上**有效，
不外推。我在 45/46 说的「瓶颈在提示层」讲大了。

二、**引导把 bash 该赢的场景弄差了**（预注册 3 被证伪）。首次定稿是
有引导 2.40/4 vs 无引导 3.20/4：「起一个 http server」5 次里 5 次去选 `list_dir`。
只写「别用 bash 干 X」而不写「bash 是用来干什么的」，模型学到的是
「少用 bash」而不是「按活选工具」。

据此补了一句：「bash 用来做上面这些工具做不到的事：跑任意命令、管道与重定向、
改权限、起进程。」复测 2.40 → 2.80 → 定稿 2.60。**仍低于无引导，没修完**，已登记 TODO。

这条改动不在本轮计划里。加它的理由是：这一轮交付的就是「能抓到回归的测量」，
而它抓到的第一个回归是我自己上一轮引入的——建好工具却把它报的警搁着，
比不建更糟。
