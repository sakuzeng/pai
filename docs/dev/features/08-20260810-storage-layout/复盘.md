# 08-20260810-storage-layout · 复盘

交付前写（规矩 8）。「做了什么」在 [devlog.md](devlog.md)，这里只记可迁移的东西。

## 学到了什么

**「把已知缺陷钉成测试」这个手法，比写进 TODO 有效得多。**
slug 碰撞（`/a-b/c` 与 `/a/b-c` 撞成同一个）写进 TODO 的下场是没人会读；
写成一条**断言它确实会撞**的测试，将来任何人想「顺手加个转义修好它」，
第一件事就是让这条测试变红，然后被迫读 docstring 里的理由（CC 同款、加转义就丢掉与 CC 一致的诉求）。
**TODO 是给想找活干的人看的，测试是拦住想改东西的人的。** 两者不可互相替代。

## 我现在质疑什么

**一、把「加 sessionId + cwd」并进本轮，可能是个不该开的口子。**
我给的理由是「本来就要动 SessionLog，各一行」——但这正是 scope creep 最常见的措辞。
按我自己刚立的判据（规矩 7），字段变更属于「改变交付结果」，理应独立立项；
我却用「顺手」把它收编了。它没出事，是因为恰好只有两个字段、且 `cwd` 确实是被 08 逼出来的
（集中存放导致信息丢失）。但如果下次「顺手」的是五个字段呢？
**判据应该加一句：「顺手」只在『不做它，本轮交付就是有缺陷的』时成立。**
`cwd` 满足（不加就丢信息），`sessionId` 其实不满足——它是搭便车的。

**二、R#15（同秒碰撞）也是搭车修的，而它是一笔两天前就登记的旧账。**
好处是一行代码顺手关掉；坏处是**它让本轮的 diff 不再纯粹**——将来查「文件名为什么带短 id」，
得先读懂 08 的 spec 才知道那是旧账不是新需求。**旧账搭车修，应该在提交信息里单独成句**
（我做了），但更好的做法或许是单独一个 `fix/` 提交。

**三、「输入历史仍用哈希」这条，我给的理由可能站不住。**
我说「可读性的价值在目录树里，不在同级文件名里」——听着有道理，但真实场景是：
用户今天正是**翻着 `~/.pai/history/e4887ef95b86e3ee` 问「这是什么」**才发现测试污染的。
如果那时文件名是可读的，他一眼就知道是哪个项目的历史，也许更早发现异常。
这条我倾向于承认当时判断错了，已登记 TODO 重新评估。

**四、没有做迁移，是用户拍的板，但我没提醒代价。**
「老数据直接删」执行起来是：用户自己去 `rm -rf ~/.pai/projects`。而**旧目录名是哈希**，
用户根本认不出哪个对应哪个项目——所以实际上只能全删。这个代价我当时没说，
用户是在信息不完整的情况下拍的板。**下次涉及数据删除的拍板，必须先说清「删的时候你能不能认出要删什么」。**

## 下次怎么做更好

拍板问答里凡是涉及**删除/迁移**的选项，必须附一句「执行时你会看到什么、能不能分辨」——
第四条质疑就是漏在这里。
