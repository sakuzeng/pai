# feature 31 复盘

## 学到什么

- 冒烟场景是 refactor 最合口径的护栏。「行为与输出逐字不变」这个验收，
  单测只能覆盖它断言过的那部分；功能测试 20260824 留下的 28 个冒烟场景
  断言的恰是用户可见面（warn 文案、信任问答、拒绝理由、工具集），
  重构后复跑 4 套全过，比「全量测试绿」多说了一层话。检查产物当回归资产，
  这次是顺手捡到的，值得当成惯例：独立测试留下的场景脚本别删。
- 测试先行会反过来定实现风格：要让关闭路径可打桩，装配方就得走
  `mcp.` 模块属性调用而不是顶层 from-import——先写红测试时就被迫想清了
  这一层，实现跟着测试的口径走，而不是反过来。

## 哪里走了弯路

- 没有大弯路（改动面在动工前的结构盘点里已经量过）。一个小教训：
  try/finally 的机械缩进用脚本做完后 diff 里 100 来行「只变缩进」，
  review 噪音大；当初 29 复盘拒绝大缩进的理由其实还剩一半成立，
  另一条路是把 REPL 主循环提成独立函数再包——没走，因为那会动更多行的
  「非缩进内容」，与「行为字面不变」的验收口径更难对齐。取舍记录在此。

## 我现在质疑什么（必答）

- `assemble` 的参数面偏宽（9 个关键字参数），差异点全走参数注入。
  第三个消费方（阶段 7 evals 的回放装配是候选）出现时，参数还会再长——
  届时该考虑配置对象或阶段函数，而不是继续加参数。现在不预防性抽象
  （dsh 同款戒律），但这条线要有人看着。
- `Assembly` 返回面偏宽：`loaded_skills`/`working_dirs`/`skills` 带出来了，
  可 interactive 重构后并不解包它们——带着是「未来可能用 + 可测」，
  但这就是轻微的 speculative generality。下次动这里时若仍无人消费，收窄。
- 候选 B（模块级全局注入位 set_catalog/set_tracker/set_memory_dir…）落选
  保留后，这些全局被 assemble 包了一层，反而更不显眼了。单进程 CLI 现实
  用法里互串未真实发生（conftest 的 REGISTRY 快照兜着测试），但「装配收敛
  让全局注入更隐蔽」这一点是本次改动的负外部性，B 的论据略微变强了。
  记录在需求池的落选条目旁不再展开。

## 下次怎么做更好

- refactor 类需求动工前先把「行为不变」的功能级护栏（冒烟场景）点一遍名，
  而不是依赖全量单测的间接覆盖——这次是恰好有现成的，下次未必。
- 大段机械缩进这类高噪 diff，提交信息里写明「该范围仅缩进变化」，
  给 review 者一个可跳过的锚。
