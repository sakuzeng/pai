# 52-word-wrap · 复盘

## 学到了什么

**一个缺陷推迟三轮，第四轮修它时发现成因和三轮前写下的不一样。** 44 复盘里我认的是
「逐字符折行会劈开英文单词」，45 实测记的三例也都读成「断点落在词中间」。真修的时候打印断点才看见：
`rules.py` 的断点在句点上，劈开词的是 44 为了标点避头加的那条规则——它把 `s` 挤下来陪句点。
换句话说，三轮前我登记的成因是对的一半，而修法要针对的是另一半。
可复用的一条：**修一个观察来的缺陷之前，先让代码自己说一遍它在哪一步做了什么**，
不要拿三轮前的笔记当事实。

第二条：两条排版规则叠加时，顺序是设计的一部分。避头和补词各自都对，先后不同结果不同。
写成「先算 keep，再依次收紧」比写成两个 if/elif 分支清楚——elif 那版恰恰漏掉了它们同时成立的情况。

第三条：按宽度区间跑断言真的能抓到东西。44 复盘写下这条经验，这轮第一次当主力用：
`range(24, 81)` 里只有 3 个宽度红，单点测试挑中它们的概率不到 5%。

## 哪里走了弯路

- 第一版实现按「断点自己是词字符」判断，跑完仍有 3 条红。我先怀疑是改动没生效（去读了一遍源码），
  再怀疑是别的折行路径（去查了 `_hard_wrap`），最后才加调试打印——顺序反了，
  打印断点是最便宜的一步，应该第一个做。

## 我现在质疑什么

- 词字符不含 `.` `/` `-`，于是 `docs/dev/STATUS.md` 可以断在 `/` 上，宽度 60 那次就断成
  `docs/dev` + `/STATUS.md`。读得出来，但一条路径被劈成两行仍然不好看。要不要把「路径」
  当成一个词，取决于窄屏下留白多少能接受——没有数据，先留着。
- 行尾空格是我顺手剥的，没有单独拍板。它改变了所有折行的输出（不只是词回退那些），
  代码块走的是 `_hard_wrap` 不受影响，表格自己补空格对齐也不受影响，所以 44 的测试全绿。
  但「顺手改了所有折行的输出」这件事本身值得被看见。
- `_hard_wrap`（代码块）仍逐字符断。注释说「代码里没有词」——可是代码里全是标识符。
  那条注释当时写的是「不找词边界」的理由，现在读起来不太站得住；只是代码块本来就常超宽，
  改了收益不明显。
- 这轮只做了六条里的一条。其余五条（token 预算、计时、footer、权限文案）还在 TODO，
  用户下次问「接下来做什么」时它们仍是第一梯队。

## 下次怎么做更好

- 修观察来的缺陷，第一步是打印真实执行路径，不是读代码也不是读旧笔记。
- 多条排版/布局规则叠加时，写成「一个 keep 变量依次收紧」，不写成 if/elif 分支。
- 顺手做的改动（本轮的剥行尾空格）也要在档案里单独写一行，否则它只活在 diff 里。
