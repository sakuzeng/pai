- pai 锚点：**已落地** `guards/design_gate.py` + `.claude/settings.json`（工作区自身的方案门禁，档案见 docs/dev/features/03-20260809-design-gate/）；pai 产品侧的权限层在 roadmap 阶段 4，挂点对应 pi 的 `beforeToolCall` / `afterToolCall`

## 概念

hook = 在 agent 生命周期的固定点执行外部命令/检查的挂点。CC 有 26 个事件，
对 pai 有意义的核心是四个：

- **PreToolUse**（工具调用前）——可返回 allow / deny / ask，**门禁的落点**
- **PostToolUse**（调用后）——记录与审计的落点（如 anna 的 read_log）
- **UserPromptSubmit** / **Stop**——输入预处理与收尾校验

## 门禁模式（为什么它重要）

把「先讨论再动手」这类提示词约束降级到**确定性层**的机制载体就是 PreToolUse：
命中受保护路径 → 用代码判定过程产物是否齐备 → deny（缺什么告诉模型，让它自己补）
或 ask（必须真人拍板的那一个节点）。三条铁律来自 anna 实战（详见 anna/gates.md）：

1. deny 模型可自救绕过，ask 不可伪造——ask 只用在刀刃上；
2. 记录与判定职责分离，记录器永不打断会话；
3. 门禁自己必须带测试 + 退出码三态（通过/不通过/**没检查**）。

**deny 之后的问答回路**（硬约束与软引导的接力）：deny 只硬拦「改代码」这一步，
拒绝理由（reason 文本）作为工具结果回到模型上下文，**引导**它走合法路径——
调 AskUserQuestion（选项式弹窗，用户选择作为工具结果返回）或纯对话把候选讲给用户。
拿到拍板后模型写确认块、改状态字段（档案在 docs/ 下不受门禁管，刻意的：
文档路通、代码路锁），再重试原操作即放行。边界：「去问」本身仍是提示词层，
模型可伪造确认块（留 diff 痕）；要让「问」也不可伪造，用 PreToolUse 的第三种
返回值 `ask`（宿主弹权限框，必须真人点）——anna 只在「方案齐备、只差拍板」
一个节点用它，pai 门禁 v1 未用，留作升级。另一已知旁路（R3#9）：hook 只匹配
Edit 类工具，Bash 重定向写文件可绕过——不拦（误伤太大），如实声明靠审查兜底。

## fail-open 还是 fail-closed：按**失败的代价**分场景（2026-08-11 追加）

门禁自己挂了（超时、崩溃、起不来）怎么办？这是设计门禁时必答、且极易一刀切的一问。

**先看两个独立实现选了什么**：pi 的 `emitToolCall` **不捕获异常**，上层转为拦截
（外部参照把「钩子异常被吞、默认放行」列为踩坑清单第 1 条）；CC 的分类器解析失败
即 block。**两个互不相干的实现选了同一个默认值：fail-closed。**

但 pai 一开始选了 fail-open（D#50），理由是「开发期门禁 `design_gate.py` 已有先例」。
**这是场景错配**，复议后（D#54）改成按场景分：

| 门禁类型 | 失败的代价 | 选择 |
|---|---|---|
| **运行期安全门禁**（挡 agent 动用户的机器） | 安全事故 | **fail-closed** |
| **开发期自律门禁**（挡 AI 改自己源码时没走流程） | 流程没走到 | **fail-open** |

后者选 fail-open 有个现实理由：一个写错的自律门禁会让开发**整个停摆**，
而人在那种情况下通常直接把门禁全关掉——等于一道都不剩。

**两处相反是刻意的，所以要各自加测试钉住**，否则日后一定有人来「统一一下」。

### fail-closed 的范围要收敛到「没拿到判定」

改成 fail-closed 时还有个精度问题：**「崩溃」在子进程语境下是有歧义的**。
脚本 `raise` 与脚本主动 `exit 1`，退出码都是 1，**分不出来**。
而 CC/pai 的协议把「其他退出码」定义为脚本*能够表达*的一种状态
（我跑完了、有问题、但别拦）。一并改成拒绝就是改掉协议本身，
且会让任何一个写得不严谨的钩子变成一道随机的墙。

最终的判据是**「调用方有没有拿到判定」**，而不是「被调用方有没有出错」：

| 情况 | 结果 |
|---|---|
| 超时、起不来（`OSError`，或 shell 的 126/127） | **拒绝**——没拿到判定 |
| 退出码 0 + 有效决策 / 退出码 2 | 按脚本说的 |
| 退出码 0 无有效输出 / 其他退出码 | 无意见——脚本表过态了 |

**进程内钩子与子进程钩子在这里能力不同**：pi 的钩子是进程内函数，
异常能被捕获，它**区分得出**「没跑完」；子进程只有退出码可看，分不出来。
抄别人的失败语义时，要先确认自己的钩子机制有没有同样的分辨能力。

**还有一条实现细节能让这整段变成死代码**：用 `shell=True` 起子进程时，
命令不存在**不会抛 `OSError`**——shell 自己吞掉并返回 127。
只捕获 `OSError` 的话，「起不来 → 拒绝」这条分支永远触发不到。
