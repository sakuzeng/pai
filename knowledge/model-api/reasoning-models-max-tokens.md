# 推理模型的 `max_tokens`：它不是省钱旋钮，是截断风险旋钮

- 来源：无单一外部原文。OpenAI 兼容协议的 `max_tokens` 语义 + 2026-08-11 在 pai 上对
  `deepseek-v4-flash` 的实测（features/10 的召回侧查询）
- 精读日期：2026-08-11
- pai 锚点：`src/pai/core/recall.py`（`RECALL_MAX_TOKENS`）、
  量测脚本 `pai_playground/smoke/recall_max_tokens.py`

任何给推理模型（reasoning / thinking 档）发「只要一个短答案」的请求的程序都会撞上这个。
它不报错，只是**概率性地返回空字符串**。

## 一、机制

OpenAI 兼容协议里 `max_tokens` 限的是 **completion 的总预算**，而推理模型的
`reasoning_tokens` **算在这个预算里**。于是一次请求的实际顺序是：

```
模型先烧 reasoning_tokens 思考 ──> 剩下的额度才用来吐 content
                                   剩 0 → content = ""，且 finish_reason 不一定是 length
```

**思考长度不受你控制，也不稳定**。同一个 prompt、同一个 query，实测三次的
`reasoning_tokens` 分别是 **218 / 112 / 1941**——差 17 倍。

## 二、实测（`deepseek-v4-flash`，同一 prompt 同一 query，跑了两次）

| `max_tokens` | 第一次 `reasoning` / `content` | 第二次 `reasoning` / `content` |
|---|---|---|
| 256 | 218 / 有 | 51 / 有 |
| 512 | 112 / 有 | **512 / 空**（预算全烧在思考上） |
| 1024 | 79 / 有 | 55 / 有 |
| 2048 | **1941** / 有 | 38 / 有 |

**两次结果不一样，这本身就是结论**：思考长度是抽签（38 ~ 1941，差 50 倍），
而且**不单调**——第二次跑里 512 失败而 256 成功。

所以「把上限调到刚好够用」这个思路根本不成立：**没有哪个小上限是安全的**。
截断的表现也不是报错，是 `content` 悄悄变成空串。

## 三、为什么容易踩

1. **抄来的常数带着它的模型假设**。`max_tokens: 256` 这种数字在非推理模型上完全合理
   （「只让它吐几个文件名，别写作文」），抄到推理模型上语义就变了——
   那 256 现在要先喂给思考。**常数是跟着模型类别走的，不是跟着任务走的。**
2. **失败是静默的**。空 `content` 通常会被解析成「模型什么都没选 / 什么都没说」，
   与「模型明确表示没有」不可区分。上层于是当成正常结果，不报错、不重试、不告警。
3. **离线测试测不出来**。假 provider 想返回什么就返回什么，永远不会替你模拟
   「思考把预算吃光」。这个 bug 只有真跑一次才会现形。

## 四、怎么做

- **给推理模型的 `max_tokens` 要给足**（几千量级），并在常量旁边写清楚为什么不能调小。
  计费按**真实用量**走，上限调高不额外花钱；调低省不到钱，只会静默丢结果。
- **把「没说话」与「明确说了空」在解析层分开**：解析不出结构 → 当故障（计数、告警），
  解析出了空列表 → 当正常判断。混为一谈，故障就永远触发不了任何保护。
- **真跑一次**。这类 bug 属于「离线全绿、线上全废」，只有一次真实请求能证伪。

## 五、同源的第二个坑：模型会把提示里的装饰一起抄回来

同一次实测撞到的：清单给的是 `- [feedback] 构建约定.md (今天): 描述`，
要求模型「只输出文件名」，它回的是 `"[feedback] 构建约定.md"`——**把行首的类型标记
一起抄了回来**。如果下游用「逐字相等」去校验白名单，会 100% 静默丢弃全部结果。

通用做法：**校验用白名单，匹配放宽一点**——在模型回的字符串里**找**一个已知标识符
（取最长匹配，否则 `a.md` 会抢走 `xa.md` 的票），而不是要求它逐字等于。
安全属性（不能选清单外的东西）由白名单保住，容错留给匹配。
