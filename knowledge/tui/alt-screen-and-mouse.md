## 一、`?1049h` 不是「切过去」，是「存光标 + 切过去 + **清掉**」

| 序列 | 干什么 |
|---|---|
| `\x1b[?1049h` | 保存光标 → 切到备用屏 → **清空备用屏** |
| `\x1b[?1049l` | 切回主屏 → 恢复光标（主屏内容原样，应用没法弄脏它） |

第三步「清空」是定义的一部分，于是有一条反直觉的后果：

> **已经在备用屏里再发一次 `?1049h`，屏幕会被清掉、光标回到 (1,1)。它不是幂等的。**

实测 iTerm2 3.6.11 与 Terminal.app 470.2 **都是这个行为**（光标从「行5」变「行1」，
iTerm2 抓屏确认先前内容消失）。这条值得单独记，因为**有真实源码把它写反了**：
CC `src/ink/ink.tsx` 里 `handleResize` 的注释说「iTerm2 treats ?1049h as a buffer
clear even when already in alt — that's the blank flicker」，
而同一文件 `reenterAltScreen()` 的 docstring 却说「a terminal-side no-op if already
in alt」。**前者对，且不是 iTerm2 独有。**

**工程后果**：任何「自愈式重进备用屏」（resize / SIGCONT / 睡眠唤醒 / ssh 重连之后
补一发 `1049h` 确认自己还在）都会闪一下白屏。要么别发，要么发完当帧全量重绘。

## 二、退出备用屏，主屏**原样还回来**——这是「像新开一个窗口」的技术基础

实测：进备用屏前打的 6 行文字、以及光标所在的行与列，在 `?1049l` 之后**逐字还原**，
备用屏里写的东西一个字都没漏到主屏。应用**不需要**自己保存/重放主屏内容。

代价不在这里，在别处（下面三节）。

## 三、鼠标上报：1000/1002/1003 是**互斥单选**，1006 是正交的编码开关

常见的抄法是一口气发四条（pi、CC 都这么写）：

```
\x1b[?1000h  \x1b[?1002h  \x1b[?1003h  \x1b[?1006h
```

发完再用 DECRQM 一条条问回来（iTerm2 实测）：

```
?1000 → 未设置    ?1002 → 未设置    ?1003 → 已设置    ?1006 → 已设置
```

**1000/1002/1003 是同一个旋钮的三个档位，后设的覆盖先设的**：

| 模式 | 上报什么 |
|---|---|
| 1000 | 只报按下与松开 |
| 1002 | 加上「按住键拖动时」的移动 |
| 1003 | **任何**鼠标移动都报（哪怕没按键） |

1006 不是「要不要报」而是「**怎么编码**」，所以能与 1003 并存：

```
按下：  \x1b[<0;12;3M          松开：\x1b[<0;12;3m     （区别只在结尾 M/m）
拖动：  按钮值 |32              滚轮：按钮值 |64（上=64、下=65）
坐标是 1-based，且没有老式编码 223 列的上限
```

**照抄那串四条序列 = 选了最费的一档**：鼠标划过窗口就有字节不断流进 stdin，
应用得逐条解析再丢掉。要点击与滚轮的话 1002 就够。

### 按钮位里最容易读错的一格：**低两位 3 = 没有按键**

```
button & 0b11 → 0=左 1=中 2=右 **3=没有按键**
button & 32   → 移动
button & 64   → 滚轮
```

于是 **`35`（32|3）是「没按键的移动」**，不是拖动。把它当拖动的后果很具体：
用户松手之后，选区还跟着鼠标走。pai 2026-08-11 真跑时就撞了这一条。

> ⚠️ **订正一条本篇早先的实测记录**：曾记「iTerm2 报不出无按键移动（1003 与 1002 无差别）」，
> 那是探针那两段用户在滚轮而不是移动指针造成的假象。
> **1003 确实上报无按键移动**——上面那个 bug 就是证据。
> 教训与本篇第五节同源：**没观测到 ≠ 不存在**，尤其当「没观测到」来自一次
> 你无法确认对方到底做了什么的手工操作。

## 四、拿走鼠标 = 拿走终端原生的「选中复制」

终端把鼠标事件转发给应用之后，用户拖选文字就不再是终端的选区了。
后果是**静默的**：用户拖一下，什么也没发生。

补救只有两条，都不便宜：
① 自己实现选区（CC 为此写了 917 行，含跨行、双击选词、拖到边缘自动滚、
   滚出视口的行要另存、软折行要拼回逻辑行，最后还要把文本**写进剪贴板**——见下）；
② 给用户一个关掉鼠标的开关（CC 有 `CLAUDE_CODE_DISABLE_MOUSE`，
   注释直说动机就是「让 tmux/kitty/终端原生的 copy-on-select 继续能用」）。

大多数终端还留了第三条**用户侧**的路：按住修饰键（iTerm2/Terminal.app 是 Option）
拖选可以绕过应用的鼠标捕获——但这属于「用户得知道」，不属于「产品做到了」。

### 自写选区之后，「复制到剪贴板」是另一个坑：**OSC 52 会被静默拒绝**

`\x1b]52;c;<base64>\x07`（OSC 52）是纯终端方案：不 spawn 进程、天然穿透 ssh。
但**实测 iTerm2 3.6.11 上它一个字都没写进剪贴板**（BEL 与 ST 两种结尾都试过，
剪贴板保持测试前的哨兵值）——多数终端出于安全默认禁止应用写剪贴板，
且**拒绝是静默的**：终端不报错，应用无从知道自己没写成。

配合第五节（DECRQM 不可移植，**问不出终端支不支持**），结论是：

> **不能只靠 OSC 52。** 本地要有一条系统剪贴板路径（macOS `pbcopy`、
> Linux `wl-copy`/`xclip`/`xsel`、Windows `clip.exe`），OSC 52 只当 ssh/tmux 场景的兜底。
> CC 正是这么分的（`termio/osc.ts`：`native` / `tmux-buffer` / `osc52`，
> 按 `SSH_CONNECTION` 分流）；而 pi 只发 OSC 52——**在这台机器上它的复制是坏的**。
> 参照实现跑得通，不代表在你的终端上跑得通。

## 五、**没法问终端「你支持什么」**——DECRQM 不可移植

`CSI ? Ps $p`（DECRQM）本该回 `CSI ? Ps ; 值 $y`，值里 0=不认识、1=开、2=关、
3/4=永久开/关。实测：

- iTerm2 3.6.11：12 条查询**全部规矩回复**（`?1016` 回「4=永久未设置」，即明确不支持）。
- Terminal.app 470.2：**12 条全部超时无回复**，而同一窗口里 CPR（`\x1b[6n`）**正常回**。

两条推论：

1. **能力探测得靠别的**（`TERM_PROGRAM` / `TERM` 环境变量、启发式、或者干脆
   「发出去、不认识就当没发生」——DECSET 对不认识的模式本来就是静默忽略）。
   CC 全靠环境变量判断，看源码时以为是偷懒，实测之后知道**是没得问**。
2. **探测本身会污染被测对象**：不被识别的查询序列在 Terminal.app 上会漏成可打印字符，
   把光标推走一列。本次差点因此得出「Terminal.app 退出备用屏时光标没还原」的错误结论——
   把查询顺序换一下，结论就反了。
   **测量手段与被测现象在同一根管子里，这是终端编程特有的一类假象。**
   同一类假象后来又撞了两次（读屏工具给的是复合视图、录制工具漏了一个写入出口），
   三次凑成了一条独立的方法论：[K engineering/instruments-lie.md](instruments-lie.md)。

## 六、备用屏里 resize：终端**不替你重排**

实测（iTerm2，127x27 → 72x15，应用故意不重画）：`SIGWINCH` 照常来；
屏幕内容**没有被合理重排**，超宽的行既没截断也没重折——不重绘就是脏的。

⚠️ **2026-08-11 交付后订正**：当时还记了一句「甚至混进了主屏的残留文本」，
后来用 `screencapture` 截真窗口证明**那是读屏工具（AppleScript `contents`）的假象**，
真实屏幕上没有主屏残留。**「终端不替你重排」成立，「终端会把主屏内容混进来」不成立。**
删掉错的那半句、留下订正记录，见
[features/13 evidence 第 7 条](../../docs/dev/features/13-20260811-alt-screen/evidence/20260811-alt-screen反向对照/说明.md)。

所以在备用屏里，**resize 之后不全量重绘 = 屏幕就是坏的**。
这与主屏模式的处理策略不同：主屏下应用只拥有底部若干行，重画那几行就够；
备用屏下整屏都归应用，整屏都得重来。

还有两条**只有真跑才会撞到**的（pai 交付前的反向对照撞出来的）：

- **`SIGWINCH` 处理器会在一帧写到一半时打断你**。信号处理器里调重绘，
  两帧的字节就交错写出去了；更糟的是后一帧会把「上一帧屏幕上有什么」覆盖成已画好，
  于是下一帧的 diff 以为没变化——**错位从此永久留在屏幕上**。渲染入口要么加重入保护，
  要么信号里只置标志位。
- **resize 之后，「这一帧和上一帧一样所以什么都不用写」不成立**：
  上一帧记的是**应用以为**屏幕上有什么，而终端刚刚背着它动过。要强制作废那份记忆。

（相关但别搞混：主屏模式下若应用持有整份文档，宽度一变有些实现会连
`\x1b[3J` 清 scrollback 一起做——那是**另一回事**，见
[K pi-tui-main-screen 第四节](../tui/pi-tui-main-screen.md)。）

## 七、备用屏带来的**新失败模式**：「我以为我在，其实不在」

主屏模式下没有「我在哪个屏」这个状态，也就没有它不一致的问题。备用屏有：

- 终端编辑器（vim/nano/less）自己会写 smcup/rmcup（就是 `?1049h/l`），
  **它退出时的 rmcup 会把你也带回主屏**，哪怕你本来就在备用屏；
- tmux detach→attach、ssh 重连、笔记本睡眠唤醒都可能重置终端的私有模式，
  **而这三件事都不发 SIGCONT**；
- 程序崩溃时若没走到清理代码，用户会被留在一个空的备用屏里。

配合第 1 条（重进不幂等、会清屏）与第 5 条（没法问终端），
**自愈只能是「有强信号时才做，且做完立刻全量重绘」**——猜不得，也问不得。
