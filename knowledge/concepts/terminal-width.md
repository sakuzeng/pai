# 终端宽度：为什么 `len(s)` 不是你要的那个数

- 来源：无单一外部原文。Unicode 东亚宽度（UAX #11）+ ANSI 转义序列 +
  2026-08-10 在 pai 上的实测（features/05 task 8）
- 精读日期：2026-08-10
- pai 锚点：`src/pai/modes/statusline.py`

任何要在终端里画一行东西（状态行、进度条、表格）的程序都会撞上这两个坑。
中文环境下第一个坑是必然会踩的。

## 坑一：中文占两列，`len()` 数的是字符不是列

```python
len("中文")                      # 2
display_width("中文")            # 4  ← 终端实际占的列数
```

判据是 `unicodedata.east_asian_width(c)`，返回六种之一：
`W`（Wide，汉字、假名）、`F`（Fullwidth，全角标点）算**两列**，其余算一列。

```python
def display_width(text: str) -> int:
    return sum(2 if unicodedata.east_asian_width(c) in ("W", "F") else 1 for c in text)
```

按 `len()` 截断到 80「字符」，一行中文实际会占 160 列——**撑破行、自动折行、
原地刷新（`\r`）之后残留上一行的尾巴**，画面直接烂掉。

诚实边界：`east_asian_width` 只是近似。`A`（Ambiguous，如 `±`、部分希腊字母）在
CJK 字体下是两列、西文字体下是一列，标准本身就说它依赖上下文；emoji 与组合字符
（`👨‍👩‍👧` 这类 ZWJ 序列）更是另一套规则。pi 为此依赖了专门的
`get-east-asian-width` 包。**pai 现在把 `A` 当一列，是个已知的近似**——
真出问题再引依赖，而不是先引。

## 坑二：ANSI 转义符不占列，所以**不能拿带颜色的串去量宽度**

```python
CYAN + "◐ bash" + RESET      # len 15，display_width 15，实际只占 6 列
```

`\x1b[36m` 这类序列终端不显示，但它在字符串里实打实占位置。
量宽度、截断都必须在**可见文本**上做。

**由此推出唯一正确的顺序**：

1. 构造 `(可见文本, 颜色码)` 的分段列表——**别提前拼**；
2. 按可见文本累加宽度，决定哪些段留、哪段要截；
3. **最后**才给留下来的段套颜色。

先上色再截断的后果不只是宽度算错——还可能**把转义序列从中间切断**，
终端收到半截 `\x1b[3` 会把后面的正常文本当控制码吞掉，画面从此错乱到下一次全屏重绘。

pai 第一版犯的是另一种：`color=True` 时干脆跳过截断（因为「有转义符量不准」），
而真 tty 上走的**正是**彩色路径——等于彩色输出根本没有宽度限制。
测试要剥掉转义符再量可见宽度才能照出来：

```python
visible = re.sub(r"\x1b\[[0-9;]*m", "", colored)
assert display_width(visible) <= width
```

## 坑三：截断要给省略号留位置

截到宽度 `width` 之后再追加 `…`，结果就是 `width + 1`（而且 `…` 本身在部分终端算两列）。
正确做法是循环累加时用 `width - 1` 当上限，给省略号预留。

## 单行原地刷新不需要 alt-screen

`\r` 回到行首 + `\x1b[K` 清到行尾，就能覆盖重画一行，滚动仍然交给终端。
alt-screen（`\x1b[?1049h`）是给「接管整屏并自己管布局」用的，画一行状态用不着。

配套的两条判断：

- **非 tty 就别输出转义符**（`stream.isatty()`），否则管道、CI 日志里全是乱码；
- 尊重 `NO_COLOR` 环境变量（社区约定：设了就别上色）。

## 为什么值得把渲染写成纯函数

`render(events, width) -> str` 不碰终端句柄，于是宽度、截断、颜色全部可以离线断言；
副作用（`\r`、`flush`、查终端列数）隔离在一个薄薄的 printer 里。
这也正是 pi 的 TUI 契约（`Component.render(width) -> list[str]`）的形状——
不是审美，是**唯一能把「画得对不对」写成测试的形状**。


## 补记 2026-08-11：emoji 的宽度是不确定的（feature 12 实撞）

中文占两列这条是**确定**的（East Asian Width = W/F），emoji **不是**：

- 很多 emoji 的 EAW 是 `W`，但不同终端按 1 列还是 2 列排版并不一致；
- 带变体选择符（U+FE0F）时更乱；
- 更前置的问题是**字体覆盖**——emoji 不在等宽字体里，缺字直接渲染成 ▯。

后果与本篇正文那条同源：**只要终端与应用对宽度的判断差一列，整行的光标定位就错**。

所以界面自己的字形一律用**文本呈现**的符号（`●` `✳` `└` `─` `❯` `⧗`），
并把它测住——遍历所有字形断言「码位 < U+1F000」且「不是宽字符」且「显示宽度为 1」。
审美判断不好测，物理约束好测。详见 [terminal-raw-mode.md](terminal-raw-mode.md) 第三节。

另一条同源的：`display_width` 必须**剥掉转义序列**（CSI/OSC/APC 都不占列）。
pai 起初只在「先按可见文本截断再上色」的前提下才正确，
一旦有零宽标记（TUI 的光标标记）嵌进文本就当场算错。
