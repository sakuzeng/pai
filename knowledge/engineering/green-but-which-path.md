# 绿的是哪条路：测试环境的巧合会让整批断言失去意义

- 来源：无单一外部原文。pai 在 2026-08-10 至 2026-08-26 之间撞到的四次同族事故，
  事后归纳（feature 15/16/20/36/38 各出一次）
- 精读日期：2026-08-26
- pai 锚点：`tests/fake_provider.py`、`src/pai/core/rules.py` 的 `_relative`、
  docs/dev/features/38-20260826-offline-real-gap/、docs/dev/features/36-.../复盘.md

一批测试全绿，通常被读成「这段行为是对的」。但绿只证明了一件事：
在这套测试环境里，那条被执行的路径是对的。当测试环境相对真实环境有某种巧合时，
被执行的可能根本不是你以为的那条路——而这种失败不会有任何症状。

四种巧合，形状不同、后果一样。

## 一、测试为了让被测路径跑起来而注入的参数，正是真实路径上会卡住的地方

pai 的压缩要同时满足两个条件才会触发：估算超过警戒线，且相邻两个锚点之间的
真实差值累计够大。离线测试一律直接传 `CompactionSettings(keep_recent_tokens=1)`
把第二个条件按到最低——于是压缩链路测试全绿，而在真实使用中它一次都没被触发过
（用户 2026-08-10 实测报告）。

判据：凡是测试为了「让它跑起来」而调过的参数，都要单独问一句
「真实取值下这条路还走得到吗」。走不到的话，这批测试证明的是另一条路。

## 二、基准为了让被测代码生效而注入的到达形态，恰是真实路径上不会出现的

pai 给鼠标拖动加渲染节流，离线基准量到 206ms → 14ms 的巨大收益。
真机复现时两列数字没有差别——基准用紧循环加假时钟喂事件，造出了「一批很多条」
的到达形态，而真终端是「很多批各一条」，节流在后者上根本不生效
（features/16 与 20 的两次结论相反，后者推翻前者）。

判据：性能基准要先说清「输入是怎么到达的」，再说吞吐。到达形态本身就是被测条件。

## 三、两个坐标系在测试环境里恰好相等

pai 的路径规则把「模型给的相对路径」按项目根解析，而模型的相对路径其实是相对
cwd 的。七条测试全绿，因为它们都在项目根下跑——两个基准重合，错的代码给出对的
答案。只有在子目录里启动时才现形。

判据：只要一段代码在两个坐标系之间搬运（cwd 相对 / 项目根相对 / 绝对；
本地时间 / UTC；字节 / 字符 / 列宽），就必须有一条测试让这两个坐标系不相等。
否则那批断言什么也没证明。

## 四、仪器把某个真实会变的量常量化，于是下游的分支永远走同一边

pai 的假 provider 对每一轮都回同一个 `usage`。而锚点簿记的正是这个数、
切点算法靠相邻锚的差值反推——差值恒为 0，切点永远算成「无可压」，
自动压缩在所有 e2e 里结构上不可达。没有任何测试因此变红，它们只是从来没走到那段。

这一种与前三种的区别：前三种让你以为验过了，这一种让那条路根本不存在。
详见 [instruments-lie.md](instruments-lie.md) 的骗法五。

## 共同的操作纪律

1. 交付一个功能时，除了「测试绿了」，还要能回答「它在真实条件下被执行过吗」。
   答不上来就说明这批测试的对象是测试环境，不是产品。
2. 给假的那一端（假 provider / 假时钟 / 假文件系统）列一张
   「它与真的哪里不同」的表，逐条问「这处不同会不会让某条路径不可达」。
   常量化的字段最值得查——真实世界里会变的东西被写成了定值，
   而下游可能正靠它的变化做判断。
3. 真实使用里报告的现象若与离线测试的结论相反，那本身就是最高优先级的线索，
   不是两条各自待办的条目。pai 那条「压缩从未触发」与「压缩测试全绿」
   并排放了十几天，谁也没被逼着回答「那绿的是什么」。
