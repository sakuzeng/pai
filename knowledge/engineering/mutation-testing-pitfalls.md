# 注入反证的坑：注错了和没测住，现象一模一样

- 来源：无单一外部原文。anna 的「门禁必须带测试」方法论回流
  （见 [hooks-gates.md](hooks-gates.md)、[anna/gates.md](../anna/gates.md)，本地不入库）
  + 2026-08-09 / 2026-08-11 在 pai 上做的三轮共十余条注入反证的实测
- 精读日期：2026-08-11（2026-08-26 追记第五条）
- pai 锚点：docs/dev/features/07-20260810-permissions/devlog.md、
  docs/dev/features/09-20260810-working-dir-boundary/devlog.md、docs/dev/roadmap.md

注入反证（把实现故意改错，断言测试确实变红）是验证「安全机制的测试不是摆设」
的标准手段，roadmap 把它写成了硬要求。做过两轮之后攒下三条教训，
换任何项目、任何语言都成立。

## 一、注入点会被前面的分支屏蔽，而屏蔽的现象 = 全绿

2026-08-11 的实例。求值链是这样的：

```
1 deny 规则 → 2 危险路径 → 3 用户显式配的 ask → 4 bypass → … → 7 兜底 ask
```

要验的性质是「第 3 步的 ask 与第 7 步的 ask 待遇不同」（前者 bypass 也要问、
后者 bypass 放行）。第一次注入：把第 4 步的 bypass 挪到第 7 步之前。

结果 14 条全绿。 第一反应是「这个性质没被测住」。

真相是注入没打中：第 3 步仍在 bypass 之前，照样先命中返回，性质根本没被破坏。
把 bypass 提到第 3 步之前才真正取消区分，测试立刻红。

每次注入之后先回答一个问题：我改的这行，在目标场景里真的会被执行到吗？

控制流靠前的分支会屏蔽靠后的注入点，而「被屏蔽」和「没有测试覆盖」
在现象上完全不可区分——都是全绿。这是注入反证最危险的失效模式，
因为它给出的是假阴性：你以为自己发现了测试漏洞，实际只是注错了。

### 「没被执行到」有两种成因，别混为一谈

上面那种是控制流层面的（前面的分支先返回了）。还有一种是测试用例层面的：
注入点没问题，但那条测试根本不走那条路。

2026-08-11（feature 13）的实例：注入「新内容一到就把视口拽回底部」，
断言那条「往回滚历史时视口不许被拽走」的端到端测试必须变红——结果全绿。
查下来：那条 e2e 里按了 PgUp 之后再也没有新内容到达，
`commit` 那个注入点在整条测试里一次都没执行。
补上「滚上去之后再问一个问题」这一步，注入立刻变红（连带打红两条离线测试）。

写反证时（不是跑完之后）先回答：哪一行代码会因为这个注入而执行到不同的结果？
那一行在这条测试里被执行几次？ 答不上来，说明测试还没覆盖那个场景，
该补的是测试而不是反证。

## 二、一个常量翻不出全部防线：正交的防线要分别注

2026-08-11 另一个实例：把权限求值顺序整个翻过来
（`deny → ask → allow` 改成 `allow → ask → deny`），打红 4 条。
但另一组 7 条复合命令测试一条都没红——求值顺序与「复合命令逐条要求」
是两条正交的防线，只验前者会给出「整个系统被测住了」的错觉。

注入点要覆盖每一条独立的防线，而不是找一个最显眼的常量翻过来交差。

判断方法：先把系统的防线列出来（这里是「顺序」「复合命令拆分」「不对称的
require_all」「边界判定」「免疫项」），每条至少一次注入。
七条注入里真正有信息量的，是那些只打红一小簇测试的——
它们证明了那一簇测试确实钉住了那一条性质。

## 三、红阶段就绿的测试，不具备本次鉴别力（但仍有价值）

TDD 的红→绿数字容易读出错觉。2026-08-10 那次：7 条新测试里有 2 条
在实现之前就是绿的——因为占位实现（朴素 fnmatch）恰好给出同样答案。
数字显示 `5 failed → 18 passed`，很漂亮，但那一步真正验到的只有 5 条。

那 2 条不是废的：它们钉的是未来的回归（「别在剥离包装器时顺手把环境运行器
也剥了」）。但它们不是本次实现正确性的证据，写 devlog 时要分清。

在 plan 的测试清单里给每条标 `[红]` / `[本就绿·防回归]`。
标不出来的，说明还没想清楚这条测试到底在钉什么。

## 五、反证不红时，先怀疑实现，不要先怀疑测试（2026-08-26 追记）

前面第一条讲的是「注入没打中」。2026-08-26 又撞到两次，形状不同、结论更要紧：
反证不红，有可能是实现里根本没有你以为的那行逻辑。

两个实例（feature 39，同一次交付里连着出现）：

- 拿掉心跳里的 `app.refresh()` → 测试照样绿。真相：`driver.poll` 自己已经在该
  重画的时候重画了，那句 refresh 从头到尾没有效果。多写的、无害的一行，
  和漏写的、有害的一行，在测试上的表现一模一样——都不会红。
- 拿掉退出时的「卸载心跳」→ 测试照样绿。真相有两层：那条测试第一版是假的
  （「调一下看有没有回声」，而心跳的契约就是吞掉一切异常，卸没卸载都没回声）；
  更要紧的是实现本身装卸不对称——装在 try 之前、卸在 try 的 finally 里，
  异常路径上永远不卸载。

所以顺序要反过来：反证不红 → 先去读一遍被改坏的那行真正在做什么 →
再判断是「注入没打中」「实现与设想不符」还是「测试确实没测住」。
先怀疑测试的代价是把好测试删掉，而那比留一条弱测试更糟。

配套的一条：注入反证选错位置，会给出「这条测试没用」的假结论。
同一次交付里验「中断 e2e 能不能红」时，第一次拆掉的是中断事件的发射，
测试照样绿——因为「已中断」这三个字有两个来源（事件渲染与收尾文案）。
换成拆「流式装配认不认中断标志」才红。

## 四、操作纪律

- 注入前备份、注入后 `grep` 确认无残留。七次注入里每次都是
  `cp 文件 /tmp/x.bak` → 改 → 跑 → `cp` 回来，最后 grep 关键行确认还原。
  忘了还原而恰好测试全绿，就把一个真实的洞提交进去了。
- 红字输出整段贴进 devlog，不写「都变红了」。哪几条红、红在哪一行，
  是这次注入有没有打中的唯一证据。
- 还原后复跑全量，不只跑相关文件。
