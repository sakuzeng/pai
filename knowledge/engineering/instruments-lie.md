# 观测工具会骗人：五种骗法，以及它们共同的验收判据

- 来源：无单一外部原文。pai 在 feature 13（备用屏）、14（录制回放）、16（鼠标与选区）里
  四次被自己的观测工具误导，事后归纳
- 精读日期：2026-08-11
- pai 锚点：`src/pai/tui/record.py`、`src/pai/tui/replay.py`、
  `tests/fake_provider.py`（骗法五）、
  docs/dev/features/13-20260811-alt-screen/复盘.md、
  docs/dev/features/38-20260826-offline-real-gap/

写终端 UI（或任何「结果只存在于一块屏幕上」的东西）时，你会给自己造一批观测工具：
录制器、回放器、屏幕模拟器、读屏脚本、假 provider。它们会以五种不同的方式骗你，
而其中三种在现象上都长得像「被测代码有 bug」，最后一种什么现象都不给。

四条都不是终端专属——换成日志采集、埋点、快照测试、录制回放型的调试器，同样成立。

---

## 骗法一：测量手段污染被测对象

发出去的探测本身改变了现场。

pai 的实例：用 `DECRQM`（`CSI ? Ps $p`）问终端「备用屏现在开着吗」。
Terminal.app 不认识这个查询，于是把它当成可打印字符吐在屏幕上，
光标被推走一列。而我正在测的恰恰是「退出备用屏之后光标有没有回到原位」——
于是量出「差一列」，差点写下「Terminal.app 不还原光标」这个错误结论。
把查询顺序换成「先读光标再问模式」，结论就反了。

判据：探测与被测现象是不是走同一根管子？
终端里是同一个字节流；HTTP 里是同一个连接；日志里是同一个 stdout。
是的话，先设计一次「不探测」的对照。

## 骗法二：全量记录器漏掉了第二个出口

它号称记录写给 X 的全部字节，实际只包住了一个写入者。

pai 的实例：录制器包的是渲染器的 `write`，而终端生命周期（进出 raw mode、
进出备用屏）走的是另一条路直接写 `sys.stdout`。于是录制文件里没有 `?1049h`——
回放时认不出这是一段备用屏录制，按「数换行估高度」建了一块比真实终端矮的屏，
帧末尾几行被钳在最后一行叠成一团。
看起来是渲染器画错了，其实是录制漏了。

判据：给「全量记录器」验收时，要问的不是「它记的对不对」，
而是「被记录的那个出口，是不是唯一的出口」。
做法：把写入点当成一个必须收敛的集合——`grep` 一遍谁在写 X，
而不是抽查几条记录看内容对不对（内容永远是对的，缺的那条根本不在里面）。

## 骗法三：读取工具给的是复合/滞后视图

它读出来的不是屏幕，是它自己拼的一个东西。

pai 的实例：用 AppleScript 的 `contents` 读 iTerm2 的屏幕内容，
在 resize 之后读到顶部有两行主屏的残留文本，与备用屏的内容混在一起。
据此差点得出「终端 resize 时会把主屏内容混进备用屏」这个结论（还写进了 evidence）。
后来用 `screencapture` 截真窗口——屏幕上干干净净。

判据：任何「工具告诉我屏幕上有什么」的结论，
都要能被「人眼（或像素）看到的」复核一次。
复核不必每次做，但每个新结论第一次成立时必须做一次——
因为错误的结论会立刻变成设计约束（这次差点变成「resize 必须清屏」，而清屏是错的）。

## 骗法四：能力探测探的是另一个能力

你以为在问「我能不能做 X」，实际问到的是「我能不能做 Y」，而 Y 恰好是允许的。

pai 的实例：要合成鼠标点击来测终端的鼠标上报，先探一下 macOS 的辅助功能权限：

```
osascript -e 'tell … System Events to get name of first process'   → 正常返回
osascript -e 'tell … System Events to click at {300, 300}'         → -25211 不允许辅助访问
```

读进程列表与合成输入事件在 macOS 里是两级权限。我拿前者的成功当成了后者可用的证据，
写完整套驱动、跑起来才在真正那一步撞墙。

判据：探测语句与真正要用的语句，必须是同一个动作。
「能连上数据库」不等于「能写这张表」，「能列出文件」不等于「能读这个文件」，
「API 返回 200」不等于「这个字段有值」。
最省事的做法：用真正的那条语句做一次最小副作用的试跑，而不是找一个"看起来同类"的便宜替身。

## 骗法五：仪器让被测路径结构上走不到（2026-08-26 追记）

前四种都是「观测到的东西不对」。第五种更隐蔽：观测链路没有报告任何错误，
它只是让某条路径在这套仪器下不可能被执行——于是你永远看不到它的任何行为，
包括它的 bug。

pai 的实例（feature 38）：假 provider 对每一轮都回同一个 `usage`
（`prompt_tokens` 恒为 100）。真 provider 的 `prompt_tokens` 随对话增长，
而 pai 的锚点簿记的正是这个数、切点算法靠相邻锚的差值反推。
差值恒为 0 意味着：无论对话多长、无论保留门槛设多小，切点永远算成「无可压」。
自动压缩因此在所有 e2e 里结构上走不到，而没有任何测试会因此变红——
它们只是从来没走到过那一段。这条路空了十几天，期间还有人（2026-08-10 的用户）
在真实使用里报告过「压缩一次都没触发」，两边一直没接上头。

判据：给假的那一端列一张「它与真的哪里不同」的表，然后逐条问
这处不同会不会让某条被测路径不可达。不是「像不像」，是「可达不可达」。
特别值得查的是常量化的字段——真实世界里会变的东西，在假实现里被写成了定值，
而下游可能正靠它的变化做判断。

修法同样具体：让假的那一端在这个维度上也会变（pai 的做法是
`prompt_tokens` 每轮增长一个常数），而不是在测试里绕过那道坎。
绕过去的测试会绿，但绿的是绕过去的那条路。

## 共同的形状

前三次的现象完全一致：你以为找到了被测代码的 bug。
第四次略有不同——它让你以为自己有能力做一次观测，结果那次观测根本没发生。
第五次最安静：它什么现象都不给你，只是让一整条路径从此不被执行。
五次的真相都在观测链路上，不在被测对象上。所以：

1. 先怀疑最近新加的那个工具，尤其当「bug」的形状很奇怪（少了几行、多了一列、
   混进了不该存在的内容）。真实的渲染 bug 通常有一致的规律，工具的假象往往没有。
2. 每个观测工具自己要有测试（pai 的终端模拟器有 21 条）。
   feature 14 复盘写过一次「验证工具自己也要被验证」，feature 13 又撞两次——
   说明这条不是一次性教训。
3. 交叉验证要换一条独立的链路，不是把同一个工具再跑一遍：
   读屏 vs 截图、录制 vs 直接抓 pty、模拟器 vs 真终端。
   同源的两次观测一起错，而且错得一模一样。
