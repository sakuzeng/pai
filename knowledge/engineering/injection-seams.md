# 装配期捕获：依赖注入最容易犯、最难测的那个错

- 来源：无单一外部原文。2026-08-11 在 pai 上**同一个坑连撞两次**之后的整理
  （docs/dev/features/12-20260811-tui/）
- 精读日期：2026-08-11
- pai 锚点：`src/pai/core/gate.py`、`src/pai/core/permissions.py`（`PermissionModeState`）、
  `src/pai/modes/interactive.py`（`AskerRef`）、features/12-20260811-tui

## 一、形状

依赖注入的常见写法是**在装配期把依赖作为参数传进去**，闭包/字段把它存下来：

```python
def make_gate(rules, mode, asker):
    def gate(tool, args):
        decision = decide(tool, args, rules, mode=mode)   # ← mode 是当时那个值
        if decision.kind == "ask":
            return ask_the_human(decision, asker)          # ← asker 是当时那个函数
    return gate
```

这在依赖**从头到尾不变**时完全正确，也是绝大多数教程里的样子。
问题出在依赖**会变**的时候：

- 用户按快捷键切换了权限模式；
- 界面层起来了，问答通道要从「读一行 stdin」换成「弹一个对话框」。

此时闭包里存的还是**装配那一刻的值**。改外面那个变量不起作用，
因为闭包捕获的是值不是引用（在 Python 里是「捕获了绑定，但调用方换的是另一个绑定」）。

**症状不是报错，是「我改了但没反应」**，或者更坏——像 pai 撞到的那样，
旧依赖走到一条已经不成立的路径上（在 raw mode 下调 `input()`），把程序整个卡死。

## 二、判据：这个依赖会不会在进程生命周期内改变？

| 依赖 | 会变吗 | 怎么传 |
|---|---|---|
| 规则集、配置文件内容 | 不会（会话级不变量） | **传值**，捕获没问题 |
| 当前模式、当前主题、当前用户 | 会 | **传持有者**，每次现取 |
| 问答通道、日志通道、渲染器 | 会（不同前端不同实现） | **传持有者** |

写法上只差一点：

```python
current = mode() if callable(mode) else mode      # 兼容旧的传值调用
current_asker = asker.get() if hasattr(asker, "get") else asker
```

保留「也能传值」这条，旧调用方（如非交互模式）一个字都不用改——
这一点很重要，否则「改成可变」本身就成了一次破坏性变更。

## 三、为什么它特别难测

pai 第一次修这个坑（模式）时写的测试是这样的：

```python
gate = make_gate(rules, mode=state, asker=None)
assert gate("write_file", args).kind == "deny"     # default 模式
state.set(BYPASS)
assert gate("write_file", args).kind == "deny"     # bypass 模式
```

**两次都断言 `deny`，所以它换回「捕获成常量」照样绿**——
这条测试什么都没测住。改成两次结果**不同**的场景（`default → deny` /
`acceptEdits → allow`）之后，注入反证才真能打红。

> **规律**：验证「改完立刻生效」的测试，**前后两次的结果必须不同**。
> 一样就说明这条测试不具鉴别力——它验证的是「函数能跑」，不是「函数看见了新值」。

## 四、更值钱的那条：同一个坑会连撞两次

pai 在 feature 12 里**同一天先后撞了两次**：先是权限模式，修完之后
问答通道又以完全相同的形状坏了一遍（而且第二次的后果严重得多——程序死住）。

修第一个的时候，脑子里想的是「模式这个东西要能切」，
而不是「**装配期捕获**这个模式在这份代码里还有几处」。

> **可迁移的做法**：修掉一个「装配期捕获」的 bug 之后，
> **立刻把同一个装配函数的其余参数逐个过一遍**，问同一个问题：
> 「这个会不会在进程生命周期内改变？」
> 修 bug 的当下是唯一一次你脑子里装着这个模式的时刻，错过就得等它自己再炸一遍。

## 五、连带的教训：接缝上的 bug，离线测试结构上看不见

feature 12 交付时有 171 条离线测试全绿，用户真跑当场打回三条，
**三条全在组件之间的接缝上**：

| bug | 接缝 |
|---|---|
| 模型的回答完全不上屏 | 渲染函数返回 `None`（「流式已打过」）↔ 界面层跳过增量事件——**两边都以为对方会打** |
| 权限框卡死 | 装配期捕获的 asker ↔ 界面层换的 asker |
| 排版满屏阶梯 | 渲染函数产出**多行字符串** ↔ 上屏函数假设**单行** |

共同点是：每个组件**单独看都对**，各自的测试也都对。
坏的是「A 认为 B 会做」与「B 认为 A 会做」之间那条没人负责的缝。

> **做法**：逐组件测之外，至少要有**一条把整条链路走完**的测试
> （事件进 → 屏幕上有字），哪怕它很粗。
> 判据：**如果两个组件对同一件事的假设写在各自的注释里，那就是一条缝**——
> 假设没有被任何一段代码强制过。

## 近亲：不是「捕获了旧值」，而是「读得太早」

装配期捕获是**闭包存了旧值**；还有一种长得很像、成因不同的：值是现取的，
但**取的时机排在它被更新之前**。

2026-08-11 的实例（pai feature 13）：一帧画面由「滚动区 + 底部 dock」组成，
视口高度 = 屏幕高 − dock 高，而 dock 的状态行里要显示「已上滚」——
于是依赖成了环：**dock 高度决定视口，视口决定滚动状态，滚动状态又改变 dock 的内容。**
第一版按「渲染 dock → 算视口 → 更新滚动」的顺序走一遍，
结果状态行上的「已上滚」永远慢一帧（用户滚了一次，屏幕上要等下一次按键才提示）。

修法是**画两遍**：第一遍只为量出 dock 有多高，更新完滚动状态，第二遍才是真的画。
代价是 dock 渲染跑两次（纯函数、有缓存，可接受）。

> 判据与装配期捕获同源：**问「这个值是什么时候算出来的，它之后还会变吗」。**
> 区别在于修法——捕获的病要改成传持有者，读得太早的病要改成重排顺序或多算一遍。
> 两者的症状也不同：捕获是「我改了但没反应」，读得太早是「慢一拍」。
